# 契约版本演进

## 1. 版本边界

`enterprise-submission-v1` 是线上消息中的显式标识，也是不可变 schema 的名字。
企业智能体和监管平台都只依赖 `contracts/` 发布物，不依赖对方的语言模型、类、
数据库或源码。任何一方可以完全重写实现，只要继续通过同一组契约一致性测试。

以下版本各自独立：

- 提交契约：`enterprise-submission-v1`
- 回执契约：`enterprise-submission-receipt-v1`
- 错误契约：`enterprise-submission-error-v1`
- 能力发现：`enterprise-submission-capabilities-v1`
- HTTP 认证：`hmac-sha256-v1`
- 设备观测签名：`mineguard-governed-observation-hmac-sha256-v1`

修改其中一个，不自动修改其他版本。

## 2. 何时必须升主版本

发布后的 V1 schema 不原地改变语义。出现以下任一变化必须新建 V2 schema、
OpenAPI 和示例：

- 新增必填字段、删除字段或改变字段类型；
- 收紧或改变枚举、范围、格式、默认值或空值语义；
- 改变哈希覆盖范围、规范化算法或签名材料；
- 改变幂等作用域、窗口含义、来源证明要求；
- 让原先有效消息变为无效，或让同一字段产生不同监管含义；
- 将企业侧声明升级为监管侧结论，或反向改变信任边界。

仅修正错字、增加不具约束力的说明可以做文档补丁，但不得改变 schema 和线上
行为。若必须放宽 V1 校验，也应优先发布新版本，以便审计记录能精确还原当时规则。

## 3. 发布流程

1. 为新版本复制并重命名 schema，不覆盖旧文件。
2. 添加新版本示例、OpenAPI 路径或媒体协商声明和迁移说明。
3. 双方分别运行本地 schema、固定哈希和签名向量测试。
4. 监管端先在 capabilities 中公布 `supported`，企业端探测后启用影子生成。
5. 双方在非生产环境做黄金样例、拒绝样例、重放、幂等和大包测试。
6. 新版设为 `current`；旧版继续为 `supported`。
7. 需要下线时把旧版标为 `deprecated` 并公布 `sunset_at`。除紧急安全事件外，
   建议至少提前 180 天。
8. 日落后仍保留旧 schema、说明和历史解析能力，保证存量审计可重放。

客户端不得“猜测”服务器支持的最高版本。每次部署或缓存到期后读取 capabilities，
只选择双方明确支持的交集。未知契约版本必须拒绝，不能按“接近 V1”宽松解析。

## 4. V1 到后续版本的兼容原则

- `submission_id`、`idempotency_key` 在迁移或重试中保持稳定；转换后的不同版本
  内容必须使用新幂等键或由双方明确约定转换关系，不能静默覆盖。
- 旧消息不补造来源。迁移工具缺少证据时必须输出缺项，而不是用 LLM 填充。
- 监管平台只在版本适配层把契约字段转换成本地领域模型。适配结果、schema
  版本、schema 摘要和原始消息摘要必须一同审计。
- 企业智能体只把本地连接器输出转换成契约对象，不导入监管平台 SDK。
- 新版本不能允许企业智能体直接提交“核实正常”“合法例外”“违规”等监管标签。

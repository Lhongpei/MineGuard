# 契约版本演进

## 1. 版本边界

`enterprise-submission-v1` 是线上消息中的显式标识，也是不可变 schema 的名字。
企业智能体和监管平台都只依赖 `contracts/` 发布物，不依赖对方的语言模型、类、
数据库或源码。任何一方可以完全重写实现，只要继续通过同一组契约一致性测试。

以下版本各自独立：

- 提交契约：`enterprise-submission-v1`
- 回执契约：`enterprise-submission-receipt-v1`
- 错误契约：`enterprise-submission-error-v1`
- 能力发现：`enterprise-submission-capabilities-v1`
- HTTP 认证：`hmac-sha256-v1`
- 设备观测签名：`mineguard-governed-observation-hmac-sha256-v1`
- 矿端遥测批次：`edge-telemetry-batch-v1`
- 矿端遥测回执：`edge-telemetry-receipt-v1`
- 企业内部连接器自动建稿：`enterprise-autofill-ingestion/v1`
- 企业内部连接器来源健康：`enterprise-source-health/v1`
- 企业内部连接器运输签名域：`ENTERPRISE-CONNECTOR-HMAC-SHA256-V1`

修改其中一个，不自动修改其他版本。

`enterprise-autofill-ingestion/v1` 只连接企业伴随 connector 与单矿 Agent，不进入
政府接口。改变来源 revision 起点、签名六行材料、机器权限边界、幂等语义或允许机器
确认/报送，均属不兼容变更，必须发布新版本，不能原地放宽。

`enterprise-source-health/v1` 与业务快照分别版本化；它只能更新时效和采集状态，不能
携带原始记录、修改来源贡献或执行草稿生命周期动作。新增 outcome、改变陈旧边界或把
空结果解释为撤回，都属于不兼容变更。两个企业内部协议目前仍处于首次生产发布前的
共同建设基线，`observed_at`、`coverage_as_of` 和健康心跳必须成套上线，不能只升级
发送端或接收端。

目标架构另外发布一组相互关联但仍各自显式标识的 V2 消息：

- `five-quantity-submission-v2`
- `intake-receipt-v2`
- `analysis-report-v2`
- `risk-delivery-ack-v2`
- `enterprise-risk-response-v2`
- `response-receipt-v2`
- 应用消息与 HTTP 认证：`hmac-sha256-v2`

V2 从 V1 迁移的是产品边界，不是把 V1 原地改名。V2 固定为一个煤矿一个企业
智能体、一份月报包含逐日及三班五量、政府唯一五量引擎和双向风险闭环；V1 继续
保留用于历史解析。V2 六类消息中的任一结构或语义发生不兼容变化，都必须单独升
新版本并同步发布工作流兼容矩阵，不能只修改 OpenAPI 而不更新 schema 和向量。

### 建设期 V2 口径校正（2026-08-01）

V2 尚未作为生产契约发布时，建设基线曾把入井人员量误写成通用“用工量”
`labor_persons`。本次在首个生产发布前一次性校正为 `mine_entry_persons`，并把五个
业务组固定为 `airflow`、`electricity`、`blasting_materials`、
`mine_entry_personnel` 和 `production`。火工品组继续用 `detonators_count` 与
`explosives_kg` 两个不同单位的原子字段表达，不定义二者相加的总量。

旧建设期样例、演示数据库和固定签名向量不构成生产兼容面，应随本次校正重新生成；
不得改写或冒充成新报文。首个生产发布完成后，任何同类字段改名或语义变化都必须按
本文件规则发布新契约版本，不能再次原地修改 V2。

## 2. 何时必须升主版本

发布后的 V1 schema 不原地改变语义。出现以下任一变化必须新建 V2 schema、
OpenAPI 和示例：

- 新增必填字段、删除字段或改变字段类型；
- 收紧或改变枚举、范围、格式、默认值或空值语义；
- 改变哈希覆盖范围、规范化算法或签名材料；
- 改变幂等作用域、窗口含义、来源证明要求；
- 让原先有效消息变为无效，或让同一字段产生不同监管含义；
- 将企业侧声明升级为监管侧结论，或反向改变信任边界。

仅修正错字、增加不具约束力的说明可以做文档补丁，但不得改变 schema 和线上
行为。若必须放宽 V1 校验，也应优先发布新版本，以便审计记录能精确还原当时规则。

## 3. 发布流程

1. 为新版本复制并重命名 schema，不覆盖旧文件。
2. 添加新版本示例、OpenAPI 路径或媒体协商声明和迁移说明。
3. 双方分别运行本地 schema、固定哈希和签名向量测试。
4. 监管端先在 capabilities 中公布 `supported`，企业端探测后启用影子生成。
5. 双方在非生产环境做黄金样例、拒绝样例、重放、幂等和大包测试。
6. 新版设为 `current`；旧版继续为 `supported`。
7. 需要下线时把旧版标为 `deprecated` 并公布 `sunset_at`。除紧急安全事件外，
   建议至少提前 180 天。
8. 日落后仍保留旧 schema、说明和历史解析能力，保证存量审计可重放。

客户端不得“猜测”服务器支持的最高版本。每次部署或缓存到期后读取 capabilities，
只选择双方明确支持的交集。未知契约版本必须拒绝，不能按“接近 V1”宽松解析。

## 4. V1 到后续版本的兼容原则

- `submission_id`、`idempotency_key` 在迁移或重试中保持稳定；转换后的不同版本
  内容必须使用新幂等键或由双方明确约定转换关系，不能静默覆盖。
- 旧消息不补造来源。迁移工具缺少证据时必须输出缺项，而不是用 LLM 填充。
- 监管平台只在版本适配层把契约字段转换成本地领域模型。适配结果、schema
  版本、schema 摘要和原始消息摘要必须一同审计。
- 企业智能体只把本地连接器输出转换成契约对象，不导入监管平台 SDK。
- 新版本不能允许企业智能体直接提交“核实正常”“合法例外”“违规”等监管标签。

## 5. 2026-07-28 矿端批号安全勘误与迁移

试点投产基线在联调中发现：若矿端批号没有认证客户端前缀，全局批号表可能被另一
客户端提前占用。当前系统尚处建设期，因此在首次生产发布前把 V1 示例和 schema
统一收紧为 `{client_id}--batch_{32位小写十六进制摘要}`，并把客户端编码上限
收紧为 88 字符。HMAC 算法和签名材料没有变化，但示例 body 改变，所以固定
body 摘要和签名向量必须随之更新。

已有环境按以下顺序升级，不能静默改写在途批号：

1. 先升级所有边缘端，使新建批次使用客户端命名空间；旧批次一旦分配，重试期间
   仍保持原批号。兼容读取只识别旧实现实际生成的 `batch_{32位小写十六进制}`
   格式，不能借此接受任意无前缀批号。
2. 在旧监管接收策略仍可用的受控窗口内排空、核对所有 legacy pending 批次，
   保存回执和请求体摘要。
3. 确认没有 legacy pending 后再启用监管端强制校验。数据库中已接收的旧批次
   保持只读可查，GET 回执和审计重放不受新入口校验影响。
4. 若强制校验后仍发现旧 pending，不得直接改数据库或自动换批号，因为旧请求
   可能已被监管端接收。应先按原 `batch_id + body_sha256` 查回执；无回执时通过
   经审批的兼容接收窗口处理，有回执时按原回执人工结清。

若任何单位已把旧 V1 作为正式生产契约对外发布，不应原地套用本勘误；应复制为
新契约版本，按第 3 节的双版本和日落流程迁移。

## 6. 2026-07-28 V1 统计窗口与细化指标扩展

本扩展同样发生在首次正式生产发布前：只新增可选 `interval`、扩展指标/单位
枚举，并修正雷管计数的单位约束。已被边缘端和监管端语义校验接受的旧报文不需要
补字段，仍可按原形重放。示例增加了新指标，因此 raw-body 摘要和固定 HMAC
向量同步更新。

部署必须先让接收端支持新字段，再让发送端产生新指标；旧接收端不得靠忽略未知
字段“兼容”新报文。若某单位已把扩展前 V1 对外作为生产契约发布，应将扩展复制
为新版本并走第 3 节迁移，不得原地改变线上 schema。

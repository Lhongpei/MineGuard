# 煤矿五量企业智能体部署与运维

本文只描述当前 Agent ↔ Platform 五量交换 V2。一个 Agent 服务固定绑定一个煤矿和
独立经营主体；另一个所有者的煤矿必须部署另一套进程、数据库、账号和逐矿密钥。
固定目录和设备/API 连接器属于本 Agent，不再部署第三个 `edge-agent` 产品。

本文后续的 systemd/Nginx 示例面向 Linux。Windows 10/11/Server 原生安装、逐矿
实例、WinSW 服务、NTFS ACL、日志及包含隔离证据的状态备份恢复见
[`deploy/windows/README.md`](../deploy/windows/README.md)。两种系统使用同一 V2
合同，但服务托管和文件权限方案不能混用。

## 1. 安装

以下示例把代码放在 `/opt/enterprise-agent`，状态放在
`/var/lib/enterprise-agent`，配置放在 `/etc/enterprise-agent`：

```bash
sudo useradd --system --home /var/lib/enterprise-agent \
  --shell /usr/sbin/nologin enterprise-agent
sudo install -d -m 0755 -o root -g root /opt/enterprise-agent
sudo install -d -m 0750 -o root -g enterprise-agent /etc/enterprise-agent

cd /opt/enterprise-agent/agent
python3 -m venv .venv
.venv/bin/python -m pip install -e .
.venv/bin/enterprise-agent --version
```

从 `agent/` 目录安装很重要。若命令行入口未进入当前 shell 的 PATH，可一直使用绝对
路径 `/opt/enterprise-agent/agent/.venv/bin/enterprise-agent`，不需要反复安装。

## 2. 环境文件与身份

```bash
sudo install -m 0640 -o root -g enterprise-agent \
  deploy/enterprise-agent.env.example \
  /etc/enterprise-agent/enterprise-agent.env

sudo -u enterprise-agent \
  /opt/enterprise-agent/agent/.venv/bin/enterprise-agent hash-password
```

把产生的 PBKDF2 摘要写入单行 `ENTERPRISE_AGENT_USERS_JSON`。不写明文密码。
演示账号 `demo / 123123123` 只在回环且没有正式账号时启用，被强制标记为待换密，
不能确认或提交。

必须逐矿登记并核对以下身份：

| 变量 | 含义 |
| --- | --- |
| `ENTERPRISE_MINE_ID/NAME` | 本实例唯一煤矿 |
| `ENTERPRISE_OPERATOR_ID/NAME` | 该矿独立经营主体 |
| `ENTERPRISE_SYSTEM_ID` | 企业智能体系统身份 |
| `PLATFORM_V2_SENDER_ID` | HTTP 运输发送方，必须与 `ENTERPRISE_SYSTEM_ID` 完全相同 |
| `REGULATORY_SYSTEM_ID/PARTY_ID` | 政府平台接收方身份 |
| `ENTERPRISE_EXCHANGE_KEY_ID` | 企业发出应用消息的 key ID |
| `REGULATORY_EXCHANGE_KEY_ID` | 企业验政府入站应用消息的当前 key ID |

页面不能修改这些值。政府端也必须把 transport sender、应用消息 sender、party 和
mine 绑定成一条逐矿登记，不能相信报文自报身份。

## 3. 双 HMAC、TLS、CA 与换钥

V2 每次请求有两层完整性：

1. 应用消息 HMAC：覆盖 contract、message/correlation/causation、revision、参与方、
   mine、payload JCS SHA-256 和签名 envelope；
2. HTTP 运输 HMAC：覆盖方法、原始 path-with-query、sender、时间、nonce、contract
   和实际 body SHA-256。

两层使用不同固定签名域，并且程序强制要求分别显式配置内容不同的高熵密钥：

```text
ENTERPRISE_EXCHANGE_HMAC_SECRET
PLATFORM_V2_TRANSPORT_HMAC_SECRET
```

远程 `PLATFORM_V2_BASE_URL` 必须是 HTTPS origin，不能带账号、路径、查询或片段。
私有 CA 使用普通 PEM 文件：

```text
PLATFORM_V2_CA_BUNDLE=/etc/enterprise-agent/regulatory-ca.pem
```

客户端拒绝全部 HTTP 重定向，即使目标仍在同一域；反向代理必须直接暴露规范 V2
路径。政府应用签名换钥期间可同时配置上一把 key ID 和 secret：

```text
REGULATORY_PREVIOUS_EXCHANGE_KEY_ID
REGULATORY_PREVIOUS_EXCHANGE_HMAC_SECRET
```

两项必须同时存在。完成存量 outbox/inbox 验证窗口并经双方确认后，再删除上一把。
密钥修改需要重启，不通过网页热更新。

## 4. 数据目录与自动获取

人工上传和直采均为合法采集方式，只记录 `manual_import` 或
`direct_collection`，不计算可信度等级。固定目录示例：

```text
ENTERPRISE_FIVE_QUANTITY_WATCH_DIRS=/srv/mine-readonly/five-quantity-inbox
```

服务账号需要来源目录和文件的读权限，不需要写权限。监听器不递归、不跟随符号链接，
只处理白名单后缀，等待文件大小和 mtime 连续稳定，再用 no-follow 文件描述符读取。
SHA-256 相同内容只建一份草稿。

解析失败的原始字节复制到 Agent 状态目录：

```text
/var/lib/enterprise-agent/five-quantity-quarantine/
```

隔离目录模式 `0700`、文件模式 `0600`；不能位于来源目录内部。来源原件不删除。
数据库路径变化时，隔离目录随新数据库父目录变化。备份时应把数据库、WAL/SHM（若
存在）和隔离目录作为一个状态集合处理。

当前没有任意 URL GET 定时器。为某厂商设备增加 GET 连接器时，至少要逐来源固定
HTTPS origin/path、禁止重定向、私有 CA、独立凭据、请求/响应上限、超时、内容类型、
稳定 source ID、hash 去重、失败隔离和来源健康；不得让业务用户提交任意 URL。

## 5. systemd

```bash
sudo install -m 0644 -o root -g root \
  deploy/enterprise-agent.service.example \
  /etc/systemd/system/enterprise-agent.service
sudo systemctl daemon-reload
sudo systemctl enable --now enterprise-agent
```

示例单元固定回环监听、低权限账号、`UMask=0077`、只写状态目录、只读配置目录、
`NoNewPrivileges` 和最小 capability。若监听目录在 `ProtectHome=true` 覆盖的 home
路径下，服务将不可见；生产建议使用 `/srv/...`，并在单元中按本单位策略显式增加
只读路径。

终端前台启动后没有新日志、命令不返回，是服务器正常 `serve_forever`，不是卡死。
systemd 下用以下命令观察：

```bash
sudo systemctl status enterprise-agent
sudo journalctl -u enterprise-agent -n 200 --no-pager
sudo journalctl -u enterprise-agent -f
curl -fsS http://127.0.0.1:8090/api/v1/health
```

`Ctrl+C` 或 `systemctl stop` 会停止目录监听、outbox/poll 线程和 HTTP 服务。

## 6. HTTPS 反向代理

复制 `deploy/nginx-enterprise-agent.conf.example`，替换域名和证书。浏览器实际 origin
必须与 `ENTERPRISE_AGENT_PUBLIC_ORIGIN` 完全相同，应用只接受同源 Host/Origin。
生产设置 `ENTERPRISE_AGENT_SECURE_COOKIE=true`。

ET/XLSX 等文件经 base64 放入 JSON，请求体会比原文件约大三分之一。后端原文件上限
20 MiB，Nginx `client_max_body_size` 至少配置 32 MiB。只对登录路径限速；不要让
health、文件导入和 outbox 重试共享登录预算。代理日志不得记录 Cookie、CSRF、
请求/响应体或查询中的敏感信息。

## 7. 运行状态与故障处置

登录后查看 `/api/v2/status`：

- `mine_id/system_id` 必须等于本矿登记；
- `platform_configured=true` 只表示配置已加载，不保证网络在线；
- `watched_directories` 是实际白名单；
- `quarantine_directory` 必须在 Agent 状态目录；
- `last_acknowledged_cursor` 只在 delivery ack 成功后推进；
- `acquisition_trust_tiering=false` 是设计约束。
- 默认列表不显示 `discarded`；审计或排障用 `include_discarded=true` 读取原文和状态。

常见故障：

| 现象 | 检查与处置 |
| --- | --- |
| 启动时报 sender 不一致 | 令 `PLATFORM_V2_SENDER_ID=ENTERPRISE_SYSTEM_ID`，并核对政府登记 |
| 远程 HTTP 被拒绝 | 改用 HTTPS；本机 `127.0.0.1/localhost/::1` 才允许 HTTP |
| CA 错误 | 检查 PEM、权限、有效期和完整链；不能使用符号链接 |
| HTTP 30x | 修正平台/代理直接路径，客户端不会跟随 |
| outbox `failed` | 保留原 message ID 和 idempotency key；修复网络/密钥后让后台重试，不能重建消息 |
| 报告签名失败 | 停止业务处理，核对政府 key ID/secret 和系统时间；不要把未验签内容展示为风险 |
| cursor 不推进 | 先检查本地报告是否落库及 ack 是否成功；不能人工跳 cursor |
| 文件重复 | SHA-256 已存在，属于幂等防重，不要通过改文件名绕过 |
| 文件隔离 | 查看收件记录中的受控错误；保全来源原件，修正格式后产生新内容再导入 |
| 临时账号不能确认 | 配置逐用户正式账号及 `confirm`、`submit` 权限，不要放宽 demo 门禁 |

## 8. 备份、恢复与审计

SQLite 静态内容未由应用自身加密，生产卷和备份介质必须使用单位认可的静态加密。
不要在运行中只复制 `.db`；选择停机备份整个 `/var/lib/enterprise-agent`，或使用经过
恢复演练验证的 SQLite 在线备份方案。

恢复后检查：

1. `fq_drafts` 的 queued/submitted 状态和回执存在；
2. `fq_drafts/fq_imports` 的 discarded 记录、原始 payload 和放弃审计事件存在；
3. `fq_outbox` 中发送中记录会安全恢复为 failed 并按原消息重试；
4. `fq_inbox` 报告、ack 状态和 cursor 一致；
5. `fq_responses` 的确认、消息和政府回复回执存在；
6. `/api/v2/audit` 返回 `valid=true`；
7. 隔离文件数量与收件隔离记录相符；
8. 数据库、目录所有者和 `0700/0600` 权限正确。

本地 hash 链能发现非同步篡改和损坏，但不是外部不可抵赖签名。高要求环境应定期把
链头锚定到企业外部只写审计系统，且该系统不能与 Agent 数据库共享写权限。

## 9. 发布验收

```bash
cd /opt/enterprise-agent/agent
.venv/bin/python -m compileall -q src
.venv/bin/ruff check src tests
.venv/bin/pytest -q
```

验收至少包含：每种文件格式、缺失值不插补、人工/直采无信任分层、目录稳定与隔离、
应用/运输签名、七条平台路径、禁止重定向、当前/上一把验签密钥、outbox 重启恢复、
opaque cursor、报告 ack、结构化回复、权限门禁和前端四页流程。

## Legacy

旧 V1 草稿、通用 Harness、新闻和任务调度说明不属于当前默认部署。历史调用方迁移期
如需保留，应在变更单中明确标注 Legacy，并单独验收；不得把 `PLATFORM_BASE_URL`
等 V1 变量混进本页 V2 环境文件，也不得部署独立 `edge-agent` 作为第三产品。

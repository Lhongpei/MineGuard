# 企业填报智能体部署与运维

本页用于把企业端从开发终端中的前台命令，转换为可重启、可监控、数据路径固定的
Linux 服务。企业端和监管平台仍是两个独立部署单元；本服务只持企业账号、草稿库
和平台运输凭证，不应获得监管数据库或来源设备签名密钥。

## 1. 目录与账号

下面使用独立低权限账号和固定绝对路径：

```bash
sudo useradd --system --home /var/lib/enterprise-agent \
  --shell /usr/sbin/nologin enterprise-agent
sudo install -d -m 0755 -o root -g root /opt/enterprise-agent
sudo install -d -m 0750 -o root -g enterprise-agent /etc/enterprise-agent
```

把仓库部署到 `/opt/enterprise-agent`，在 `agent/` 内创建虚拟环境并安装：

```bash
cd /opt/enterprise-agent/agent
python3 -m venv .venv
.venv/bin/python -m pip install -e .
.venv/bin/enterprise-agent --help
```

代码和虚拟环境由发布账号管理，运行账号不应拥有写权限。草稿、审计和提交记录只
写入 `/var/lib/enterprise-agent`。

## 2. 环境文件

复制仓库中的安全字段模板，不要直接复用示例值：

```bash
sudo install -m 0640 -o root -g enterprise-agent \
  deploy/enterprise-agent.env.example \
  /etc/enterprise-agent/enterprise-agent.env
```

使用交互命令生成用户密码摘要：

```bash
sudo -u enterprise-agent \
  /opt/enterprise-agent/agent/.venv/bin/enterprise-agent hash-password
```

然后编辑环境文件中的单行 `ENTERPRISE_AGENT_USERS_JSON`。文件必须保持
`root:enterprise-agent`、`0640`；不得写入明文密码、来源网关 HMAC 密钥或真实
原始材料。平台运输 HMAC 与来源 HMAC 是两类密钥，企业智能体只能持前者。

生产平台地址必须是 HTTPS。企业页面若也由 HTTPS 反向代理提供，应设置
`ENTERPRISE_AGENT_SECURE_COOKIE=true`，并把
`ENTERPRISE_AGENT_PUBLIC_ORIGIN` 设置为浏览器实际使用的唯一 HTTPS origin，
例如 `https://report.enterprise.example`。该值不能含路径、查询、片段或账号信息；
非标准端口必须显式包含。若只是单机或 SSH 隧道上的临时 HTTP 验收，应移除
public origin 并保持 Secure Cookie 为 `false`，否则浏览器不会通过 HTTP 发回
Secure Cookie。

## 3. systemd

复制并核对单元文件中的安装路径、账号和端口：

```bash
sudo install -m 0644 -o root -g root \
  deploy/enterprise-agent.service.example \
  /etc/systemd/system/enterprise-agent.service
sudo systemctl daemon-reload
sudo systemctl enable --now enterprise-agent
```

示例单元的关键约束：

- `WorkingDirectory` 固定代码目录；数据库仍使用环境文件中的绝对路径；
- `EnvironmentFile` 由 root 管理，应用日志不会回显其中的密钥；
- `Restart=on-failure` 处理异常退出，但正常人工停止不会自动拉起；
- `UMask=0077` 限制新建数据库及临时文件权限；
- `ProtectSystem=strict` 把系统和应用目录设为只读；
- `StateDirectory` 与 `ReadWritePaths` 只开放企业状态目录；
- `NoNewPrivileges`、空 capability 集及其他 systemd 沙箱项降低进程权限；
- `KillMode=control-group` 保证停止服务时一并清理其子进程。

服务只监听 `127.0.0.1:8090`。正式多人访问应由企业内网 HTTPS 反向代理连接该
回环端口；临时远程验收可使用 SSH 隧道，不要直接对局域网暴露 8090。

## 4. HTTPS 反向代理

仓库提供 [Nginx 示例](../deploy/nginx-enterprise-agent.conf.example)。域名与证书
必须换成本单位值，并与环境文件保持一致：

```text
ENTERPRISE_AGENT_PUBLIC_ORIGIN=https://report.enterprise.example
proxy_set_header Host report.enterprise.example;
```

代理必须保留这个精确 Host authority，浏览器发送的 Origin 也必须与 public
origin 精确相同。应用不会读取或信任 `X-Forwarded-Host`、
`X-Forwarded-Proto`、`X-Forwarded-For` 来放宽 Host/Origin 校验；真实客户端
地址以受保护的反向代理日志为准。防火墙只向用户开放代理的 443，不开放 8090。

应用连接看到的是代理的 `127.0.0.1`，因此应用内置的登录失败保护只是第二道边界，
不能代替按真实客户端 IP 的边缘限速；多名用户还会共享这一应用侧地址预算。
Nginx 示例只对精确的 `/api/v1/auth/login` 设置独立 `limit_req`，不会误伤 health、
草稿保存或正式提交。代理必须直接看到真实客户端 IP；若它前面还有受信负载均衡器，
应按本单位标准只信任明确上游并正确配置 Nginx real-ip 模块，绝不能无条件信任
任意客户端提供的 X-Forwarded-For。

示例 access log 记录真实连接地址、方法、规范化路径、状态和耗时，不记录查询串、
Cookie、CSRF、请求体或响应体。若接入单位的统一日志平台覆盖该格式，也必须继续
排除认证头和报送内容，并对日志读取设置权限和留存周期。

配置后先在服务器本机检查后端 health，再通过正式域名登录并创建一个测试草稿。
若返回 `host_not_allowed`，核对 Nginx 的 `Host` 与 public origin 的 authority；
若返回 `cross_origin_request_denied`，核对浏览器 URL、HTTPS 与端口是否完全一致。

## 5. 启停、日志与健康检查

```bash
sudo systemctl status enterprise-agent
sudo systemctl restart enterprise-agent
sudo systemctl stop enterprise-agent
sudo journalctl -u enterprise-agent -n 200 --no-pager
sudo journalctl -u enterprise-agent -f
curl -fsS http://127.0.0.1:8090/api/v1/health
```

health 返回 `status=ok` 说明企业 HTTP 服务可响应；
`platform_configured=true` 只说明三项平台配置已装载，不代表监管平台当前在线。
`harness_available=true` 表示受控任务运行时已加载，
`tool_calling_mode=llm|deterministic` 表示当前是模型规划还是纯本地确定性模式；
两者都不表示某一具体任务已完成。正式监控还应单独检测监管 capabilities、HTTPS
证书有效期、系统时钟、磁盘剩余空间、任务失败/等待批准数量和最近一次备份。

日志正常情况下只包含请求路径、状态码和启动信息，不应包含 Cookie、请求体、
密码或 HMAC。若出现提交失败，可按错误码排查，但不要把环境文件或完整报送包贴入
工单和聊天。

## 6. 数据、重启与备份

SQLite 草稿、原始材料摘要、人工核对、回执和审计数据是明文静态存储；应用只通过
系统账号、目录权限和 `UMask` 限制访问，没有宣称数据库本身已加密。生产主机必须
对状态盘或卷启用单位认可的静态加密与密钥托管，备份介质同样加密，并对
`/var/lib/enterprise-agent`、备份读取和恢复操作保留访问审计。

SQLite 主文件运行时可能同时存在 `-wal` 和 `-shm`。不要在服务运行中只复制单个
`.db` 文件。当前企业端没有内置在线备份命令；部署单位应选用以下一种受控方式：

1. 在维护窗口停止服务，确认端口已关闭后备份整个
   `/var/lib/enterprise-agent`，完成后再启动；
2. 使用经过验证的 SQLite 在线备份工具，并在恢复演练中验证草稿、提交记录及
   审计链。

备份必须使用独立的最小权限凭证，设置留存与销毁周期，并通过加密传输送达备份
系统。恢复时先完成审批和审计登记，停止服务，恢复到权限为
`enterprise-agent:enterprise-agent`、目录模式 `0700` 的状态目录，再启动并检查：

- 草稿和回执数量符合备份时点；
- 已成功提交的草稿仍保持锁定；
- 失败提交保留原幂等键和原请求，可在平台恢复后重试；
- 每个重要草稿的审计完整性仍为有效。
- 智能任务、工具调用、批准记录和任务事件链均可读取，过程链完整性仍为有效；
- 中断时正在执行的写动作若被标记为“结果未知”，已由人员对照草稿修订和审计记录
  完成人工处置，不能直接重放。

更换 `ENTERPRISE_AGENT_DB`、`WorkingDirectory` 或运行账号前必须显式迁移数据，
否则“重启后数据丢失”通常只是进程打开了另一份相对路径数据库。

## 7. 发布前验收

从仓库根目录运行完全独立的黑盒验收：

```bash
python3 scripts/verify_two_process.py
```

该脚本使用临时目录，不接触生产数据库或真实密钥，并验证正常链路、权限拒绝、
配置缺失、错误运输密钥、端口占用、平台停机恢复、幂等重试、双端重启持久性及
退出清理；还会经公开 HTTP 接口运行一次无模型煤炭体检并检查工具目录、预算和
任务事件链。发布升级后应同时执行企业端测试和合同校验。

升级前不要遗留待批准的写工具。工具参数摘要同时绑定当前 Harness 和工具定义；
若版本变化，旧批准应失败关闭，由创建人重新发起任务并核对新动作。任务列表只能
返回摘要，完整参数和结果只允许创建人从任务详情读取。发现事件链、参数摘要或结果
摘要校验失败时，应立即停止批准动作、保全数据库副本并进入安全事件处置，不要通过
直接改库把状态改成“成功”。

任务事件 SHA-256 链和同库链头可以发现意外损坏、尾部截断及没有同步更新事件的
局部改库，但不是外部数字签名，不能防住有权同时改写整库并重算摘要的主机管理员。
如需更强不可抵赖性，应把链头定期发送到单位的外部只写审计系统或时间戳服务；该
外部锚定不应与企业草稿数据库共用写权限。

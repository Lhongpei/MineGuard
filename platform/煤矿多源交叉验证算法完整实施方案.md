## 1. 结论与建设目标

本文所称“交叉验证”不是机器学习中的 K 折交叉验证，而是对同一真实生产活动在人员、设备、环境、生产、运输、库存、销售和票税等不同系统中留下的“数字投影”进行一致性验证。

不建议将其实现成一个单一算法。生产可用的系统应由以下六类能力共同组成：

1. **数据真实性与质量检测**：先判断数据是否完整、及时、可追溯、是否可能断传、重放或篡改。
2. **确定性规则与事件匹配**：处理人卡匹配、区域定员、设备启停逻辑等确定性较强的问题。
3. **物料平衡与全局约束优化**：计算全部指标能否同时成立，以及恢复一致性所需的最小修正量。
4. **时序异常与变化检测**：发现单日看似合理、长期模式却突然改变或持续偏移的问题。
5. **概率化证据融合**：区分独立证据与同源重复数据，形成可校准的线索置信度。
6. **反事实和上限求解**：回答“现有高可信数据最多支持多少未申报产量、账外销售量或异常库存”。

平台不只输出一个红黄绿分数，而应同时输出：

- 数据质量状态；
- 全局一致性评分；
- 异常指标及合理区间；
- 最小冲突指标/约束集合；
- 疑似异常方向和可能场景；
- 支持与反驳该场景的证据；
- 数据不足时的“不确定”结论；
- 建议优先核查的对象、时段和原始证据。

### 1.1 必须遵守的四条设计原则

1. **数据质量问题、生产异常和违法违规线索必须分开判定。** 数据断传不能直接解释为停产，也不能直接认定为造假。
2. **合规阈值不能作为“逼数据合规”的推断约束。** 例如，不能把核定产能作为产量估计的硬上限，否则真实超产会被模型错误解释为计量数据异常。
3. **低可信数据不能被简单丢弃。** 它在数值推断中可以降低权重，但其断传、重放、异常平滑等现象本身要进入“数据失真风险”证据链。
4. **模型输出是核查线索而不是事实认定。** 高风险结论必须能回到原始记录、设备、视频片段、业务单据和规则版本。

## 2. 首先解决原方案中的指标口径问题

原文前部的“十二量”为：用工、定位、运煤、出煤、动储、销售、纳税、用电、火工、用风、分风、涌水；后文求解器使用的“十量”为：风量、电量、火工品量、入井人员量、产量、开采量、销售量、运输量、洗煤量、开票量。两者存在替换、重叠和语义不清，不能直接编码。

应建设“指标本体 + 别名映射”，算法面向指标关系图运行，不把“十量”或“十二量”硬编码在程序中。

### 2.1 建议的标准指标编码

| 领域 | 标准编码 | 含义 | 推荐粒度 |
|---|---|---|---|
| 用工 | `labor.roster_count` | 在册/排班人数 | 日、班次 |
| 定位 | `person.underground_count` | 实际井下去重人数 | 分钟、班次 |
| 定位 | `person.labor_hours` | 有效井下人时 | 班次、日 |
| 生产 | `coal.face_output_t` | 工作面估算或计量产量 | 班次、日 |
| 运煤 | `coal.underground_haul_t` | 井下皮带/矿车运煤量 | 分钟、班次 |
| 出煤 | `coal.surface_output_t` | 井口/主井出煤计量 | 分钟、班次 |
| 动储 | `inventory.raw_stock_t` | 原煤库存快照 | 日、盘点时点 |
| 洗选 | `wash.feed_t` | 入洗原煤量 | 班次、日 |
| 洗选 | `wash.product_t` | 精煤/产品煤产出 | 班次、日 |
| 销售 | `sales.shipped_t` | 实际装车发运量 | 车次、日 |
| 开票 | `invoice.coal_quantity_t` | 发票对应煤量 | 单据、日 |
| 纳税 | `tax.declared_quantity_t` | 纳税申报对应销量 | 月 |
| 用电 | `energy.active_kwh` | 有功电量 | 15 分钟、班次 |
| 火工 | `explosive.used_kg` | 审批领用后实际消耗 | 班次、日 |
| 用风 | `air.total_m3_min` | 矿井总风量 | 分钟 |
| 分风 | `air.branch_m3_min` | 分区/工作面风量 | 分钟 |
| 涌水 | `water.inflow_m3_h` | 矿井或分区涌水量 | 分钟、小时 |
| 设备 | `equipment.runtime_s` | 关键设备运行时长 | 秒、分钟 |
| 采掘 | `advance.mining_m` | 采煤推进度 | 班次、日 |
| 掘进 | `advance.tunneling_m` | 掘进进尺 | 班次、日 |

### 2.2 每个指标必须补齐的语义维度

同名指标只有在以下维度一致时才允许直接比较：

- 所属矿井、采区、工作面、设备或库区；
- 原煤、商品煤、精煤、中煤或矸石等物料类型；
- 湿基/干基、含水率和灰分口径；
- 瞬时值、区间累计值、累计表底或时点库存；
- 生产发生时间、过磅时间、记账时间、开票时间和上传时间；
- 计量单位、倍率、正负方向和小数精度；
- 实测值、人工填报值、模型估计值或派生值；
- 数据源、采集链路和上游派生关系。

在指标字典和业务边界未确认前，算法只能进入影子运行，不能形成正式监察线索。

### 2.3 指标必须映射到物理节点或流转边

仅有指标名称还不够。应为每个矿井配置生产物流拓扑：

```text
工作面
  → 井下运输皮带
  → 井下煤仓
  → 主井提升
  → 地面原煤仓
      ├→ 原煤装车销售
      └→ 洗选投料 → 产品煤仓 → 装车销售
```

每个计量点映射到某个节点状态或某条流转边。例如三台串联皮带秤是同一批物料在三条边上的重复观测，不能相加为总运输量。建议保存：

```text
metric_code
physical_object_id
node_or_edge
from_node
to_node
material_type
measurement_type
root_data_source
valid_from
valid_to
```

没有完成物理拓扑映射的指标，只允许进入数据质量和统计异常模块，不进入强物料平衡。

## 3. 总体算法架构

建议采用“两个底座、六层算法、一个决策出口”的结构。

### 3.1 两个底座

**指标关系图**

描述人员、工作面、设备、物料、库存、销售单据之间的关系，以及指标间的物理、业务和时序约束。每个矿井可以覆盖默认参数，但不能修改公共指标语义。

**证据溯源图**

记录每个观测值来自哪台设备、哪个接口、哪份业务单据，经过了哪些聚合和模型处理。证据融合时按独立采集链路计数，避免把同一 ERP 数据导出的销售表、开票表和日报误认为三份独立证据。

### 3.2 六层算法

| 层级 | 能力 | 典型输出 |
|---|---|---|
| L0 | 来源真实性、设备健康和数据质量 | 缺失、迟到、重放、时钟漂移、异常平滑 |
| L1 | 身份、事件和确定性规则匹配 | 无卡、卡人不符、超定员、禁区进入 |
| L2 | 单指标和双指标鲁棒规则 | 越限、比值异常、逻辑不可能 |
| L3 | 全局约束优化和物料平衡 | 一致性评分、最小修正量、冲突集合 |
| L4 | 时序、变点和群体异常 | 模式漂移、长期小幅偏移、同群异常 |
| L5 | 假设驱动的证据融合与反事实求解 | 疑似场景、置信度、潜在异常上限 |

### 3.3 一个决策出口

任何算法结果都进入统一“线索编排器”，由它完成：

- 相同时间、区域和对象的告警合并；
- 支持证据和反驳证据汇总；
- 数据充分性门控；
- 风险分级；
- 生成核查步骤；
- 人工复核、反馈和闭环。

### 4.1 标准观测数据结构

所有数值型数据转换为如下结构：

```json
{
  "event_id": "sha256:...",
  "source_event_id": "POWER01-8847291",

  "signature": "base64...",
  "schema_version": "1.0"

```

### 4.2 时间字段禁止混用

至少保留：

- `event_time`：生产或业务事实发生时间；
- `ingest_time`：平台收到数据的时间；
- `posting_time`：台账记账时间；
- `business_date`：矿井业务日；
- `shift_id`：所属班次。

销售、发运、开票、纳税不能按同一天直接等值比较，必须以业务发生时间和跨期状态变量连接。

内部时间统一规范化为 UTC，同时保存源时区偏移、矿井 IANA 时区和原始时间文本。业务日切点、班次和节假日使用版本化 `shift_calendar`，所有计算窗口采用左闭右开区间 \([start,end)\)。检测到时钟漂移时保留原时间并记录 `clock_offset_ms`，不能静默改写原始时间。

原始事件只追加不覆盖。源系统修订通过新的 `CORRECT` 或 `RETRACT` 事件表达，并在 `correction_of` 指向被修订事件；业务有效时间表示“事实发生于何时”，系统有效时间表示“平台何时得知”。这样既能按当前最新事实重算，也能按当时已知数据复现历史判断。

原始层的旧事件永不更新；`system_valid_to` 只在标准层双时态视图中根据修订链推导，或在支持事务的标准表中关闭旧版本，不能反写原始对象。

契约分为两部分：

- **源签名载荷**：`source_event_id`、`source_record_key`、`source_revision`、业务时间、原始值、设备、序列号和修订指向等，由矿端签名；
- **中心可信元数据**：`event_id`、`ingest_time`、`system_valid_from`、验签结果、中心批次号和血缘节点，由中心生成，矿端传入同名字段时忽略并记录。

每次 `CORRECT` 或 `RETRACT` 必须生成新的 `source_event_id`，沿用稳定 `source_record_key`，并将 `source_revision` 递增。`CORRECT` 必须携带完整新值和 `correction_of`；`RETRACT` 不携带业务数值，但必须携带 `correction_of`、撤销原因和授权引用。修订号必须连续，缺号进入数据质量工单。

### 4.3 四类数值的聚合规则

| 类型 | 示例 | 聚合方法 |
|---|---|---|
| 瞬时量 | 风量、涌水流量 | 时间加权均值、最大/最小值；需要产量时再积分 |
| 区间增量 | 15 分钟电量、班次产量 | 同口径区间求和 |
| 累计表底 | 电表、皮带秤累计量 | 差分，并检测清零、回拨、换表 |
| 时点库存 | 原煤库存盘点 | 状态量，不得直接跨日求和或盲目前向填充 |

### 4.4 幂等和迟到数据

- 中心 `event_id = SHA-256(tenant_id | mine_id | source_system_id | source_event_id | source_revision | payload_hash)`；修订内容或修订号变化必然生成新 ID；
- 接口采用至少一次投递，平台按 `event_id` 幂等；
- 实时窗口可在水位线后形成“暂定结果”；
- 日级求解在次日固定时间形成“初版”，迟到数据到达后生成新修订版；
- 历史线索不覆盖，保留 `analysis_run_id` 和 `revision_no`；
- 数据修订导致风险下降时，要生成“撤销/降级原因”，不能静默消失。

## 5. L0：数据真实性、质量和可信度

### 5.1 质量检查项目

每个来源至少检查：

1. 完整性：预期点数、覆盖时长、连续缺口；
2. 及时性：采集延迟、上传延迟、集中补传；
3. 唯一性：重复事件、重复序号、重复业务单据；
4. 合法性：类型、单位、范围、枚举、主外键；
5. 时序性：时间倒退、设备时钟漂移、累计表回拨；
6. 稳定性：长时间平线、异常低噪声、固定周期重复；
7. 一致性：同设备瞬时量与累计量、主备表、上下游计量；
8. 可追溯性：原始对象、签名、校准记录、接口版本；
9. 设备健康：离线、故障码、校准过期、供电和网络异常；
10. 防重放：相同数据片段重复、时间戳平移后复用。

### 5.2 观测可信度

为每条观测计算：

\[
q_{j,t}=\sum_k\alpha_k q_{k,j,t},\qquad
\sum_k\alpha_k=1
\]

`q` 是面向运维展示的数据质量指数，不是概率。建议初始权重为完整性 0.25、及时性 0.15、设备健康 0.15、校准 0.15、时钟 0.10、溯源 0.10、唯一性与格式 0.10；上线后按业务重要度审批调整。严重断传、签名失败等情况直接设置状态门控。

质量信息分四条通道使用，且同一因素只能进入一次：

- **门控通道**：覆盖不足、签名失败等决定是否允许形成结论；
- **测量方差通道**：计量精度、时间对齐和聚合误差进入 \(\sigma_o\)；
- **来源可靠性通道**：经独立核查确认的长期来源可靠性进入 \(w_o\)；
- **失真风险通道**：低可信、关键时段断传、重放等行为单独形成证据。

如果关键指标全部低可信，系统必须输出“数据不足/无法判断”，不能因为模型容易拟合而给出“数据一致”。

### 5.3 来源可靠性动态更新

每个来源维护 Beta 先验：

\[
r_s=\frac{\alpha_s}{\alpha_s+\beta_s}
\]

经现场校准、人工复核或权威对账确认正确时增加 \(\alpha_s\)，确认失真时增加 \(\beta_s\)。不能只用高风险案件更新，因为这会产生选择偏差；必须保留随机抽样的低风险对照，并在统计更新时使用抽样概率校正。未处罚、未发现问题或逾期未复核不能当作负样本。自动更新设上限，重大调整需审批，避免模型通过历史偏见永久降低某个矿井的可信度。

每次分析开始时必须冻结该窗口使用的来源可靠性版本。不得因为本次某项数据与其他数据冲突，就在同一次运行中自动降低该来源权重；否则模型会通过“不相信冲突数据”来自我消解异常。

### 5.4 数据血缘和独立性

每条数据附带 `lineage_ids` 作为查询缓存，权威血缘存储为 `lineage_node + lineage_edge` 派生 DAG。证据融合时使用版本化 `evidence_cluster_member` 按“独立采集簇”分组：

- 同一 ERP 导出的销售日报和开票汇总属于同簇；
- 同一皮带秤的分钟值、班次值和日报属于同簇；
- 独立摄像机识别、独立电表和人员定位可视为不同簇；
- 共用交换机同时断网的多个传感器，其离线事件不能作为多份独立证据。

除原始血缘外，还要保存派生特征依赖图。若 HSMM 工况、电量残差和设备活动分数都使用同一馈电信号，它们不能再次作为三份证据。共享时钟、网络、人工填报人或校准设备也会形成条件相关，应归入同一依赖域或在融合模型中显式建依赖。

## 6. L1：人员、卡、视频和轨迹交叉验证

### 6.1 统一人员主键

建立：

- 人员主档 `person_id`；
- 定位卡绑定历史；
- 人脸模板版本及有效期；
- 用工单位、岗位、班组和培训资质；
- 排班、请假和外委记录；
- 闸机通行、定位、视频轨迹的来源映射。

卡号会更换，不能把卡号当人员永久主键。所有绑定关系必须带生效和失效时间。

### 6.2 井口通行会话

将以下事件按井口、方向和初始 30～60 秒窗口聚合成一次 `passage_session`：

- 闸机开关；
- 定位卡读卡；
- 人脸识别候选；
- 视频人体跟踪轨迹；
- 金属门/红外计数；
- 门禁授权记录。

窗口应根据视频轨迹开始/结束、闸机开闭和拥堵程度自适应延长或拆分，固定窗口只作为无轨迹条件下的降级策略。

### 6.3 人脸与定位卡匹配

对窗口内的人脸轨迹集合 \(F\) 和卡集合 \(C\) 构造二分图，候选边代价为：

\[
c(f,c)=w_t|\Delta t|+
w_i(1-p_{\text{face-id}})+
w_d d_{\text{direction}}+
w_r d_{\text{route}}+
w_b d_{\text{binding}}
\]

加入代表“未匹配”的虚拟人脸和虚拟卡节点，并配置拒识成本，再使用匈牙利算法或最小费用流完成一对一匹配；否则算法会在数量相等时强制把不相干的人与卡配对。保存前若干个近优匹配及代价差，代价接近时输出匹配不确定而不是强行定人。禁止仅按最近时间贪心匹配，因为多人同时入井时容易错配。

结果分类：

- 有脸、无卡：疑似无卡入井，也可能是读卡器漏读；
- 有卡、无人：疑似带卡不入井，也可能是摄像机遮挡；
- 人脸身份与卡绑定人不同：疑似人卡不符；
- 一人轨迹对应多张卡：疑似一人多卡；
- 同一卡短时间出现在不可能到达的区域：疑似复制卡或定位串号；
- 入井有记录但规定时间内无井下定位：疑似卡人分离或定位盲区；
- 井下出现稳定轨迹但无井口入井记录：疑似绕行或接口缺失。

### 6.4 人数守恒

\[
N^{inside}_t =
N^{inside}_{t-1}+N^{entry}_t-N^{exit}_t+\epsilon_t
\]

将闸机会话推导的井下人数、定位去重人数、视频计数和用工排班分别比较。差异超过容差时，先检查设备覆盖率和迟到数据，再生成线索。

### 6.5 轨迹规则

- 速度和空间跳变：依据巷道拓扑计算最短可达时间，不用二维直线距离；
- 禁区进入：结合区域规则版本、临时作业票和应急授权；
- 超定员：按区域实际人数和规则生效时间计算；
- 异常聚集：同卡长期固定、多个卡轨迹完全一致、周期性复制；
- 作业真实性：工作面人员、设备启停、分风和视频活动联合判断。

生物识别只提供候选身份及置信度。低画质、遮挡、防护装备等场景必须保留人工复核，且不能只凭一次低置信人脸结果形成高等级线索。

### 7.1 约束必须分类

| 类型 | 示例 | 在模型中的处理 |

| 物理/会计守恒 | 期初库存 + 入库 - 出库 = 期末库存 | 近硬约束，允许盘点误差 |

## 8. L3：全局一致性优化模型

### 8.1 模型对象

将窗口内所有潜在真实值、库存状态、在途状态和工况变量组成向量 \(x\)。其中数值型业务量满足：

\[
x_{i,t}\ge 0
\]

第 \(o\) 条观测为 \(y_o\)，统一观测关系为：

\[
y_o=H_ox+b_o+\varepsilon_o
\]

其中 \(H_o\) 是由指标映射编译出的稀疏行向量，可以表示：

- 单点观测；
- 一段时间内的求和或均值；
- 累计表的相邻差分；
- 多个工作面到矿井日报的汇总；
- 库存快照；
- 经校准比例和零点修正后的观测。

\(b_o\) 是已审批的零点偏置。这样日报、串联皮带、库存快照和不同时间粒度可以进入同一模型。

变量域统一约定：

- 产量、流量、库存、工时等物理量非负；
- 有符号调整拆为 \(A=A^+-A^-\)，且 \(A^+,A^-\ge0\)；
- 有符号约束残差拆为 \(u=u^+-u^-\)，且 \(u^+,u^-\ge0\)；
- 目标函数惩罚 \(A^++A^-\) 或 \(u^++u^-\)，不能直接惩罚有符号值。

### 8.2 观测残差

设置正负偏差：

\[
H_ox+b_o-y_o=d^+_o-d^-_o
\]

\[
d^+_o,d^-_o\ge0
\]

归一化残差：

\[
r_o=\frac{d^+_o+d^-_o}
{\max(\sigma_o,\sigma_{\min})}
\]

\(\sigma_o\) 只综合计量误差、聚合误差、单位转换误差和时间对齐误差。来源历史可靠性单独进入 \(w_o\)，避免同一质量因素重复计权。

### 8.3 推荐目标函数

\[
\min
\sum_o w_o\rho(r_o)
+\sum_{k,t}\lambda_k
\frac{u^+_{k,t}+u^-_{k,t}}{scale_k}
+\sum_{a,t}\lambda^A_a
\frac{A^+_{a,t}+A^-_{a,t}}{scale^A_a}
+J_{mode}
\]

其中：

- \(\rho\) 使用 Huber 损失或分段线性近似，避免单个极端值支配模型；
- \(u^+_{k,t},u^-_{k,t}\) 是业务约束正负松弛量；
- \(A^+_{a,t},A^-_{a,t}\) 是需要模型估计而非已知输入的正负业务调整量；
- `scale_k` 消除吨、千瓦时等量纲影响；
- \(J_{mode}\) 惩罚低先验工况和不合理的频繁切换。

吨煤电耗、回收率、时滞等参数默认使用窗口外数据标定并在案件窗口内冻结。参数不确定性通过预先批准的离散情景或固定上下界重复求解，不能在待审窗口中一边拟合参数、一边判断异常。极少数允许的随机效应必须有很窄的先验边界，且单独进入敏感性报告。

若使用加权绝对值或分段线性 Huber，无工况二进制时是 LP，有工况二进制时是 MILP。使用精确 Huber 二次段时分别成为 QP/MIQP；把二次损失作为近优约束再求区间可能成为 QCP/MIQCP。求解器适配层必须按能力选择模型形式，不能把它们统称为 MILP。

#### 8.3.1 权重与惩罚标定

所有权重进入版本化 `objective_parameter_set`，记录来源、样本、审批人和敏感性结果：

- \(w_o\)：只来自案件窗口开始前已冻结的来源可靠性，按同一分析配置归一化使均值为 1，并设置经审批上下界，避免某来源权重趋近 0 或无限大；
- \(\sigma_o\)：来自检定精度、聚合/对齐误差和独立正常残差尺度，不再重复乘 \(w_o\) 中的因素；
- Huber \(\kappa\)：在独立正常残差集上选择，使目标稳健性和正常样本效率达到预设目标；无样本时使用公开默认初值并明确标记“未校准”；
- \(\lambda_k\)：先按“物理守恒 > 设备能力 > 经验关系”的优先级设约束级别，再用单源/多源故障注入，使已知故障优先落到正确来源而不是错误松弛业务守恒；
- \(J_{mode}\) 的先验和切换惩罚按 8.5 节线性化，\(\lambda_p,\lambda_s\) 用已确认工况序列和持续时间标定；
- 候选解释中的复杂度系数只惩罚新增自由参数、放松的独立来源组和特殊状态数量，第一版用于排序，不转换为概率。

发布门槛：每项权重在 \(0.5\times,1\times,2\times\) 敏感性情景下，重点线索方向和首要 MCS 应保持稳定；不稳定时输出“归因依赖参数”，不得给出单一原因。

### 8.4 物料和业务约束

#### 8.4.1 开采进度与产量

若“开采量”表示推进度或采出体积，应按工作面参数转换：

\[
\rho_f^{lo}A_f^{lo}\eta_f^{lo}M_{f,t}
\le P_{f,t}\le
\rho_f^{hi}A_f^{hi}\eta_f^{hi}M_{f,t}
\]

其中 \(M\) 为推进度/体积，\(A\) 为采掘截面积，\(\rho\) 为密度，\(\eta\) 综合回采率和含矸因素。若“开采量”本身已是吨数，则改为经审批的吨数转换区间。参数必须按工作面、煤层和工况冻结，不能全矿共用固定比例。

#### 8.4.2 原煤库存

\[
I^{raw}_t =
I^{raw}_{t-1}+P_t-W_t-S^{raw}_t-O^{raw}_t
+A^+_t-A^-_t+u^{raw,+}_t-u^{raw,-}_t
\]

- \(P_t\)：井口出煤量；
- \(W_t\)：入洗量；
- \(S^{raw}_t\)：原煤直接销售；
- \(O^{raw}_t\)：其他有依据的出库；
- \(A^+_t,A^-_t\)：批准的盘点调整、含水率修正等；
- \(u^{raw,+}_t,u^{raw,-}_t\)：未解释差额。

\(A^+_t,A^-_t\) 默认是带审批和证据的输入事件，不是求解器可任意使用的自由变量；确需估计时必须拆为明确类型、设置物理上界并高惩罚。无限制“其他调整”会让任何异常都变得可解释。

#### 8.4.3 洗选平衡

\[
\eta^{lo}_{g,mode}W_t-u^{wash,-}_{g,t}
\le Q^{product}_{g,t}\le
\eta^{hi}_{g,mode}W_t+u^{wash,+}_{g,t}
\]

\[
\sum_gQ^{product}_{g,t}+Loss^{wash}_t=W_t
\]

按精煤、中煤、煤泥、矸石分别建模，产品率之和考虑工艺损耗。这里回收率边界是冻结参数，因此保持线性；若把 \(\eta\) 和 \(W\) 同时设为变量会形成双线性模型，第一版禁止这样实现。煤质或工况变化时选择已审批参数情景。

#### 8.4.4 产品库存

\[
I^{product}_{g,t} =
I^{product}_{g,t-1}+Q^{product}_{g,t}
-S_{g,t}+A^{product,+}_{g,t}-A^{product,-}_{g,t}
+u^{product,+}_{g,t}-u^{product,-}_{g,t}
\]

#### 8.4.5 井下运输与出煤

\[
P_t = \sum_{\ell=0}^{L}
\gamma_\ell H_{t-\ell}+u^{haul,+}_t-u^{haul,-}_t
\]

其中 \(H\) 为井下运煤量，\(\gamma_\ell\) 描述运输时延和计量差异。对短时间粒度可用显式在途状态代替简单滞后。

#### 8.4.6 销售、发运和开票

\[
F_t = \sum_{\ell=0}^{L_f}
\alpha_\ell S_{t-\ell}+u^{invoice,+}_t-u^{invoice,-}_t
\]

\[
\sum_\ell\alpha_\ell=1,\quad \alpha_\ell\ge0
\]

第一版可使用开票滞后分布；正式模型优先维护在途量和已销售未开票量：

\[
G_t=G_{t-1}+Dispatch_t-Arrival_t
\]

\[
S^{net}_t=Dispatch_t-PhysicalReturn_t
\]

\[
F^{net}_t=InvoiceIssued_t-RedInvoice_t-VoidedInvoice_t
\]

\[
B^{invoice}_t=B^{invoice}_{t-1}+S^{net}_t-F^{net}_t
\]

\[
B^{invoice}_t=
I^{sold\_not\_invoiced}_t-
I^{invoiced\_not\_sold}_t
\]

其中实物退货减少净销售，红字或作废减少净开票，二者不能混用。聚合余额可正可负；正式模型用带时间窗的流匹配变量将每次发运关联到到达、签收和开票事件，并分别维护“已售未票”和“已票未售”，因为两类余额可能在不同合同上同时存在。月级模型再与纳税申报总量核对。存在预开票、退票或跨月结算时，必须通过业务状态变量表示，不能简单判异常。

若只有发票金额或纳税金额，必须使用合同、煤种、质量结算、实际单价、税率和红字冲销逐单转换；禁止用全矿平均煤价简单除回吨数。金额与实物量应保留为不同维度，通过业务单据关系连接。

#### 8.4.7 电量

\[
E_t =
E^{base}_{mode,t}
+\beta^{coal}_{mode}P_t
+\sum_e \beta_e R_{e,t}
+u^{energy,+}_t-u^{energy,-}_t
\]

\(R_{e,t}\) 是通风、排水、提升、洗选等设备运行时长。只用“总电量/产量”会被固定负荷、排水和季节差异严重干扰，因此应先分解基荷和关键设备负荷。

#### 8.4.8 人员与产量

\[
\pi^{lo}_{mode}H^{face}_t-u^{labor,-}_t
\le P_t \le
\pi^{hi}_{mode}H^{face}_t+u^{labor,+}_t
\]

使用工作面有效人时 \(H^{face}\)，不能用矿井全部入井人数。检修、管理、辅助运输人员应分别建模。该经验区间仅在“确认生产”工况下激活，上下界均为软约束。

#### 8.4.9 火工品

\[
B_t =
\beta^{tunnel}_{rock}L^{tunnel}_t+
\beta^{mining}_{mode}Q^{blast}_t+
u^{explosive,+}_t-u^{explosive,-}_t
\]

综采煤量通常不能与火工品简单成比例。火工品优先关联掘进进尺、岩性、爆破作业票和炮采工程量。

#### 8.4.10 风量

风量首先用于安全约束：

\[
V^{branch}_t\ge V^{person}_t,\quad
V^{branch}_t\ge V^{gas}_t,\quad
V^{branch}_t\ge V^{equipment}_t,\quad
V^{branch}_t\ge V^{rule}_t
\]

用总风量推断产量只能作为弱经验关系。更有效的交叉验证是将风机功率、风门状态、压差、瓦斯浓度、工作面人员和分风量联合起来，判断传感器失真或未经计划的作业活动。

#### 8.4.11 涌水与排水

\[
\Delta W^{sump}_t =
Q^{inflow}_t-Q^{pump}_t-Q^{other}_t
+u^{water,+}_t-u^{water,-}_t
\]

涌水量主要用于验证排水设备电耗、泵运行和水仓水位。它可以辅助识别非计划采掘活动，但不能作为独立产量换算依据。

### 8.5 工况选择

为生产、检修、停产、综采、炮采、掘进等工况设置二进制变量 \(z_{mode,t}\)：

\[
\sum_{mode}z_{mode,t}=1
\]

每种工况启用不同参数区间。若工况来自批准计划，则作为观测；若由模型推断，必须输出推断不确定性并与计划差异形成证据。

业务约束通过 indicator/GDP 与工况绑定：

\[
z_{r,t}=1\Rightarrow g_{r,t}(x)\le0
\]

例如仅当 `blasting` 工况为 1 时启用火工品关系，仅当 `production` 工况为 1 时启用劳动生产率区间，检修时不启用最低产出。优先使用求解器原生 indicator；若由 Pyomo GDP 转换为 big-\(M\)，每个 \(M\) 必须从变量边界推导并进入模型测试。

令 \(\tilde\pi_{r,t}=\max(\pi_{r,t},\epsilon_\pi)\) 后重新归一化，避免 \(\log 0\)。对每个工况和相邻时段建立：

\[
s_{r,t}\ge z_{r,t}-z_{r,t-1},\qquad
s_{r,t}\ge z_{r,t-1}-z_{r,t},\qquad s_{r,t}\ge0
\]

\[
J_{mode}=
-\lambda_p\sum_{t,r}z_{r,t}\log\tilde\pi_{r,t}
+\frac{\lambda_s}{2}\sum_{t,r}s_{r,t}
\]

由于每时段只有一个工况，除以 2 后一次状态切换计一次。若模型中没有最小化 \(s\) 的正系数，应再加上界/等式约束，避免 \(s\) 任意取值。

### 8.6 滚动窗口

推荐：

- 实时人员事件：30～120 秒窗口；
- 设备与环境联动：5～30 分钟窗口；
- 生产平衡：最近 7～30 日滚动求解；
- 开票和销售：30～90 日；
- 纳税：按月求解并回溯日级结果。

窗口开始必须传入上一窗口的库存、在途批次、已售未票、已票未售和未完成人员会话，并携带各自区间或惩罚先验；不能只固定为一个点值。窗口尾部保留这些跨期状态及迟到状态，不强制清零。已经最终确认的更早数据冻结，最近 3～7 日允许按修订策略重算，以避免首尾制造假冲突。

### 8.7 最小冲突集合

普通软约束模型总能求解，因此要额外计算可解释冲突：

1. 先运行弹性模型，找出非零残差和松弛量；
2. 将高可信观测限制在计量误差范围内；
3. 对相关约束运行 IIS/冲突精炼；
4. 克隆严格诊断模型，将主模型中所有经验松弛 \(u^\pm\) 固定为 0，或只保留规则中已批准的正常容差；否则模型会通过原软松弛恢复可行；
5. 按“独立根来源—日期—业务环节”或实际可执行干预组定义 \(z_g\)，而不是每个字段一个变量；
6. 对观测带和可放松业务约束分别配置 indicator constraint 或由物理上界推导的有限 \(M_g\)：

\[
-k_o\sigma_o-s^-_o
\le H_ox+b_o-y_o
\le k_o\sigma_o+s^+_o
\]

\[
0\le s^+_o,s^-_o\le M_{g(o)}z_{g(o)}
\]

\[
g_c(x)\le tolerance_c+s_c,\qquad
0\le s_c\le M_{g(c)}z_{g(c)}
\]

7. 第二目标使用

\[
\sum_o\frac{s^+_o+s^-_o}{scale_o}
+\sum_c\frac{s_c}{scale_c}
\]

作为全部观测和业务约束超差量的归一化总和，并按字典序求解：

```text
第一目标：最小化放松组数及其可信代价
第二目标：最小化总超差量
第三目标：最小化原协调目标
```

8. 找到集合 \(S\) 后加入 no-good cut：

\[
\sum_{g\in S}z_g\le |S|-1
\]

枚举前 3～10 个替代 MCS，并报告不同参数/bootstrap 情景下各归因的稳定度。

IIS 是不可约不可行约束子集，不保证数量最少，也不表示集合内每项都错误；MCS 是使模型恢复可行所需放松的组。界面必须明确区分。输出“至少需要修改产量报表组或库存盘点组中的一组；若只修改产量报表，最少增加 1,900 吨”，比单纯输出异常分数更容易核查。

### 8.8 合理区间

在得到最优损失 \(L^\*\) 后，对目标指标分别求：

\[
\min x_{i,t},\quad \max x_{i,t}
\]

约束为：

\[
L(x)\le L^\*+\Delta
\]

\(\Delta\) 不能拍脑袋设置，应在独立正常校准集上选取，使近优区间达到目标经验覆盖率；也可用外部 block bootstrap 或似然比方法标定。该结果默认称为“近优敏感性区间”或“合理区间”，未经覆盖率校准不得称为置信区间。

同时做可观测性/可辨识性检查：

- 连续模型约束雅可比的结构秩和数值秩；
- 缩放后的条件数；
- 目标指标的 profile 是否平坦；
- 多情景区间宽度；
- 概率模型中的后验相关性。

产量、秤比例、库存调整和回收率可相互替代时，即使求解器给出唯一点也可能不可辨识。区间过宽或条件数异常时强制输出“证据不足”。

### 8.9 反向优化

以未申报产量 \(U^P_t\) 为例：

\[
P^{true}_t=P^{reported}_t+U^P_t
\]

\[
\max \sum_t U^P_t
\]

同时保持：

- 高可信电量、运输、库存、洗选和销售观测在误差范围内；
- 设备最大能力和运行时间成立；
- 库存非负且不超过物理容量；
- 参数位于经审批的合理区间；
- 窗口起止库存、在途和未开票状态位于已传入边界区间；
- 所有调整量均有显式业务上界；
- 物料平衡未知松弛量固定为零，或受独立总预算 \(\sum (u^+_k+u^-_k)/scale_k\le B_u\) 限制；
- 非目标数据源的放松数量受 \(\Gamma\) 限制。

求解前检查目标是否有界；无界时输出“现有感知体系无法约束该数量”，不能人为截断。输出应称为“现有证据与假设下可支持的未申报量技术上限”，并附带关键假设。对账外销售、异常库存和虚假运输分别建立不同受约束反事实模型。

### 8.10 反共谋敏感性

普通反向优化默认除被检查的报表外，其他来源均可信。现实中也可能存在两个或多个来源同时失真，因此增加“妥协预算” \(\Gamma\)：

\[
\sum_{g\ne target} z_g\le\Gamma
\]

其中 \(g\) 是独立根数据源组，\(z_g=1\) 表示允许该组超出正常误差，\(\Gamma\) 是允许异常的来源组数量。若要表达不同可信成本，另设：

\[
\sum_{g\ne target}c_gz_g\le B
\]

不能把数量预算 \(\Gamma\) 与成本预算 \(B\) 混用。分别求：

```text
Γ = 0：其他独立来源全部可信时的异常量上限
Γ = 1：允许另一个来源异常时的上限
Γ = 2：允许两个来源共同异常时的上限
```

还可以给定希望隐藏的数量 \(U_0\)，反求最小篡改面：

\[
\min\sum_g c_gz_g,\qquad
\text{s.t.}\quad \sum_tU^P_t\ge U_0
\]

该结果回答“如果要隐藏 2,000 吨，至少还需影响哪些独立计量链”。这不是对共谋事实的认定，而是用于揭示当前感知体系的盲区和补点优先级。

### 8.11 一致性评分

不建议把优化目标值直接线性映射成 0～100。不同矿井规模、指标数量和数据质量会导致目标值不可比。

固定分析配置、指标集合、覆盖等级和参数版本后，为每个假设 \(H\) 预先登记相关观测集合 \(O_H\)、约束集合 \(C_H\)、可估计调整集合 \(D_H\) 和异常统计量：

\[
A_H(W)=
\frac{
\sum_{o\in O_H(W)}w_o\rho(r_o)+
\sum_{k\in C_H,t\in W}
\lambda_k(u^+_{k,t}+u^-_{k,t})/scale_k
+\sum_{a\in D_H,t\in W}
\lambda^A_a(A^+_{a,t}+A^-_{a,t})/scale^A_a
}{
\max(\sum_{o\in O_H(W)}w_o,\epsilon)
}
\]

例如隐瞒产量只使用预先登记的产量、运输、库存、洗选、设备能力等因子，人员无卡假设使用另一套统计量。不得把同一个全局分数复制给全部假设。全局 \(A_{global}\) 只用于总体态势，不参与场景级 P1/P2。

在同矿井/矿型、同工况、同覆盖等级的独立外部确认正常窗口中保存 \(A_{H,j}\)。新窗口为 \(A_{H,new}\)，计算每个假设独立校准的保形 \(p_H\)：

\[
p_H=
\frac{1+\#\{j:A_{H,j}\ge A_{H,new}\}}{n_H+1}
\]

定义经验一致性分位和异常分位：

\[
ConsistencyScore_H=100p_H
\]

\[
AnomalyScore_H=100(1-p_H)
\]

该 \(p_H\) 值不是“正常概率”。滚动重叠窗口不能直接当作交换样本，应使用非重叠或留有间隔的 block calibration，并按矿型/工况做 Mondrian 分组。

正式日级检验单元固定为：

```text
test_id = tenant_id + mine_id + hypothesis_code
          + business_date + analysis_profile_version
```

同一 `test_id` 的迟到数据修订只替换结果，不增加一次新检验。以“同一辖区、同一业务日、全部非生命安全假设”为检验族，对最终 \(p\) 值执行 Benjamini–Hochberg，保存校正后的 `q_value`。P1/P2 使用 `q_value`，不再直接使用原始 \(p\)。尚未终结的重叠窗口只进入 P3 观察；若确需流式正式统计告警，应单独实现预先批准的 online-FDR/alpha-investing 方案，不能复用日级阈值。生命安全硬规则不进入该统计检验族。

同时给出证据等级：

- A：最宽可信参数范围下仍冲突，且有不少于三个独立根数据源；
- B：标准参数范围冲突，放宽范围后可以解释；
- C：仅有趋势、单源或弱统计异常；
- D：数据不完整、模型不可观测或求解不稳定。

校准样本不足时只输出等级和原始残差，不输出看似精确的概率。

### 8.12 数值示例

某日取得：

| 指标 | 观测值 | 正常误差 |
|---|---:|---:|
| 上报产量 | 5,000 吨 | ±2% |
| 主运输皮带 | 7,100 吨 | ±1.5% |
| 洗选投料 | 6,800 吨 | ±2% |
| 原煤库存增加 | 250 吨 | ±100 吨 |

由“洗选投料 + 原煤库存变化”得到：

\[
P\in[6814,7286]
\]

由主运输皮带得到：

\[
P\in[6993.5,7206.5]
\]

假设主运输皮带、洗选计量和库存盘点分别来自三个独立根数据源簇，则除产量报表外的数据共同支持容差带交集：

\[
P\in[6994,7207]
\]

上报产量的计量容差为 \([4900,5100]\)，两者无交集。可能得到：

```text
IIS-1：上报产量 + 主运输皮带
IIS-2：上报产量 + 洗选投料 + 原煤库存平衡

首选 MCS：上报产量记录
容差带交集：6,994～7,207 吨
若以交集中心作展示值：约 7,100 吨
最小向上修正：约 1,994 吨
```

这里的 6,994～7,207 吨是确定性容差带交集，不是 8.8 节的近优统计区间。正确表述是“上报产量与三个独立根数据源簇存在至少 1,994 吨的技术差额，建议核查”，不能表述为“已查实隐瞒 1,994 吨”。

### 8.13 求解器实现选择

- 第一版日级产运储销模型：LP/QP，HiGHS 等即可；
- 工况选择、运输/开票匹配、MCS：MILP，使用支持 indicator constraint、IIS 和解池的求解器更方便；
- 建模层可使用 Pyomo、JuMP 或求解器原生 API；
- 生产环境使用求解器适配层，避免业务模型绑定单一厂商；
- 禁止随意使用 \(10^9\) 等大 \(M\)，应由库存容量、设备能力和窗口长度推导变量上界；
- 主求解使用热启动；合理区间的最小/最大问题可以并行；
- IIS、MCS、反事实和区间只对候选异常触发；
- 保存求解状态、最优界、gap、缩放信息和求解日志。

求解器适配层在启动时登记能力矩阵：

| 能力 | 通用建模层 | 需要原生 API/特定求解器 |
|---|---|---|
| LP、普通 MILP、分段线性损失 | 可统一实现 | 否 |
| QP/MIQP/QCP | 视后端能力 | 是 |
| IIS/冲突精炼 | 接口不完全统一 | 通常是 |
| 原生 indicator constraint | 支持程度不同 | 通常是 |
| 解池/替代 MCS | 支持程度不同 | 通常是 |
| 热启动 | 格式和效果不同 | 通常是 |

Pyomo 等建模层不保证上述能力跨求解器一致。区间求解应克隆已编译模型、增加近优约束并替换目标；IIS、解池和原生 indicator 通过具体求解器适配器调用。服务启动和发布测试必须验证生产求解器确实具备分析配置声明的能力。

## 9. L4：时序、变点与群体异常

约束优化擅长解释业务一致性，但可能漏掉“各系统同步按比例修改”的协同失真，因此需要独立时序检测。

### 9.1 单指标鲁棒基线

按矿井、工作面、工况、班次、工作日类型分别建立基线：

- 中位数和 MAD；
- 分位数回归；
- 带季节项的鲁棒趋势分解；
- 对持续小偏移使用 EWMA/CUSUM；
- 对结构突变使用 PELT 或贝叶斯变点检测。

不建议直接用均值和标准差，因为异常历史会污染基线。

### 9.2 关系残差检测

先由物理/业务模型得到残差，例如：

\[
r^{energy}_t=E_t-\hat E(P_t,R_t,mode_t)
\]

再对残差做变点和异常检测，比直接对原始电量做黑箱异常检测更稳定、可解释。

### 9.3 保形异常分数

在同矿井、同工况的已确认正常残差集合上计算非一致性分数，得到：

\[
p_t=\frac{1+\#\{a_j\ge a_t\}}{n+1}
\]

使用 \(1-p_t\) 作为异常程度。保形方法可给出经验覆盖率，但前提是校准集与当前数据近似同分布；发生设备更换或工艺改变时必须重新校准。

### 9.4 协同篡改检测

重点检测：

- 多个指标在同一时点按固定比例同步缩放；
- 小数尾数、时间间隔或噪声模式异常一致；
- 长时间平线后一次性补传；
- 历史片段平移、复制和循环播放；
- 报表值总是刚好低于监管阈值；
- 原始分钟值与日报汇总值的统计特征不相容；
- 相邻矿井、同类型设备群体中显著异常但内部“完美一致”。

可使用重复片段哈希、动态时间规整、频谱/熵特征、尾数分布和群体稳健距离。无监督模型只用于线索排序，不能单独作为高风险结论。

### 9.5 同群比较

以采掘方式、煤层条件、设备配置、设计产能和灾害等级构造可比矿井群，使用分层模型：

\[
\theta_m=\theta_{group}+\delta_m
\]

样本少的矿井向同群参数收缩，数据充分后逐步使用本矿参数。禁止跨工艺直接比较简单“吨煤指标排名”。

### 9.6 工况识别

工作面工况建议使用隐半马尔可夫模型（HSMM），状态包括：

```text
停产、启动、正常采煤、掘进、放炮、检修、搬家倒面、降负荷、设备异常
```

输入为关键设备功率、开停状态、人员驻留、皮带、视频活动、火工事件和计划信息。HSMM 显式描述不同状态的最短/典型持续时间，能避免一次电流波动被误判为开始生产。

计划信息只作为先验，不能直接当事实；否则系统无法发现计划外作业。工况模型输出每个状态的概率，优化模型可以：

- 第一版直接选择最大概率工况；
- 第二版把状态概率转为工况选择惩罚；
- 低置信工况同时求多个情景，并扩大合理区间。

工况推断和后续验证共享信号时必须防止循环计证。每个派生特征都进入全链路依赖 DAG，并采用以下一种已声明策略：

1. **情景隔离（第一版推荐）**：工况只用于选择参数情景，其输入信号不再作为独立支持证据；原始信号的残差仍可展示，但融合权重归入同一依赖域。
2. **留一域重算**：评价电力证据时，用不含电力域的 HSMM 后验；评价人员证据时，用不含人员域的后验。
3. **联合推断**：将工况、物理状态和观测因子置于同一概率图，一次性计算后验。

不同策略的结果不得混合计分；分析运行清单记录所用策略和依赖图版本。

### 9.7 概率数字孪生

当积累了足够稳定数据后，可将确定性优化模型升级为动态概率图：

```text
工作面活动
  → 开采/产量
  → 皮带与提升
  → 原煤库存
  → 洗选及产品库存
  → 发运销售
  → 开票
  → 纳税
```

人员、电量、设备、火工、风量、涌水是活动状态的旁观测；库存、在途和未开票量是跨期隐状态。观测噪声优先使用 Student-t 分布，正常/异常数据源可用混合分布表示。

只有当每个残差、松弛和参数惩罚都对应明确且归一化的概率分布与先验时，优化解才能解释为最大后验估计；否则它只是正则化数据协调结果。概率模型补充后验区间、候选状态概率和后验预测检查。在线可采用鲁棒卡尔曼滤波、变分推断或粒子滤波，离线用贝叶斯采样标定。第一版不必建设完整贝叶斯系统：先以“参数情景 + 合理区间求解”近似，待数据成熟后再升级。

概率版本开发前必须冻结一份模型卡，至少明确：

```text
状态向量：
  工作面活动、真实产量、各库存、在途量、未开票量、设备偏置
状态转移：
  物料平衡、库存非负、工况持续时间和跨期业务状态
观测分布：
  每类传感器/台账的误差分布、时间聚合和缺失机制
异常源状态：
  正常/失真转移概率、最短持续时间和稀疏先验
推断：
  算法、初始化、多链/多起点、收敛阈值和超时降级
检查：
  后验预测覆盖、残差独立性、模拟恢复和可辨识性
```

异常源状态必须有稀疏和持续性限制，并接受独立设备健康证据约束；否则概率模型可能把所有业务冲突都方便地解释成“传感器异常”。

### 9.8 分布外检测

新设备、新煤层、新工艺或极端灾害条件可能超出训练分布。每次推断同时计算：

- 工况模型的最大状态概率；
- 关键特征到训练样本的稳健距离；
- 参数是否频繁触及边界；
- 预测区间是否异常宽；
- 多个候选解释是否接近。

超过阈值时标记 `out_of_distribution`，自动降级或弃权，不沿用看似精确的历史概率。

## 10. L5：假设驱动的证据融合

### 10.1 不直接融合成一个万能异常分数

先定义可核查假设：

- `H01` 疑似无卡入井；
- `H02` 疑似人卡不符/一人多卡；
- `H03` 疑似未经批准工作面活动；
- `H04` 疑似隐瞒产量；
- `H05` 疑似账外销售；
- `H06` 疑似虚假运输或过磅；
- `H07` 疑似监测数据断传、重放或篡改；
- `H08` 疑似超能力生产；
- `H09` 疑似区域超定员；
- `H10` 疑似安全设施或环境参数异常。

每个假设配置支持证据、反驳证据、必要数据、独立证据簇要求和核查建议。

### 10.2 数据充分性门控

以“疑似隐瞒产量”为例，至少满足：

- 生产窗口覆盖率达到设定值；
- 至少两个独立高可信证据簇；
- 物料平衡或设备运行证据至少有一类；
- 库存边界或销售时滞没有足以解释差异；
- 关键设备检修、计量校准和人工调整记录已纳入。

不满足时输出“观察”或“数据不足”，不能升级为高等级线索。

### 10.3 概率融合模型

有足够历史核查标签后，使用带单调约束的逻辑回归或广义加性模型：

\[
\operatorname{logit}P(H)=
\beta_0+\sum_g f_g(e_g)
\]

- \(e_g\) 为按独立血缘簇聚合的证据；
- 对明显单调关系设置单调约束；
- 同一血缘簇内使用最大证据或有上限的聚合，防止重复计数；
- 使用等距回归或 Platt 方法校准输出；
- 按矿井类型验证校准误差。

标签不足时先使用专家权重形成 0～100 的“线索分”，不得称为概率。待积累复核结果后再升级为校准概率。

由于高风险案件更容易被送审，训练集存在选择偏差。平台必须记录每条候选线索的入审策略和估计抽样概率，持续随机抽取一小部分低风险对照；训练/校准时使用逆倾向加权或双重稳健估计，并按矿型评估。未完成这一设计时，模型输出只能称“已复核队列条件分数”，不能称辖区总体事件概率。

### 10.4 多维输出，不强行压成一个分数

每条线索至少保留：

- `data_quality_score`：数据是否足以判断；
- `consistency_score`：全局业务是否自洽；
- `hypothesis_confidence`：某一异常假设的证据强度；
- `impact_level`：潜在影响范围；
- `urgency_level`：是否仍在持续；
- `review_priority`：供任务排序使用。

可参考：

\[
review\_priority =
confidence\times impact\times persistence\times urgency
\]

但界面必须同时显示各分项，避免一个总分掩盖“不确定性高”。

### 10.5 候选原因竞争

发现不一致后，不直接命名为“造假”，至少比较以下替代解释：

```text
H0：正常波动或业务时滞
H1：单个传感器故障
H2：跨系统时钟错位
H3：工况或参数真实变化
H4：库存盘点、在途量或计量口径问题
H5：产量漏报
H6：账外运输或销售
H7：未经计划工作面活动
H8：多个数据源协同失真
```

为每个候选原因建立受限模型，只允许修改相应变量：

- 称重故障模型只允许调整秤的比例、零点和对应观测；
- 时钟错位模型只允许调整来源时间偏移；
- 库存问题模型只允许调整盘点误差和批准状态；
- 漏报模型允许增加未申报产量，但不能任意改动其他高可信来源；
- 隐蔽工作面模型允许增加未申报活动状态及其资源消耗。

分别计算：

\[
J(H_j)=
\min_\Delta
\sum_iw_i\rho\left(\frac{\Delta_i}{\sigma_i}\right)
+\lambda\Phi_{\text{constraint}}
+\lambda_H Complexity(H_j)
\]

平台展示前三个解释、最小修改量、剩余无法解释的残差及支持/反驳证据。能以更少独立数据源、更小修正量解释现象的假设优先，但第一名仍只是核查方向。

这里是“受约束反事实解释”，不是严格因果反事实。没有经专家确认的因果图、可干预变量和混杂因素控制时，系统只能说明哪种结构化修改最能恢复一致，不能据此声称找到了异常原因。

### 10.6 核查行动优化

当候选假设概率以及“执行动作后可能得到什么结果”的条件概率都已通过历史复核校准时，可从候选动作中选择最能区分当前解释的行动：

\[
a^\*=\arg\max_a
\frac{\mathcal H(H\mid E)-
\mathbb E[\mathcal H(H\mid E,result(a))]}
{cost(a)}
\]

即单位核查成本下最大化预期信息增益。候选动作例如：

- 调取某班次皮带秤原始累计表底；
- 检查某台计量设备校准和维修记录；
- 对指定煤场进行盘库；
- 调取某工作面设备馈电波形；
- 回看具体时段视频及定位轨迹；
- 抽查指定车辆、磅单、门禁和 GPS；
- 核对合同、签收、发票及红字冲销。

第一版通常还没有可靠条件概率，应使用专家配置的“假设—检查动作—成本—区分能力”矩阵，通过 0-1 背包/集合覆盖模型生成预算内启发式核查清单，不得把它称为期望信息增益最优；有足够复核数据后再升级。

### 10.7 自动弃权

出现以下任一情况时，模型应输出“数据修复/人工验证”，而不是强制生成违规线索：

- 关键数据质量低或有效覆盖不足；
- 只有一个弱证据簇；
- 候选解释得分接近；
- 样本处于训练分布之外；
- 参数刚发生未确认变更；
- 合理区间过宽；
- 证据之间高度冲突；
- 求解器未得到可接受 gap。

缺失证据表示“未知”，既不支持也不反对某个假设。

### 10.8 试点期默认分级规则

以下只作为系统试运行初值，不是监管认定阈值，必须经历史回放和专家评审后按场景发布：

```text
P0 实时安全告警
  已配置的生命安全硬规则触发
  → 不等待统计模型，立即推送并保留原始证据

P1 重点核查
  数据充分性通过
  且不少于 2 个独立高可信证据簇
  且日级检验族 BH 校正后 q_value <= 0.01
  且宽参数情景下仍有实质冲突
  → 生成专项核查工单

P2 一般核查
  数据充分性通过
  且日级检验族 BH 校正后 q_value <= 0.05
  且冲突跨 2 个班次持续，或单次差额达到业务最低重要量
  → 进入人工研判队列

P3 观察
  只有单源异常、弱趋势或候选原因接近
  → 延长窗口并等待新增证据

DQ 数据治理
  关键覆盖不足、签名失败、时钟异常、设备校准失效
  → 进入数据质量工单，不输出“正常”
```

“业务最低重要量”应同时考虑绝对差额和相对差额，例如：

\[
gap\ge\max(gap_{\text{absolute}},\ 
ratio_{\min}\times baseline,\ 3\sigma)
\]

绝对量和比例由业务专家按不同场景配置，不能全省共用一个值。

## 11. 重点场景的可执行检测配方

### 11.1 疑似隐瞒产量

支持证据：

- 出煤计量低于电量、提升/皮带运行时长支持的合理区间；
- 运输、入洗、产品库存或销售量无法由申报产量解释；
- 工作面人员、设备、分风和视频显示持续生产；
- 反向优化得到显著未申报产量下限或上限；
- 差异跨多个班次持续存在。

反驳证据：

- 排水、通风、检修等非生产电耗显著增加；
- 消化历史库存；
- 皮带空载、试运行或计量检修；
- 销售/开票跨期；
- 经批准的库存盘点调整。

输出：

- 申报产量；
- 模型合理区间；
- 最小未解释差额；
- 反向优化上限；
- 贡献最大的三至五项证据；
- 建议核查的工作面、设备和日期。

### 11.2 疑似未经批准工作面活动

构造区域活动状态：

\[
A_{zone,t}=f(
person,\ equipment,\ power,\ air,\ methane,\ water,\ video)
\]

使用规则或隐马尔可夫模型判断“停产、检修、生产”状态，与批准采掘计划比较。至少两个独立感知簇持续出现活动，且无法由检修票解释时生成线索。

### 11.3 疑似数据篡改

同时运行：

- 签名、序号和时间连续性检查；
- 重复片段检测；
- 原始点与聚合报表复算；
- 主备传感器和上下游计量残差；
- 噪声、尾数和阈值贴边检测；
- 关键时段选择性断传检测。

“数据高度平滑”本身不是篡改证据，必须结合设备物理噪声特征、同类设备和采集链路变化。

### 11.4 疑似账外销售

使用原煤/产品煤库存、装车过磅、车牌、门禁、GPS、销售单、回款、开票和纳税构建订单—装车—出门—签收—开票链路。采用带时间窗的实体匹配和最小费用流，将每笔实物流与业务单据匹配；无法匹配的高可信出矿物流进入线索池。

### 11.5 超能力生产

先由一致性模型估计产量区间，再独立应用核定产能规则：

- 若区间下界已超过折算上限，证据强；
- 若只有点估计超过但区间覆盖上限，标记为待观察；
- 分别计算日、月、年滚动口径；
- 扣除或纳入政策允许的试生产、能力置换等已审批状态。

## 12. 系统工程架构

### 12.1 矿端边缘节点

职责：

- 协议适配和原始数据缓冲；
- 统一时间同步和设备序号检查；
- 视频人脸、人体、车辆和设备状态结构化；
- 分钟级特征计算；
- 本地确定性告警；
- 原始数据签名和断点续传；
- 网络中断时至少 7 天结构化事件缓存，容量按实测峰值和补传策略复算。

原始视频原则上留在矿端，平台保存事件、截图、短片引用和校验哈希。监管核查时按权限调阅。

### 12.2 监管平台

推荐的可替换参考技术栈：

| 能力 | 参考实现 |
|---|---|
| 消息总线 | Kafka/Pulsar |
| 流式窗口与 CEP | Flink |
| 原始数据湖 | S3 兼容对象存储 + Iceberg |
| 高频分析库 | ClickHouse |
| 配置、规则和案件 | PostgreSQL |
| 缓存和短期状态 | Redis |
| 优化服务 | Python + Pyomo/直接求解器 API |
| 开源求解器 | HiGHS、SCIP；也可接入商业或国产求解器 |
| 模型管理 | MLflow 或等价内网组件 |
| 服务接口 | Java/Go 业务服务 + Python 算法服务 |
| 可观测性 | Prometheus + Grafana + 集中日志 |

技术选型可以替换，但“原始不可变层、标准明细层、聚合特征层、分析结果层”四层数据必须保留。

存储职责必须唯一：

- **Kafka/Pulsar**：传输和短期回放，不是长期事实源；
- **Iceberg/湖仓**：原始事件、标准事件和分析快照的长期事实源；
- **ClickHouse/时序库**：从湖仓或消息流构建的查询投影，可删除重建；
- **PostgreSQL**：主数据、规则、参数、任务、案件和审批等控制面；
- **WORM 对象存储**：证据包、原始文件、视频片段和签名清单。

推荐写入顺序为“边缘批次验签 → 原始层持久化并返回 ACK → 处理清单/outbox → 标准层幂等合并 → 更新查询投影”。原始层每次提交同时生成不可变处理清单，由持续扫描任务确保已 ACK 批次最终进入标准层；另设对账任务发现“已落原始层但未完成标准化”的批次，避免 ACK 后进程故障造成静默漏处理。ClickHouse 不承担事实幂等语义；去重依据 `mine_id + source_system_id + source_event_id` 在标准层完成，查询投影通过版本列或重建处理修订。

保留期应在项目数据分类方案中确定。技术基线可设为：中心秒级普通遥测 30～90 日、分钟级标准数据长期湖仓保存、视频原流留矿端、候选线索的视频片段在矿端到期前自动固化到证据存储。

### 12.3 服务拆分

1. `connector-service`：来源连接器和接口状态；
2. `normalization-service`：单位、时间、实体和指标标准化；
3. `quality-service`：L0 数据质量和设备健康；
4. `identity-match-service`：人员、卡、脸和轨迹匹配；
5. `feature-service`：分钟、班次、日级特征；
6. `rule-service`：规则解析、执行和版本管理；
7. `optimization-service`：滚动窗口求解；
8. `anomaly-service`：基线、残差和变点检测；
9. `evidence-service`：血缘去重和假设证据融合；
10. `case-service`：线索、工单、复核和反馈；
11. `model-registry`：参数、模型和审批；
12. `audit-service`：运行快照、日志和证据哈希。

### 12.4 事件主题

```text
mine.raw.measurement.v1
mine.raw.person-location.v1
mine.raw.access.v1
mine.raw.material-movement.v1
mine.raw.financial-document.v1
mine.normalized.observation.v1
mine.feature.bucket.v1
mine.dq.issue.v1
mine.validation.run.v1
mine.validation.finding.v1
mine.evidence.updated.v1

```

不建议为每座矿井创建一组主题，以免主题数量失控。统一按领域建主题，以 `mine_id + entity_id` 为分区键，保证同一对象的事件相对有序。消息必须携带 `event_id`、`schema_version`、`trace_id` 和 `lineage_ids`。

### 12.5 AI 智能体和大模型的正确职责

大模型不直接读取十几个数字后判断是否违法。它应作为受控编排层，只调用具有确定输入输出的工具：

```text
数据质量查询工具
指标与趋势查询工具
规则执行工具
优化求解工具
证据检索工具
历史案例检索工具
核查行动规划工具
工单草稿工具
```

适合交给大模型的任务：

- 将自然语言核查问题拆成指标、时间、区域和对象；
- 检索适用规则及其有效版本；
- 编排多次求解和证据查询；
- 把结构化结果整理为易读解释；
- 根据候选原因生成核查清单；
- 汇总人工反馈并形成规则改进建议。

不应交给大模型的任务：

- 直接计算物料平衡或替代求解器；
- 凭语言相似性认定违规；
- 修改规则、参数或结案状态；
- 生成不存在的原始证据；
- 在没有工具返回时补全数值。

智能体每一句关键结论都应绑定 `evidence_id`、`rule_version` 或 `analysis_run_id`。工具参数、工具结果和最终答复一并审计；涉及规则发布、风险升级、证据导出和结案必须由有权限人员确认。

## 13. 核心数据库表

以下为最小逻辑模型，使用 PostgreSQL 风格 DDL 表达字段和约束。`metric_observation` 的长期物理事实表应落 Iceberg，ClickHouse 只保存可重建查询投影；其余主数据、配置、运行和案件表落 PostgreSQL。实施仓库应分别生成 Iceberg Schema、ClickHouse 投影 DDL 和 PostgreSQL migration，三者由同一 Schema 定义代码生成，避免手工漂移。

### 13.1 主数据、身份和物理拓扑

以下主数据均使用不可变 ID，并通过有效期保留历史：

```sql
CREATE TABLE tenant (
    tenant_id            VARCHAR(64) PRIMARY KEY,
    tenant_name          VARCHAR(256) NOT NULL,
    status_code          VARCHAR(32) NOT NULL
);

CREATE TABLE jurisdiction (
    jurisdiction_id      VARCHAR(128) PRIMARY KEY,
    tenant_id            VARCHAR(64) NOT NULL,
    parent_id            VARCHAR(128),
    jurisdiction_name    VARCHAR(256) NOT NULL,
    valid_from           TIMESTAMP WITH TIME ZONE NOT NULL,
    valid_to             TIMESTAMP WITH TIME ZONE
);

CREATE TABLE mine (
    mine_id              VARCHAR(64) PRIMARY KEY,
    tenant_id            VARCHAR(64) NOT NULL,
    jurisdiction_id      VARCHAR(128) NOT NULL,
    mine_name            VARCHAR(256) NOT NULL,
    iana_timezone        VARCHAR(64) NOT NULL,
    status_code          VARCHAR(32) NOT NULL,
    valid_from           TIMESTAMP WITH TIME ZONE NOT NULL,
    valid_to             TIMESTAMP WITH TIME ZONE
);

CREATE TABLE canonical_entity (
    entity_id            VARCHAR(128) PRIMARY KEY,
```

## 14. 对外和内部接口

外部接口使用版本化 REST/JSON；大批量数据允许 gzip NDJSON、Avro 或 Protobuf。统一采用 OIDC 访问令牌、`Idempotency-Key`、`trace_id` 和 RFC 7807 错误结构。批次大小、单事件大小、压缩算法、请求超时和并发上限由网关配置并在接口文档公开。

### 14.1 数据接入

```http
POST /api/v1/observations:batch
Idempotency-Key: <batch-id>
```

人员和业务事件使用同一批次信封、签名和 ACK 语义，载荷 Schema 分开：

```http
POST /api/v1/person-locations:batch
POST /api/v1/access-events:batch
POST /api/v1/material-movements:batch
POST /api/v1/inventory-snapshots:batch
POST /api/v1/financial-documents:batch
POST /api/v1/device-health-events:batch
```

每种 Schema 均由注册中心版本化，并提供正常、修订、撤销和错误样例。

批次请求包含事件数、首尾序列号、内容哈希、签名和 `signature_key_id`。只有原始批次进入持久化事实层后才返回持久化 ACK；进入消息队列但尚未落事实层不算成功。响应逐条或按区段返回接受、重复、拒绝及原因，不得因一条坏数据拒绝整批：

```json
{
  "batch_id": "B-001",
  "status": "PARTIAL_ACCEPTED",
  "accepted": 998,
  "duplicates": 1,
  "rejected": 1,
  "next_expected_sequence": 8848290,
  "errors": [
    {
      "source_event_id": "POWER01-8847288",
      "code": "UNIT_NOT_ALLOWED",
      "detail": "metric energy.active_kwh does not accept unit MW"
    }
  ]
}
```

客户端仅对未确认区段指数退避重试；平台通过限流响应和 `Retry-After` 实施背压。

### 14.2 触发分析

```http
POST /api/v1/analysis-jobs
Idempotency-Key: <analysis-request-id>
```

```json
{
  "mine_id": "M001",
  "window_start": "2026-07-01T00:00:00+08:00",
  "window_end": "2026-07-21T00:00:00+08:00",
  "analysis_profile": "production_balance_v1",
  "reason": "scheduled"
}
```

接口先创建可变 `analysis_job`，返回 `202 Accepted` 和任务地址；此时不要求输入快照或运行清单已经生成。任务状态固定为：

```text
QUEUED → SNAPSHOTTING → RUNNING → EXPLAINING
       → SUCCEEDED | PARTIAL | FAILED | CANCELLED
```

`PARTIAL` 必须附求解器当前可行解、best bound、gap 和缺失的后处理步骤。

### 14.3 查询结果

```http
GET /api/v1/analysis-jobs/{analysis_job_id}
GET /api/v1/analysis-jobs/{analysis_job_id}/runs
GET /api/v1/analysis-runs/{analysis_run_id}
GET /api/v1/analysis-runs/{analysis_run_id}/residuals
GET /api/v1/cases?mine_id=M001&status=pending
GET /api/v1/cases/{case_id}/evidence
```

列表接口使用游标分页，不使用大偏移量；长报表和证据包异步生成。查询可以用 `as_known_at` 选择“当前最新事实”或“当时已知事实”。

### 14.4 复核反馈

```http
POST /api/v1/cases/{case_id}/review
```

反馈至少包括：

- 已证实、已排除、数据不足、部分成立；
- 排除或证实原因；
- 对应原始证据；
- 涉及的数据源问题；
- 可用于训练与否；
- 复核人和时间。

人工改结果不能覆盖算法原始输出，只能生成新的审核记录。

`reviewer_id`、机构和复核时间由访问令牌及服务器生成，客户端不能自报。案件状态按固定状态机转换，修改请求携带 `If-Match`/版本号做乐观锁；参数、规则发布和高风险结案采用双人审批。

## 15. 求解流程伪代码

```python
def run_cross_validation(mine_id, window, profile):
    snapshot = load_versioned_input_snapshot(mine_id, window, profile)
    quality = run_data_quality(snapshot)

    if not quality.minimum_requirements_met:
        return build_inconclusive_result(
            reason=quality.blocking_reasons,
            quality_issues=quality.issues,
        )

    observations = normalize_and_align(snapshot)
    modes = load_or_infer_operating_modes(observations)
    parameters = load_approved_parameters(mine_id, window, modes)
    constraints = compile_constraint_graph(profile, parameters, modes)

    model = create_model()
    bind_frozen_parameter_scenario(model, parameters.primary_scenario)
    latent = add_latent_metric_variables(model, observations, window)
    residuals = add_measurement_factors(
        model=model,
        latent=latent,
        observations=observations,
        reliability=quality.observation_reliability,
    )
    slacks = add_business_constraints(model, latent, constraints)
    set_robust_objective(model, residuals, slacks)

    solution = solve(model)
    if solution.status not in {"optimal", "acceptable_gap"}:
        return build_solver_failure_result(solution)

    conflict_set = find_minimum_conflict_set(
        observations, constraints, solution
    )
    intervals = solve_reasonable_intervals(
        model, solution.objective_value, selected_metrics=profile.outputs
    )
    sensitivity = solve_approved_parameter_scenarios(
        observations, constraints, parameters.alternative_scenarios
    )
    temporal = run_residual_and_change_detectors(
        observations, solution, modes
    )
    counterfactuals = run_hypothesis_counterfactuals(
        observations, constraints, profile.hypotheses
    )

    evidence = build_lineage_aware_evidence(
        quality=quality,
        solution=solution,
        conflicts=conflict_set,
        temporal=temporal,
        counterfactuals=counterfactuals,
    )
    cases = evaluate_hypotheses_with_gating(evidence, profile)

    persist_reproducible_run(
        snapshot=snapshot,
        quality=quality,
        solution=solution,
        intervals=intervals,
        sensitivity=sensitivity,
        evidence=evidence,
        cases=cases,
    )
    return cases
```

### 15.1 求解器异常处理

- 超时：返回当前最优解、最优界和 gap，低置信标记；
- 数值不稳定：自动缩放量纲后重试；
- 不可行：检查硬约束/IIS，不得返回“全部异常”；
- 无界：说明变量缺少物理上限或状态边界，属于模型配置错误；
- 参数缺失：回退到经审批的同群宽区间，并降低结论等级；
- 数据不足：输出不确定，不使用零值填补。

## 16. 参数标定与模型训练

### 16.1 参数来源优先级

1. 法规、设计文件和设备铭牌；
2. 检定/校准报告；
3. 矿井审批后的工艺参数；
4. 已确认正常的本矿历史数据；
5. 同类型矿井分层先验；
6. 专家临时区间。

每个参数都要保存来源、样本期、适用工况、上下界、批准人和版本。

### 16.2 历史清洁样本

不能直接把全部历史当正常数据。清洁样本筛选：

- 关键数据覆盖完整；
- 无已知事故、检修、系统切换和计量故障；
- 物料平衡初筛通过；
- 业务专家抽样确认；
- 异常时段不进入基线，或降低权重。

用于保形校准和概率校准的集合必须独立冻结，并尽量由盘点、校准、现场核查等外部事实确认。不能先用当前异常模型把历史“清洗”为正常，再用同一批数据证明该模型误报率低。模型更新后保留独立时间段、整矿或工况作为外部测试集。

### 16.3 鲁棒标定

- 比例参数采用 Theil–Sen、Huber 回归或分位数回归；
- 洗选回收率按煤种和工况分组；
- 电耗分解基荷、设备负荷和生产负荷；
- 参数边界优先取业务可解释的分位区间；
- 样本少时使用同群分层收缩；
- 参数变更先影子验证再生效。

### 16.4 标签体系

复核标签不能只有“真/假”，建议：

```text
confirmed_violation
confirmed_operational_anomaly
confirmed_data_quality_issue
explained_by_approved_activity
false_positive
insufficient_evidence
partially_confirmed
```

只有证据闭环且质量合格的标签才进入监督训练。

真实违规样本少时可组合：

- 规则标注函数；
- 已核实历史案件；
- 具有物理一致性的数字孪生故障注入；
- 正例—未标记学习；
- 能估计规则相关性的弱监督标签模型；
- 主动学习选择“高风险、高不确定、具有代表性”的案件复核。

但不得把“未处罚”视为正常。未经双人或规定流程确认的反馈不进入训练集；对异常集中由少数审核人产生、标签突然翻转和批量同质反馈设置污染监控。

### 16.5 漂移监控

监控：

- 输入缺失率和取值分布；
- 参数残差分布；
- 模型合理区间覆盖率；
- 线索数量和矿井排名突变；
- 人工复核通过率；
- 新设备、新工作面和工艺切换。

区分接口漂移、输入分布漂移、指标关系漂移、概念漂移和概率校准漂移，并按矿型/工况切片。漂移触发“冻结当前自动升级 → 原因审查 → 影子重标定 → 审批 → 灰度 → 可回滚发布”，不得自动大幅放宽阈值以“消灭告警”。

## 18. 测试体系

### 18.1 单元测试

- 单位换算；
- 累计表清零和换表；
- 跨班次、跨日和跨月；
- 库存平衡；
- 开票滞后；
- 一人多卡和多人同时入井匹配；
- 规则生效/失效时间；
- 缺失、重复和迟到事件。

### 18.2 性质测试

自动生成满足全部约束的数据，验证：

- 等比例单位换算不改变结论；
- 同一事件重复接入不改变结果；
- 增加无关指标不改变原冲突集合；
- 在容差内扰动不应频繁翻转告警；
- 真实物料守恒场景的松弛量接近零；
- 注入已知差额后能恢复正确方向和数量级。

### 18.3 故障注入

至少覆盖：

- 隐瞒 5%、10%、20% 产量；
- 销售延迟、开票跨月和库存消化；
- 电表偏置、皮带秤漂移；
- 传感器断传、重放、固定值；
- 多系统同步比例缩小；
- 设备检修造成异常电耗；
- 同卡复制、卡人分离、摄像机遮挡；
- 未计划工作面活动；
- 极端涌水和排水负荷。

另设红队场景：多个系统同步缩放、重写时间戳、复制正常噪声、选择性断传、伪造库存调整以及控制一个或两个独立来源后的最优规避策略。每项指标同时报告点估计和 bootstrap 置信区间，样本不足时不得仅报单一百分比。

### 18.4 历史回放

模型验证必须按时间向前切分，并增加整矿留出和工况留出，禁止随机打散导致未来数据、修订结果或同一事件派生特征泄漏。业务专家对高分、低分和临界样本分层抽检，不能只查看系统认为异常的样本。

三个月数据可以支撑首版物料平衡开发，但不足以校准季节性、年度产能、月度票税和低频工况。正式概率/时序验收应尽量覆盖完整年度；暂时无法取得时，用真实案例和物理一致的数字孪生注入补足，并明确哪些季节和工况尚未验证。

### 18.5 影子运行

正式推送前运行 4～8 周：

- 结果只对项目组和授权业务专家可见；
- 统计每矿每周线索量、误报原因和数据缺口；
- 参数调整全程留痕；
- 达到验收门槛后再分场景开放。

### 18.6 建议验收指标

以下是候选目标，最终应按试点数据确定：

| 类别 | 指标 |
|---|---|
| 数据 | 核心指标有效覆盖率、迟到率、可追溯率 |
| 算法 | 历史已知案例召回率、Precision@K、每矿每周无效线索数 |
| 区间 | 合理区间在确认正常样本上的经验覆盖率 |
| 校准 | Brier 分数、可靠性曲线或分档命中率 |
| 稳定性 | 小扰动导致风险等级翻转的比例 |
| 时效 | 人员实时告警延迟、日级求解完成时间 |
| 解释 | 带完整证据包和版本信息的线索比例 |
| 运维 | 接口可用性、分析任务成功率、可重放率 |

建议把“每矿每周可处理的有效线索数量”作为核心产品指标，而不是追求告警越多越好。

## 19. 部署、性能和安全

### 19.1 计算调度

- 人员、禁区和定员：流式实时；
- 设备/环境联动：5 分钟微批；
- 日级生产平衡：每日定时并在数据修订时增量重算；
- 月度票税：申报数据到达后运行；
- 反事实和最小冲突集合：只对候选异常执行，节省计算。

### 19.2 性能目标建议

- 实时结构化事件接入 P95 小于 10 秒；
- 井口人员事件 P95 告警小于 30 秒；
- 单矿 30 日日级 LP/QP 求解一般小于 1 分钟；
- 含工况二进制和冲突精炼的复杂任务设置 5～15 分钟上限；
- 求解超时必须返回 gap 和降级结果；
- 平台核心服务按至少 99.9% 可用性设计。

实际容量按“矿井数 × 点位数 × 上报频率 × 保留周期”测算。高频原始传感器在边缘形成分钟特征后上送，关键原始片段按需留存引用。

容量公式：

```text
持续 EPS = 矿井数 × 每矿点位数 × 中心有效采样频率
日原始量 = EPS × 平均事件字节数 × 86,400
年逻辑量 = 日原始量 × 365 ÷ 列式压缩比
物理容量 = 年逻辑量 × 副本/纠删码系数 × 1.2 预留
```

仅作采购前压测基线的参考场景：

```text
50 座矿井
每矿 2,000 个遥测点，边缘后平均 0.2 次/秒
每矿 1,000 张活动定位卡，5 秒一次
平均结构化事件 300 字节

持续约 36,000 EPS，设计峰值 100,000 EPS
未压缩约 0.93 TB/日
按 3.5:1 列式压缩约 97 TB/年逻辑容量
考虑冗余和预留约 170～190 TB/年物理容量
```

最终采购必须以试点 30 日真实压缩率、峰值、定位密度和补传流量复算。若中心接收所有点位 1 秒原始值，容量可能增加数倍。

### 19.3 容灾和边缘连续运行

- 矿端至少缓存 7 天结构化事件，中心持久化 ACK 后才清理发送队列；
- 网络恢复后限速补传，不挤占实时安全事件；
- 中心消息、计算、数据库和对象存储跨机架多副本；
- 建议中心 RPO 不高于 5 分钟、RTO 不高于 2 小时；
- 数据库持续归档日志，湖仓元数据和规则配置定期备份；
- 证据对象异地复制，且定期做离线验签；
- 每季度演练断网补传、数据库切换、快照重放和证据恢复；
- 上线验收以 2 倍设计峰值连续压测 2 小时，不丢失已 ACK 事件。

### 19.4 安全

- 生产网、矿端边缘区和监管平台分区隔离；
- 双向证书、接口白名单和最小权限；
- 一矿一证书，支持轮换、吊销和失窃应急处置；
- OIDC 统一身份、监管用户 MFA；
- RBAC + ABAC 同时限制辖区、机构、矿井、数据类别和操作类型；
- `tenant_id` 全链路隔离，控制库启用行级安全策略；
- 数据传输和静态存储加密；
- 密钥由 KMS/HSM 托管，密钥材料不进入配置文件、镜像或日志；
- 原始数据签名、关键事件哈希链；
- 人脸模板单独加密并限制用途；
- 原始视频按法规和内部制度设置留存期；
- 查看、导出、调阅和参数修改全部审计；
- 审计日志写入业务管理员不可删除的不可变存储；
- 规则、参数和模型上线采用双人审批；
- 禁止算法服务直接控制生产设备。

智能体调用工具必须通过独立工具网关：逐工具授权、参数白名单、只读数据查询默认、返回内容与指令隔离、外部文档按不可信数据处理。检索到的文档或证据不得改变系统权限、批准规则或工具调用策略，以防提示注入。

## 20. 实施路线和团队拆分

### 阶段 0：口径与试点准备，2～3 周

- 选 2～3 个数据基础较好的试点矿；
- 完成指标字典、实体编码和班次日历；
- 明确原文“十量/十二量”映射；
- 绘制数据血缘和系统接口清单；
- 确定核查标签和验收指标；
- 收集 3～6 个月历史数据。

退出条件：关键指标语义、来源、单位、粒度和责任人全部明确。

### 阶段 1：数据底座和 L0，4～6 周

- 建设标准观测模型；
- 接入人员定位、出煤、电力、库存、销售等首批数据；
- 完成时间对齐、幂等、质量评分和血缘；
- 建设数据质量看板；
- 实现原始数据快照和重放。

退出条件：核心指标有效覆盖率达到试点约定值，历史任意日期可重算。

### 阶段 2：人员与五量 MVP，6～8 周

- 上线人—卡—脸—轨迹匹配；
- 上线产量、运输、库存、洗选、销售物料平衡；
- 实现规则 DSL、滚动窗口、最小修正和解释；
- 建立线索工单和证据包。

退出条件：故障注入测试通过，业务专家可根据证据包完成核查。

### 阶段 3：扩展十/十二量和高级检测，6～8 周

- 增加电量、人员人时、设备运行、火工、风量、涌水；
- 上线时序残差、变点、重复片段和群体比较；
- 上线最小冲突集合和反向优化；
- 开展参数分层标定。

退出条件：影子运行的线索量、有效率和稳定性达到验收门槛。

### 阶段 4：证据融合与规模化，4～8 周

- 建立假设证据图；
- 用复核标签训练并校准融合模型；
- 多矿批量调度、模型漂移和运维告警；
- 扩展到辖区矿井；
- 建立月度模型治理机制。

## 21. 推荐的第一版范围

第一版不要一次性上线全部“十量/十二量”。建议选择：

1. 人员定位 + 井口闸机 + 人脸/视频；
2. 井口出煤；
3. 井下/出矿运输；
4. 原煤和产品煤库存；
5. 洗选投料及产品；
6. 销售发运；
7. 关键生产、提升、通风、排水设备电量和运行时长。

原因是这些数据能形成最清晰的“人流 + 设备流 + 物料流”闭环。火工品、风量、涌水、开票和纳税应在业务口径、时间跨度和数据质量验证完成后逐步纳入。

第一版必须交付的不是“大模型界面”，而是：

- 一套统一指标和数据契约；
- 一套可配置约束；
- 一个可重算的滚动求解服务；
- 一个最小冲突和合理区间解释器；
- 一个证据去重和线索工单闭环；
- 一组经故障注入和历史回放验证的检测场景。

## 22. 不建议采用的做法

- 把全部指标输入一个自编码器，用重构误差直接判违法；
- 将核定产能作为产量估计硬上限；
- 将缺失数据填零后参与物料平衡；
- 当天销售、当天运输和当天开票直接等值比较；
- 使用总入井人数推算工作面产量；
- 使用总电量除以产量形成全矿统一固定阈值；
- 将综采产量与火工品量强行线性绑定；
- 把多个由同一系统派生的报表当成独立证据；
- 在数据不足时仍输出“低风险/正常”；
- 自动用新增异常数据更新正常基线；
- 只显示风险分数，不提供原始证据和反驳因素；
- 让算法结果未经人工核查直接形成执法认定。

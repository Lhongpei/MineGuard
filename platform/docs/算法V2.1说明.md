# MineGuard 算法 V2.1：稳健交叉验证、物料流、时序与历史证据

> **历史算法资料（Legacy）**：本文记录早期多入口、多算法 V2.1 研究实现，文中的
> `/v1/analyze/*` 和治理写接口不属于当前产品。可复用的历史、时序、加权 L1 和 MCS
> 思路已收敛到唯一十量 V3 引擎；当前口径见
> [十量 V3 部署与运行](../../docs/十量V3部署与运行.md)。

## 1. 定位

算法 V2.1 在原有单窗口交叉验证之外，形成七层能力：

1. 计量语义聚合：先区分窗口总量、区间增量、累计表、时点库存和瞬时流率，再进入分析。
2. 物理主模型：用加权 L1 协调、物料平衡和最小修正集（MCS）识别不能同时成立的来源组合，并对全部最小优先修正情景取保守结果。
3. 时间展开物料流协调：把连续窗口中的生产、运输、库存、加工和销售画成物理网络，在一个模型中解释跨期库存、运输时延、计量误差和损耗区间。
4. 条件历史基线：只使用同矿、同配置、同工况且已经人工核验为正常的过去窗口，以 median/MAD 和上尾最大稳健距离的经验稀有度判断当前窗口是否罕见。
5. 时序异常检测：对同一矿井、来源和指标的历史值或有符号残差检测离群、缓慢漂移、均值变点及来源健康异常。
6. 合法情景库：用不可变版本记录已经审批的检修、停产、调拨等特殊工况，解释符合条件的历史罕见性。
7. 保守证据融合：并列展示物理、条件历史、时序和合法情景是否相互支持，只生成影子复核优先级，不改写物理状态。

整体证据关系如下：

```text
可信观测 ──> 计量聚合 ──> 加权 L1 + 物料平衡 + MCS ──> 物理主结论
                              │
                              ├─> 固定特征 ─> 人工核验正常历史基线 ─┐
                              └─> 来源残差 ─> 过去时时序检测 ──────┤
运行工况 ──────────────────────────────> 合法情景匹配 ─────────┤
                                                                  ↓
                                            保守融合与影子复核优先级
```

这里的“主结论”有明确含义：`analysis.status`、证据等级、物理差额和正式
`review_priority` 仍由物理 L1/MCS、数据质量门和诊断完整性决定。历史和时序只能
提供独立佐证或提出额外复核线索，不能把物理冲突改成一致，也不能单独制造 P1。

各算法可直接从命令行运行：

```bash
mineguard aggregate examples/aggregation_interval.json
mineguard flow examples/flow_normal.json
mineguard flow examples/flow_anomalous.json
mineguard temporal examples/temporal_drift.json
```

在源码目录尚未安装命令时，可使用：

```bash
PYTHONPATH=src python -m mineguard.cli flow examples/flow_normal.json
```

命令也接受内联 JSON、`@文件路径`，或以 `-` 从标准输入读取。输出始终为可机器解析的 JSON。

归档试算结果时，应同时保存输入、输出以及
`mineguard.runtime_manifest.build_runtime_manifest()` 返回的应用、Python、
NumPy、SciPy、Pydantic 和 PyYAML 版本。它不含主机名、路径或账号等部署标识，
可直接附入分析上下文。

## 2. 计量语义聚合

来源注册时必须声明 `measurement_type`：

| 类型 | 聚合规则 | 关键阻断条件 |
|---|---|---|
| `window_total` | 一个窗口只接受一个有效总量 | 多个总量含义不清、窗口边界不一致 |
| `interval_delta` | 对不重叠区间求和 | 区间重叠、越界、覆盖率不足 |
| `cumulative_register` | 相邻表底作差 | 必须有精确期初/期末边界；无标记回退；换表/清零必须 `reset_before=true` |
| `snapshot` | 期末时点值减期初时点值 | 必须有精确期初/期末边界，禁止把窗外变化归入本窗口 |
| `instantaneous_rate` | 相邻点梯形积分 | 边界缺失、采样覆盖不足 |

`min_coverage` 是硬质量门。部分值会保留在 `partial_value` 供排错，但
`aggregate_value=null`，不会进入交叉验证。缺失数据从不补成数值零。

来源容差使用：

```text
effective_tolerance =
  tolerance_abs + |observed_value| × tolerance_rel + resolution / 2
```

这些参数、计量类型、来源可靠度和依赖域均由服务端版本化来源注册表派生，可信
接入调用方不能覆盖。

所有公开算法入口都先做有限值、数量级和集合长度校验。低于可计算精度的容差、
采样周期或时序尺度会在进入积分、标准化或求解器以前被拒绝，避免除零、无穷值
或数值病态被误报成正常业务结果。

## 3. 稳健单窗口交叉验证

严格模型要求所有未放松来源的观测区间与产运、产洗销存业务平衡同时可行。若
不可行，引擎按放松来源组个数从小到大搜索，并完整评估第一层可行的全部情景。

每个优先情景分别输出合理产量区间、最小上报差额、支持来源和独立证据簇。总结果：

- `scenario_union_production_range` 是全部优先情景区间的并集；
- `robust_minimum_reported_gap` 是全部优先情景中最保守的最小差额；
- 任一优先情景无界、情景结论分歧、未找到情景或搜索组合预算耗尽时，
  `diagnostics_complete=false`，证据等级强制为 D，稳健差额不输出；
- P1 还要求 A 级、至少三簇独立证据、全部优先情景共同支持正差额。

共享同一 PLC、数据库、接口、人工台账或复制链路的来源应在
`dependency_domains` 中声明共同域。引擎按共享域的连通分量计数，一条复制链
不会被误算成多份独立证据。

每条观测输出有符号调整、绝对调整、动态容差和归一化残差；产运与库存业务平衡
分别输出 slack 和最小附加修复说明。它们表示“怎样最小代价恢复一致”，不表示
被调整来源必然错误。

质量判断同时使用总体均分和单来源质量下限。一个关键来源质量为零时，不能被
其他高质量来源的平均分掩盖。来源未提供可验证的设备健康或时钟质量时，会保留
中性数值用于连续计算，同时写入 `unverified_dimensions`；这种结果即使存在三簇
独立证据也不能评为 A 级。只有来源注册中明确给出经治理的
`device_health_score` 和 `clock_quality_score` 才视为已验证。

只要存在 `unverified_dimensions`，总体质量状态最高为 `degraded`；若同时存在
签名无效、阻断标记、必需指标缺失、总体质量低于门槛或单来源低于下限，仍优先
判为 `blocked`。质量为 `degraded` 不阻断技术模型计算，因此技术状态仍可能为
`consistent`，但辖区复核优先级必须进入 `DATA`，提示补充设备健康、时钟同步等
验证证据并安排抽查。只有质量为 `sufficient`、未验证维度为空且技术状态为
`consistent` 时，才可标为 `NONE`（无需建账）。

## 4. 历史校准与人工核验正常条件基线

### 4.1 两类历史结果不要混用

系统保留两类用途不同的历史结果：

| 结果 | 数据来源 | 用途 |
|---|---|---|
| `analysis.historical_calibration` | 同矿、同兼容键、哈希有效、质量合格且物理一致的过去 `balance.raw_anomaly` | 对原有单一异常统计量给出经验校准，便于算法连续性和离线复现 |
| `historical_evidence.assessment` | 同矿、同兼容键、同运行工况，且人工标签为 `verified_normal` 的过去窗口 | 多维正常历史证据，参与保守融合和领导端解释 |

前者是旧有技术校准，后者是本次新增的受治理参考知识。本文后续所称“条件历史
基线”，均指后者。不能因为旧校准有 p 值，就把一个未经人工核验的窗口自动当成
“历史合法数据”。

旧有经验校准会从同一矿井选择当前窗口开始时刻以前（允许恰好在边界结束）的历史
`balance.raw_anomaly`。样本还必须与当前窗口具有完全相同的兼容键：特征和引擎
版本、窗口长度、参数哈希、指标/来源/容差/依赖结构、可信接入模式、审批配置
版本及注册表快照均一致。旧版本、管理员直传或任何兼容信息不完整的数据不会混入。
只有哈希有效、质量不低于 0.8 且技术状态为 `consistent` 的窗口可进入该技术
校准；未来、低质量和已异常窗口均排除。至少需要 20 个合格窗口，最多使用最近
500 个，并记录最终样本的 feature ID 与哈希。历史查询超限时直接停用校准，
不截断后继续给概率。

旧校准的经验 p 值使用有限样本 `+1` 校正：

```text
p = (1 + 历史分数中不小于当前分数的个数) / (历史样本数 + 1)
```

历史不足时 `empirical_p_value=null`，不会用少量样本伪造概率。

### 4.2 条件历史样本的硬门槛

一个过去窗口只有同时满足以下条件，才可进入新增条件历史基线：

1. 与当前窗口是同一矿井；
2. 参考窗口已经完整结束，即 `window_end <= 当前 window_start`，不能使用重叠、
   当前或未来窗口；
3. 运行和标签在本次研判的 `decision_time` 以前已经存在，事后补贴的标签不能
   倒灌进过去决策；
4. 引擎、窗口长度、参数、来源/指标/容差/依赖结构、配置版本和注册表快照形成的
   `compatibility_key` 完全相同；
5. 运行输入、物理结果和标签链哈希有效，所属批次没有作废；
6. 批次请求、批次响应和分析上下文三个文档的哈希都有效；
7. 批次 `integrity_origin=created`，即三份摘要在新建批次时生成；升级迁移时才
   补算摘要的 `legacy_backfill` 批次即使当前校验通过，也只能展示，不能进基线；
8. 数据质量分不低于 0.8；
9. `regime_code`、`shift_code`、`season_code` 非空且 `maintenance` 明确为
   `true` 或 `false`，并且完整运行工况上下文逐字段相同；
10. 当前人工标签必须是 `verified_normal`；`legitimate_exception` 不进入正常
    基线；
11. 固定特征集合完整且与当前版本完全相同。

满足条件的样本少于 20 个时返回 `insufficient_history`；这表示“尚不能判断”，
不是“符合历史规律”。样本充足时最多选最近 500 个。系统不会在精确工况样本不足
时悄悄退回到全矿、跨季节或跨班次的大样本池。条件历史证据只在正式可信接入
链路计算；管理员沙箱直调返回未评估，不能作为绕开来源治理的历史样本入口。

### 4.3 固定特征与稳健统计

每个窗口提取以下可解释特征：

- 物理模型的 `raw_anomaly`；
- 生产与主运量的相对差 `gap_ratio.production_transport`；
- 生产与“入洗 + 原煤销售 + 原煤库存变化”的相对差
  `gap_ratio.production_wash_sales_inventory`；
- 五个正式指标各自的 `normalized_residual.<metric_code>`。

同一指标有多个来源时，原始量先取按来源可靠性加权的中位数。对每个特征维度
`j`，参考中心、尺度和当前上尾距离分别为：

```text
m_j   = median(x_1j, ..., x_nj)
MAD_j = median(|x_ij - m_j|)
s_j   = max(1.4826 × MAD_j, 1e-6, 该特征的最小业务效应)
d_current,j = max(0, x_current,j - m_j) / s_j
```

当前固定特征都是“数值越高，异常量越大”的非负量，因此只看上尾；低于历史中心
不会制造异常。当前最小业务效应下限为：`raw_anomaly=0.05`、两个
`gap_ratio=0.005`、各 `normalized_residual=0.05`，用于避免历史 MAD 为零或
很小时把微小数值噪声无限放大。

联合统计量取所有维度中最大的上尾稳健距离：

```text
D_current = max_j(d_current,j)
D_i       = max_j(max(0, x_ij - m_j) / s_j)
```

`driving_feature_names` 记录达到 `D_current` 的维度。联合经验值用同一参考集的
`D_i` 做上尾排名，并保留 `+1` 校正：

```text
p_overall = (1 + 参考样本中 D_i >= D_current 的个数) / (n + 1)
rarity_score = 100 × (1 - p_overall)
```

默认 `p_overall <= 0.05` 才标为 `historically_rare`。该分数表示“相对已核验同类
正常历史少见”，不是违规概率、违法概率或责任概率。

这里必须保留一个统计边界：`m_j` 和 `s_j` 是用这同一批参考样本拟合的，随后仍用
同一批样本的 `D_i` 排名。因此 `p_overall` 是可解释的上尾经验启发式，不是经过
独立校准集或留一法构造的严格 conformal p 值，不提供有限样本覆盖率或误报率保证。
上线后应通过独立回放、时间外验证和分工况告警率监测评估阈值，不能只凭
`p_overall` 作自动决定。

### 4.4 六类人工标签

标签以追加事件保存，修改标签实际是追加新序号；旧事件、填写人、说明、时间和
哈希链都保留。

| 标签 | 业务含义 | 可进入条件基线 |
|---|---|---|
| `verified_normal` | 已核对原始台账、设备记录和业务凭证，确认是可作为正常参考的窗口 | 是 |
| `legitimate_exception` | 确有经审批的特殊工况，且关联一个匹配的不可变合法情景版本；只解释辅助信号 | 否 |
| `confirmed_data_error` | 已确认采集、计量、传输、录入或映射错误 | 否 |
| `confirmed_technical_anomaly` | 已确认设备或生产过程技术异常，但未形成违法认定 | 否 |
| `adjudicated_violation` | 仅用于登记有权限机关按法定程序已经作出的最终结论 | 否 |
| `unresolved` | 证据不足、口径未清或仍在调查 | 否 |

“案件未处罚”“事项已关闭”或“历史上没有人提出异议”都不等于
`verified_normal`。不得批量把未复核旧数据贴成正常标签。`adjudicated_violation`
也不能由算法自动产生；本系统本身不作违法认定。`legitimate_exception` 不能与
正常样本混合估计 median/MAD，场景匹配也不能放宽正常基线。

### 4.5 `OperationalContext` 运行工况

可信接入请求可在窗口级提交：

```json
{
  "operational_context": {
    "regime_code": "longwall",
    "shift_code": "daily",
    "season_code": "summer",
    "maintenance": false,
    "approved_event_codes": [],
    "tags": ["raw-coal"]
  }
}
```

| 字段 | 含义与治理要求 |
|---|---|
| `regime_code` | 最长 64 字符；生产工况代码，例如正常生产、停产、试运转；应来自受控字典 |
| `shift_code` | 最长 64 字符；班次或统计班制代码；不能自由填写人员姓名 |
| `season_code` | 最长 64 字符；季节、水文期或本单位批准的周期代码 |
| `maintenance` | 必须明确为 `true` 或 `false`；当前窗口是否处于已确认的检修工况 |
| `approved_event_codes` | 最多 32 个、每个最长 64 字符；与该窗口关联、已经审批且可追溯的事件/工单代码 |
| `tags` | 最多 64 个、每个最长 128 字符；煤种或工艺线等受控补充标签，不应放个人信息和自由文本说明 |

事件代码和标签不能重复，服务端会排序后保存。只有 `regime_code`、`shift_code`、
`season_code` 都非空，且 `maintenance` 已显式提交布尔值时，才执行条件历史和
合法情景评估；否则返回 `not_evaluated / operational_context_required`，不能把
空上下文当作一个可用正常分组。事件代码和标签是可选的精细分组字段。

整个工况对象是受治理请求及批次上下文的快照，不是设备 HMAC 观测的一部分。
尤其 `approved_event_codes` 当前没有独立的事件注册表、事件来源签名或工单系统
验签；“approved”是业务填报语义，不是平台已独立证明审批真实。部署单位仍须从
排班、工单或生产系统取得依据，禁止为了让当前值“看起来正常”而事后改写。该
对象只参与历史分组、场景匹配和辅助解释，不进入物理 L1/MCS 约束、容差或证据
等级计算，因此不会改变物理结论。

### 4.6 合法情景库

合法情景把已审批特殊工况写成可审计规则，包括适用矿井、工况/班次/季节、
`maintenance`、必需事件代码、必需标签和特征上下界。匹配时：

- 矿井和显式工况必须符合；
- 必需事件代码与标签必须全部出现在当前 `OperationalContext`；
- 设置了上下界的每个特征都必须落在闭区间内；
- 只使用同一 `scenario_id` 的最新生效版本，哈希无效的版本不能使用。

匹配到合法情景后，还必须由该场景的 `feature_bounds` 覆盖本次全部
`driving_feature_names`，才会列入 `historical_explanation_scenarios` 并解释
历史罕见信号。它只说明“这个版本化场景可能解释辅助信号”，不能把例外窗口加入
正常 median/MAD 基线，不能放宽观测容差、删除来源冲突、把物理
`inconsistent` 改成 `consistent`，也不能自动关闭案件。

情景以 `scenario_id + version` 为不可变键：完全相同内容重试是幂等操作；同一键
提交不同内容返回冲突。系统不提供删除或覆盖接口。修改规则必须递增版本；停用也
应新增更高版本并设置 `active=false`，保留旧版本用于历史复现。
`mine_ids=null` 或空数组表示适用全部矿井，风险较高；正式规则应尽量限定矿井，
并至少使用可追溯事件代码、明确工况或合理特征边界，避免创建无条件全局解释规则。

### 4.7 保守融合规则

正式可信接入会把 `historical_evidence`、`legitimate_scenario_matches` 和
`evidence_fusion` 附在每个矿井结果旁边，不修改嵌套的物理 `analysis`：

- 物理状态为 `inconclusive`/`solver_error`，或数据质量 `blocked`，影子优先级
  始终为 `DATA`；
- 物理冲突永不因历史常见、历史不足或合法情景而降为 `NONE`，至少保留 P2；
- 已满足物理 A 级、诊断完整和质量充分条件的 P1 不被历史证据降级；
- 历史罕见或时序异常可以佐证物理冲突，但不能单独产生 P1；
- 物理一致但存在未被合法情景解释的历史罕见或时序异常时，只给
  `shadow_priority=P2`，提示人工复核；
- 合法情景只能消除“历史罕见”这一辅助信号，不能消除物理冲突；
- 历史不足永远不按正常处理。

当前融合结果是“影子研判”：`shadow_priority` 和 `agreement` 用于领导端排序与
解释，不会原地覆盖正式 `review_priority`、案件状态或物理证据等级。需要调整正式
工作流时，必须另行经过版本审批、回归验证和业务授权。

## 5. 时间展开物料流模型

### 5.1 图与时间窗口

一个请求只处理一个矿井和一种统一计量单位。物理网络由以下对象组成：

- `source`：外部物料来源，例如工作面；
- `junction`：不存货的汇合或分流点；
- `process`：当前版本中按物料守恒处理的加工节点；
- `storage`：具有跨期库存状态的节点；
- `sink`：物料离开模型的终点，例如销售接收端；
- `edge`：节点之间的运输或业务流；
- `window`：首尾相接、按时间升序排列的连续窗口。

建议一个请求内使用等长窗口。模型中的时延以“窗口个数”表示，而不是任意秒数。

### 5.2 核心变量和约束

对每条边、发出窗口和允许的时延，模型分别建立发出量 `d` 和最终接收量 `r`。若损耗率范围为 `[Lmin, Lmax]`，则：

```text
(1 - Lmax) × d <= r <= (1 - Lmin) × d
```

边还可以设置每个窗口的最小发出量和最大发出量。若时延为一个窗口，7 月 20 日的发出量会在 7 月 21 日计入到达量。

对库存节点，边界库存连续：

```text
I(t+1) = I(t) + 当期到达 - 当期发出 + 业务补入 - 业务移出
```

初始、期末和全程库存上下界是硬约束。`junction` 和 `process` 节点没有库存项，执行当期流入与流出平衡。`source` 和 `sink` 是模型边界，不强制内部平衡。

业务补入和业务移出由 `allow_business_slack` 控制。启用后，无法由已建模流量解释的差额可以付出高惩罚后进入结果；禁用后，节点平衡是硬约束。业务松弛不是正常流量，也不能自动解释成违法行为，它表示物理图、业务边界或数据仍需核验。

### 5.3 观测误差和目标函数

流量和库存观测都是软观测。单条观测的有效误差为：

```text
E = absolute + relative × |observed_value| + resolution / 2
```

观测调整的权重为：

```text
W = reliability × quality / E
```

主目标使用加权 L1 损失：

```text
最小化 Σ W × |coordinated_value - observed_value|
      + business_slack_penalty × Σ(业务补入 + 业务移出)
```

因此，高可靠、高质量、误差范围较小的观测更难被调整；低可靠或误差较大的观测更可能成为最小修复项。L1 目标比平方误差更不容易被单个极端值拖动，并能给出有方向的最小修复建议。

主目标存在多个等价最优解时，引擎对每条边逐窗口的发出量、最终接收量、
当期到达量、期末在途量以及每个库存边界分别做最小值/最大值剖面求解。只有
上下界在数值容差内重合时才报告点值和 `identified=true`；否则点值为 `null`，
保留可证明的上下界，并将整体状态标为 `underdetermined`。稳定的第二目标只用
于给出可复现的一组观测调整和业务松弛方案，不会再把其中任意选出的流量当作
唯一推断值。底层使用 SciPy HiGHS 双单纯形求解器，并设置单次求解时间上限。

这里的“损耗区间”是区间内可行协调：求解器可以在给定区间内选择可解释数据的损耗。它不是要求结论对区间内所有损耗情景都成立的 min-max 鲁棒证明。

## 6. 输入合同

顶层输入为 `FlowAnalysisRequest`，关键字段如下：

| 字段 | 要求 |
|---|---|
| `request_id` | 调用方生成的非空请求标识 |
| `mine_id` | 单一矿井标识 |
| `unit` | 全图统一单位，默认 `t` |
| `windows` | 至少一个，时区明确、按时间升序且首尾连续 |
| `nodes` | 节点标识唯一 |
| `edges` | 边标识唯一，引用已声明节点，不允许自环 |
| `inventory_states` | 必须与全部 `storage` 节点一一对应 |
| `initial_in_transit` | 所有可能在首个窗口前发出、在分析期内到达的边/窗口必须显式给出接收量边界；确认没有时上下界都写 `0` |
| `flow_observations` | 边的 `dispatch` 或 `arrival` 观测 |
| `inventory_observations` | 库存窗口 `start` 或 `end` 边界观测 |
| `parameters` | 质量门槛、业务松弛、数值容差和 `solver_time_limit_seconds` |

观测还必须给出唯一 `observation_id`、`source_id`、非负数值、测量误差、可靠度、质量分和可信标志。未知观测应直接缺省，不能写成数值 `0`。只有业务上明确记录为零时，才能提交零值观测。

输入采用严格模式：

- 未声明字段会被拒绝；
- `NaN` 和无穷值会被拒绝；
- 时间必须带时区；
- 存储节点、边、窗口和观测引用必须完整；
- 所有观测标识在流量和库存观测之间也必须全局唯一；
- 窗口、节点、边、观测、变量、约束和待剖面数量均有规模预算，超限请求必须拆分；
- 输入数量有有限上限，不能用极大值或无穷值绕过缺失数据表达。

### 6.1 质量门

求解前先执行质量门：

- `trusted=false` 的观测会阻止协调；
- 低于 `minimum_observation_quality` 的观测会阻止协调；
- 可要求最低可用观测数；
- 可要求每个窗口至少有一条可用观测。

质量门失败时返回 `quality_insufficient`，不会把坏数据静默过滤后继续得出看似精确的协调结果。

## 7. 样例与结果解读

### 7.1 正常跨期库存和运输时延

[`examples/flow_normal.json`](../examples/flow_normal.json) 包含四个日窗口：

- 入仓量依次为 `100、80、20、0 t`；
- 发运量依次为 `40、100、60、0 t`；
- 原煤库存轨迹为 `0 → 60 → 40 → 0 → 0 t`；
- 发运边固定延迟一个窗口，7 月 20 日发出的 `40 t` 在 7 月 21 日到达；
- 损耗允许在 `0.5%–1.5%` 之间，接收端观测对应 `1%` 损耗。

该样例返回 `status=optimal`、`objective_value=0` 且 `minimum_repairs=[]`。

### 7.2 异常销售发运观测

[`examples/flow_anomalous.json`](../examples/flow_anomalous.json) 保留相同物理流和库存证据，但把 7 月 21 日销售台账发运量写成 `170 t`。主运、盘库和次日接收端共同支持实际协调值 `100 t`，且该台账观测的可靠度较低。

预期关键输出为：

```json
{
  "observation_id": "dispatch-sales-21",
  "observed_value": 170.0,
  "coordinated_value": 100.0,
  "signed_adjustment": -70.0,
  "normalized_residual": -6.965174129353233
}
```

`signed_adjustment=-70` 表示为了满足全链条最小代价协调，需要将该观测下调 `70 t`。它是核查线索，不是对台账错误原因的自动定性。

### 7.3 必看输出

- `status`：`optimal`、`underdetermined`、`infeasible`、`unbounded`、`quality_insufficient` 或 `solver_error`；
- `edge_windows`：每条边逐窗口的发出、最终接收、当期到达、期初/期末在途、可识别区间、推断损耗和时延分配；
- `inventory_trajectory`：库存边界点值或区间、`identified` 以及是否有直接观测；
- `observation_adjustments`：每条观测的协调值、有符号调整和归一化残差；
- `source_adjustments`：按来源聚合的调整量和最大残差；
- `business_slacks`：尚未由物理图解释的业务补入或移出；
- `minimum_repairs`：按严重程度排序的最小修复建议；
- `assumptions`：本次求解采用的显式假设。

`optimal` 表示需要展示的监管总量在主目标最优解集合中均可唯一识别，但不等于
全部观测正常。`underdetermined` 表示模型可行且主目标已最优，但至少一个监管
总量仍有多解；此时必须依据 `data_gap` 修复项补充独立计量、容量或库存边界，
不能把 `null` 当成零。两种状态都仍应检查目标值、调整、业务松弛和最小修复项。

## 8. 冷启动方法

时间展开物料流本身不依赖历史训练数据。只要物理拓扑、窗口、硬边界、测量误差和最低数量的可信观测齐备，第一批数据即可求解。不过，冷启动阶段不应把参数写得过于精确。

建议按以下顺序影子运行：

1. 与生产、机运、洗选、仓储和销售人员共同确认物理图，尤其确认跨日运输、外购、调拨、返料和盘盈盘亏边界。
2. 测量误差优先采用检定证书、设备分辨率和历史盘点差异；没有依据时使用保守范围并记录参数责任人。
3. 初期可以启用高惩罚业务松弛，观察模型遗漏的合法业务流；拓扑稳定后，再按审批决定哪些节点使用硬平衡。
4. 为每个需要启用条件历史判断的“矿井 + 兼容键 + 完整运行工况”积累至少 20 个
   严格更早、哈希有效、质量不低于 0.8 的人工核验样本；
5. 由有权限人员逐窗调阅原始台账、设备日志和业务凭证，只把真正核验正常的窗口
   标为 `verified_normal` 并计入 20 个正常参考样本；能匹配已审批情景的窗口可
   标为 `legitimate_exception`，但只保留场景解释，不计入这 20 个；
6. 至少覆盖完整生产周期并人工复核异常，再按矿井、工况和季节分别校准损耗、
   时延、可靠度与质量门。

物理模型从第一批可信数据即可工作，但条件历史证据在第 20 个合格参考样本之前
必须显示 `insufficient_history`。如果工况分得很细，每个精确工况都要单独达到
20 个，不能把其他班次或季节拼进来凑数。冷启动结果不能给出真实“违规概率”。
不得批量补贴正常标签，也不得根据少量样本反向调窄误差范围来追求更多告警。

## 9. 两种 LP 的关系

`mineguard production` 面向单个分析窗口，使用既定产、运、储、销、洗指标快速执行交叉验证，并继续承担现有批次分析、证据等级和案件流程所需的主结果。

`mineguard flow` 是补充模型，适合以下问题：

- 今天发出的量为什么明天才出现在接收端；
- 单日不平衡是否可以由前后日库存变化解释；
- 多节点、多条运输边和损耗范围能否共同解释；
- 最小调整落在哪个来源、窗口和物理对象。

两者不应把同一来源当作两份独立证据。推荐先用时间展开模型产生跨期协调值和来源残差，再由经版本管理的映射决定是否把这些结果作为单窗口研判的辅助特征。当前 CLI 不会自动修改证据等级、风险优先级或案件状态。

## 10. 时序检测与领导端

`src/mineguard/temporal.py` 提供按“矿井 + 来源 + 指标”独立分组的过去时检测。每个时点只使用它之前的合格样本，不使用未来数据。序列可以输入原始 `value`，也可以输入物料流输出的 `signed_residual`，但同一序列不能混用两种值。

受治理的生产分析还会在当前批次落库前调用
`src/mineguard/current_temporal.py`：只读取窗口开始时刻以前、同矿、同算法兼容键、
同生产工况/班次/季节/检修状态且批次与运行摘要有效的
`balance.raw_anomaly`，默认至少 20、最多 500 个过去窗口。它把当前窗口作为最后
一点交给过去时检测器，输出 `temporal_evidence.status =
normal|anomalous|insufficient_history`，再进入保守融合。该分支不读取人工正常
标签，也不改写物理结果；“时序正常”只表示当前变化未越过过去时控制限。

模块包含：

- 滚动 median/MAD：识别相对稳健历史基线的单点高低异常；
- EWMA：识别水平逐渐偏离；
- 双向 CUSUM：识别持续正向或负向小偏移；
- Page-Hinkley：识别均值的持续变点；
- 可选统计基线适配：连续同方向异常达到门槛后，把该候选片段作为新统计
  基线种子，并重置 EWMA、CUSUM 和 Page-Hinkley 的累积状态；它不验证
  业务工况，也不能把异常认定为正常；
- 来源健康：单独识别缺失、接收延迟、过度修订和低质量；
- 异常片段：把相邻异常点聚合为可复核事件。

默认基线窗口为 30 个合格点，至少需要 8 个历史点才执行数值异常判断。冷启动期返回 `insufficient_history`；缺失值和低质量值不会补零或进入数值基线。默认情况下，已检测出的数值异常也不会污染后续基线。

为保持已有策略兼容，下面两项增强默认关闭，必须由经版本管理的策略显式启用：

- `minimum_relative_scale` 默认为 `0`。启用后，稳健尺度取
  `max(1.4826 × MAD, minimum_scale, abs(median) × minimum_relative_scale)`，
  避免非零常量序列仅因 MAD 为零而对极小相对波动过敏。每个检测点会回传绝对
  下限、相对下限和本点实际采用的 `effective_scale_floor`。但该公式在有符号
  残差的历史中位数接近 0 时，相对项也接近 0，不能宣称提供了“2% 量级保护”；
  此时实际只剩 `minimum_scale`。
- `baseline_reset_confirmation_points` 默认为 `null`。配置为不小于 2 的整数后，
  只有连续、`baseline_eligible=true` 且相对旧基线同方向的合格异常达到该数量
  才触发适配；正常点、缺失点、低质量点、基线资格不合格点或方向反转都会中断
  候选序列。因此单点尖峰和未经核实的监测点都不会重置基线。
- `baseline_reset_candidate_max_gap_seconds` 默认为 `null`，保持既有调用兼容。
  配置后，相邻候选异常的事件时间间隔一旦超过上限，旧候选立即作废；相隔数月
  的稀疏异常不能仅因数据库行相邻而被视为“连续”。

统计基线适配仍采用严格过去时处理：前几个候选点先按旧基线告警，只有达到确认
门槛的当前时点才执行适配，不回写先前结论，也不读取后续点。确认片段形成一个连续
异常事件；其后的点从候选片段建立的新基线继续学习，不会因“异常永久排除”而
无限告警。输出中的 `regime_change` 信号、`baseline_resets`、
`baseline_epoch`、`baseline_sample_count_after_update` 和
`baseline_reset_confirmed` 共同记录旧基线、新基线种子、方向、起止时刻及重置
后的样本数量，供审计复算。确认点仍保持
`accepted_into_baseline=false`，表示它没有作为“正常样本”进入旧基线；
`reset_seed_sample_count` 另行记录有多少候选异常被用于新统计基线，来源健康汇总
也分别给出普通基线准入数、基线不合格数和 reset seed 数，避免把两种含义混算。
适配只表示未核实的统计水平发生持续变化，不等同于确认复产、检修、造假或其他
业务原因，仍需结合工况标签和独立凭证解释。

MineGuard 当前受治理在线策略版本 `2.3.0` 采用更保守的上线配置：

- `baseline_reset_confirmation_points=null`，正式在线监测禁止未核实异常点自动
  晋升新基线；通用算法库仍保留显式 opt-in 能力，仅用于未核实统计适配试算；
- `minimum_relative_scale=0`，不再把接近 0 的残差序列宣传成已获得 2% 相对
  地板保护；当前只真实使用通用绝对下限 `minimum_scale=1e-6`；
- `episode_max_gap_seconds=172800`（2 天），即使异常记录在数据库中相邻，跨月
  或长时间断档也不会合并成同一告警片段；
- 候选适配的最大间隔同样配置为 2 天。当前正式策略虽关闭适配，仍把该治理参数
  固化进模型快照，防止以后启用时遗漏时间连续性约束。

正式 `refresh_temporal_audit` 还把“监测点”和“正常基线样本”分离：所有完整、
可解析的点仍可作为待检测点；只有其当前 run reference label 为
`verified_normal`，且 `reference_eligible=true`（标签链、运行哈希、批次完整性和
生命周期均有效）时，`baseline_eligible` 才为真并允许进入滚动基线。仅有
`governance_complete` 但未经人工复核的历史不会自证正常；如果没有足够的已核实
正常历史，结果保持 `insufficient_history`，不能显示为“正常”。

由于当前特征同时包含无量纲标准化残差、求解目标值和吨位差，一个全局绝对下限
无法对所有量纲都给出同等保护。安全的后续方案是建立经版本管理的 feature scale
registry：按 `feature_code + source_key + 单位/分辨率 + 工况` 配置绝对地板，并
要求每次变更有样本回放、误报率评估和审批记录。在该注册表完成前，版本 `2.3.0`
不声称 `minimum_scale=1e-6` 已解决零中心残差的全部灵敏度问题。直接算法 API
未提交增强参数时仍保持兼容默认语义；模型快照、阈值接口和检测记录保存实际配置。

命令行可用 `mineguard temporal` 直接复现。管理员可调用
`POST /v1/analyze/temporal`；领导端通过
`GET /v1/dashboard/temporal?days=90` 按账号矿区数据域读取历史特征，并显示
异常片段、贡献来源、冷启动和来源健康。GET 只计算展示，不修改案件，也不把
预警自动定案。

## 11. 风险排序

领导总览风险分为 0—100。报送异常先按应报次数归一，再按 14 天半衰期降低较旧
记录的权重；重复生产冲突、未闭环 P1/P2、待审批和超过 30 天积压分别计分并设
上限。输出 `risk_score_breakdown` 可逐项解释分数，缺报始终是风险信号，不能因
时间衰减被标成 `normal`。计算只使用统计截止时刻以前的数据。

## 12. HTTP 接口

```text
POST /v1/analyze/aggregation   管理员计量聚合直调
POST /v1/analyze/flow          管理员时间展开物料流直调
POST /v1/analyze/temporal      管理员时序检测直调
GET  /v1/dashboard/temporal    登录用户按矿区权限查看时序结果
GET  /v1/analysis-runs/{run_id}/reference-labels
POST /v1/analysis-runs/{run_id}/reference-labels
GET  /v1/admin/legitimate-scenarios
POST /v1/admin/legitimate-scenarios
```

前三个直调接口要求登录、CSRF 和管理员权限，适用于验证配置与复现；正式五量
数据仍应通过 `/v1/ingest/production*` 可信接入。直调和对应 CLI 命令属于算法
沙箱试算，不自动生成正式案件、办理事件或证据包；除非另行完成来源治理、版本审批、
持久化和闭环接入，不得把直调输出表述为已完成全证据闭环。

历史参考标签权限如下：

- GET 要求 `analysis.read`，并校验当前账号的矿区范围；
- POST 要求 `case.approve`，当前为管理员或该矿区的 `supervisor`，并要求 CSRF；
- `reviewer` 和 `viewer` 可以在授权矿区查看，但不能提交标签；
- 批次 request/response/context 任一哈希校验失败时，读取或追加标签返回
  `batch_integrity_error`；
- 接收该可信数据的账号不能再为同一运行提交 `verified_normal` 或
  `legitimate_exception`；同一账号把自己先前提交的错误/异常/违法标签改成上述
  两类高影响标签时，也需要另一名审批人；
- POST 的 `expected_sequence` 必须等于 GET 返回的当前序号；并发冲突返回
  HTTP 409，应重新读取后人工确认，不能盲目重试覆盖。

读取当前标签和追加“人工核验正常”标签：

```bash
curl -fsS -b "$COOKIE_JAR" \
  "$BASE_URL/v1/analysis-runs/$RUN_ID/reference-labels"

curl -fsS -b "$COOKIE_JAR" \
  -H "X-CSRF-Token: $CSRF_TOKEN" \
  -H 'Content-Type: application/json' \
  --data-binary '{
    "label": "verified_normal",
    "expected_sequence": 0,
    "note": "已核对原始台账、设备日志、班报和对应业务凭证。"
  }' \
  "$BASE_URL/v1/analysis-runs/$RUN_ID/reference-labels"
```

若当前标签序号已经是 3，下一次 POST 的 `expected_sequence` 就应填 3。标记
`legitimate_exception` 时必须另带 `scenario_id`；服务端会验证最新生效场景确实
匹配该运行的矿井、工况和特征边界，并把实际版本保存为 `scenario_id@version`。
该标签只登记版本化解释，GET 返回的 `baseline_eligible_labels` 仍只有
`verified_normal`：

```json
{
  "label": "legitimate_exception",
  "expected_sequence": 0,
  "scenario_id": "planned-maintenance",
  "note": "已核对批准工单、检修记录和恢复生产时间。"
}
```

合法情景的 GET/POST 均要求 `config.manage`，当前仅管理员可用；POST 同样要求
CSRF。登记示例：

```bash
curl -fsS -b "$ADMIN_COOKIE_JAR" \
  -H "X-CSRF-Token: $ADMIN_CSRF" \
  -H 'Content-Type: application/json' \
  --data-binary '{
    "scenario": {
      "scenario_id": "planned-maintenance",
      "version": 1,
      "name": "经批准的主运检修窗口",
      "description": "只解释工单覆盖时段内的历史罕见性，不覆盖物理冲突。",
      "mine_ids": ["M001"],
      "regime": "maintenance",
      "shift": null,
      "season": null,
      "maintenance": true,
      "required_event_codes": ["WORK-ORDER-APPROVED"],
      "required_tags": ["belt-replacement"],
      "feature_bounds": {
        "raw_anomaly": {"lower": 0.0, "upper": 100.0}
      },
      "active": true
    }
  }' \
  "$BASE_URL/v1/admin/legitimate-scenarios"
```

查看当前各场景的最新版本：

```bash
curl -fsS -b "$ADMIN_COOKIE_JAR" \
  "$BASE_URL/v1/admin/legitimate-scenarios"
```

不要对已经登记的 `scenario_id + version` 修改内容；相同内容重试是幂等的，不同
内容返回 HTTP 409。修订或停用必须提交更高版本，旧版本不会删除。

## 13. 已知边界与使用纪律

- 单个请求只有一种物料和一种单位，不支持煤种、水分或热值之间的联合换算。
- 当前 `process` 节点只做同单位物料守恒，不表达洗耗产率、多产品拆分或品质转换。
- 损耗和时延范围由调用方提供，模型不会证明这些参数真实。
- 时延是整数窗口；模型不自动处理窗口内部的小时级到达分布。
- 首窗口之前已经在途的物料没有自动期初在途状态。需要扩展起始缓冲窗口或显式建模。
- 超出最后一个窗口的到达会标为 `arrival_window_id=null`；解释期末结果时应保留足够的尾部窗口。
- 观测可靠度和质量分是治理参数，不是由本模型自动学习的概率。
- 条件历史联合 p 值是同一参考集拟合并排名得到的上尾最大稳健距离经验启发式，
  不是严格有限样本 conformal 保证，不代表违法概率，也不能证明因果关系。
- 历史标签可能受漏查、选择性核验和人员判断偏差影响；即使正常基线只接受
  `verified_normal` 也不能消除偏差，必须定期抽样复核标签分布和工况覆盖。
- 合法情景匹配是规则匹配，不证明工单真实、审批有效或现场确实按工单执行；这些
  原始材料仍需人工调阅。
- `approved_event_codes` 只是请求上下文快照，不是独立签名事件凭证；场景解释
  不能依赖它替代原始工单核验。
- 历史、时序和合法情景均不能覆盖物理冲突、数据质量阻断或求解器失败。
- 单窗口模型可按 `dependency_domains` 去重共享依赖；时间展开 flow 直调结果
  本身不提升单窗口证据等级，接入前仍须保持同一来源键和血缘映射。
- 结果是确定性的点协调和最小修复，不是置信区间、因果推断或违法概率。
- 极大的量级差异会影响数值条件；一个请求应统一单位并采用合理尺度。

所有输出仅用于技术筛查、数据质量治理和人工核查排序。任何行政执法、责任认定或处罚决定都必须由有权限的人员依据原始凭证、现场证据、法定程序和人工复核另行作出。

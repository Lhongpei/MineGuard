# MineGuard 可信数据接入说明

> **历史版（Legacy）**：本文描述 `/v1/ingest/*` 来源注册和旧分析管线，不是当前
> Agent ↔ Platform 五量交换合同。当前人工导入与直采均由一矿一 Agent 规范化报送，
> 且算法不按采集方式赋权；接口以
> [V2 交换规范](../../contracts/specs/five-quantity-exchange-v2.md) 为准。

## 1. 目标与信任边界

可信接入的目标不是让调用方提交一份“已经打好分”的分析请求，而是让调用方只提交
原始观测信封。以下字段由服务端配置决定，数据生产方不能在观测中覆盖：

- `mine_id` 与 `metric_code` 的来源映射；
- 单位、绝对/相对容差、设备分辨率、可靠性、根来源组和共享依赖域；
- 计量语义、采样周期、覆盖率、边界陈旧阈值和累计表复位规则；
- 来源生效期、停用状态、最大延迟和校准有效期；
- 分析参数、质量门槛和必需指标。

服务端从已审批配置和来源注册表构造内部分析请求，同时记录配置快照哈希、原始信封、
输入哈希、结果哈希和代码版本。

当前观测认证方式是 HMAC-SHA256。共享密钥意味着发送方和验证方都能生成相同
HMAC，所以它不是公钥数字签名、自然人签名、不可否认签名或可信时间戳。生产接入
应把来源密钥放入设备安全区/KMS/HSM，并通过 TLS 传输；本仓库示例密钥只能用于
隔离演示。

## 2. 接口与权限

| 接口 | 用途 | 权限 |
|---|---|---|
| `POST /v1/auth/login` | 登录并取得 Cookie、CSRF | 无需登录 |
| `GET /v1/auth/csrf` | 在当前会话中取得新 CSRF | 已登录 |
| `GET/POST /v1/governance/profiles` | 查询/注册分析配置 | `admin` |
| `GET/POST /v1/governance/sources` | 查询/注册来源 | `admin` |
| `POST /v1/ingest/production` | 单矿可信接入 | `admin` 或范围内 `supervisor` |
| `POST /v1/ingest/production/batch` | 辖区可信批次、明确缺报 | `admin` 或覆盖全部应报矿的 `supervisor` |
| `POST /v1/ingest/production/jobs` | 多窗口可信异步接入 | `admin` 或覆盖各窗口的 `supervisor` |

所有 POST（登录除外）必须同时带会话 Cookie 和 `X-CSRF-Token`。管理员可跨矿区；
非管理员必须拥有请求中每一个矿区的 `mine_scopes`。

## 3. 数据契约

### 3.1 来源

一个来源版本包含：

```json
{
  "definition": {
    "source_id": "m001-main-transport",
    "mine_id": "M001",
    "metric_code": "coal.main_transport_t",
    "root_source_group": "m001-main-belt-system",
    "unit": "t",
    "physical_node_id": null,
    "physical_edge_id": "main-belt-01",
    "material_type": "raw_coal",
    "tolerance_abs": 12.0,
    "tolerance_rel": 0.002,
    "resolution": 0.1,
    "reliability": 0.95,
    "dependency_domains": ["operations-historian"],
    "measurement_type": "window_total",
    "expected_interval_seconds": null,
    "min_coverage": 0.9,
    "max_boundary_staleness_seconds": 0.0,
    "register_modulus": null,
    "rate_time_unit_seconds": 3600.0,
    "max_delay_seconds": 60.0,
    "device_health_score": null,
    "clock_quality_score": null,
    "calibration_valid_until": "2026-12-31T23:59:59Z",
    "active": true
  },
  "version": 1,
  "effective_from": "2026-01-01T00:00:00Z",
  "effective_to": "2027-01-01T00:00:00Z",
  "hmac_secret": "仅演示使用的共享密钥请替换为安全随机长密钥"
}
```

同一 `source_id + version` 是不可变键；原样重试是幂等的，不同内容会冲突。当前
本机密钥库也不允许给同一 `source_id` 替换密钥。轮换密钥时应注册新的
`source_id`，给旧来源设置结束时间，并保留旧密钥用于历史验证。

`root_source_group` 表示同一逻辑来源；`dependency_domains` 表示不同来源组仍
共享的 PLC、历史库、接口、人工台账或复制链路。共享域的来源会按一个连通证据簇
计数，不能伪装成多份独立证据。动态容差为
`tolerance_abs + |value| × tolerance_rel + resolution / 2`，各项必须来自计量
规程、检定证书或批准规则，不能为了让结果“一致”而临时放宽。

`physical_node_id` 与 `physical_edge_id` 是可选物理映射且二者互斥：库存/料仓
类来源通常映射节点，皮带秤或运输计量通常映射边；`material_type` 记录物料口径。
这些字段进入注册表快照和审计，但当前正式五量入口不会据此自动生成时间展开
Flow 请求，技术人员仍须审批物理图。`rate_time_unit_seconds` 决定瞬时流率的
换算单位，例如“吨/小时”填 3600。

`device_health_score` 和 `clock_quality_score` 只有在设备自检、检定或时钟同步
状态有可追溯依据时才填写。留空会明确标记为“未验证”，质量状态最高为
`degraded`：不会阻断普通技术协调，但会阻止结果取得 A 级证据等级；即使技术
状态为 `consistent`，也会进入 `DATA` 队列补证和抽查，不能显示为“无需建账”。

`measurement_type` 可取：

- `window_total`：一个分析窗口一个总量；
- `interval_delta`：多个不重叠区间增量求和；
- `cumulative_register`：期初/期末及中间累计表底作差；
- `snapshot`：期末时点值减期初时点值；
- `instantaneous_rate`：按相邻时点梯形积分。

覆盖率不足、区间重叠、边界缺失或累计表无标记回退都会阻断分析，缺失绝不按零
处理。累计表换表/清零必须在对应观测上设置 `reset_before: true`；有固定表盘上限
时在来源配置 `register_modulus`。

### 3.2 分析配置

配置键是 `profile_id + version`，注册后不可原地修改。变更参数必须创建新版本，
明确有效期并重新审批。只有 `approved: true` 且覆盖整个分析窗口的版本可以执行。

当前生产模型支持五个指标：

```text
coal.reported_output_t
coal.main_transport_t
wash.feed_t
sales.raw_shipped_t
inventory.raw_change_t
```

库存变化可为负数，其余流量不能为负数。

### 3.3 运行工况上下文

正式请求可在窗口级提交 `operational_context`，用于条件历史基线和合法情景匹配：

```json
{
  "operational_context": {
    "regime_code": "longwall",
    "shift_code": "daily",
    "season_code": "summer",
    "maintenance": false,
    "approved_event_codes": [],
    "tags": ["raw-coal"]
  }
}
```

- `regime_code`、`shift_code`、`season_code` 应来自部署单位批准的受控字典；
- `maintenance` 必须显式填写 `true` 或 `false`，表示是否处于已确认检修工况；
- `approved_event_codes` 只应放可追溯的已审批事件或工单代码；
- `tags` 用于煤种、工艺线等受控分类，不应放个人信息或自由文本说明；
- 事件代码和标签不得重复；服务端会排序后保存；
- 若三个代码任一为空，或 `maintenance` 未填写，则本次可信接入仍可执行物理
  分析，但条件历史和合法情景返回
  `not_evaluated / operational_context_required`。

四个核心字段完整后，条件历史基线要求全部上下文字段精确相同，不会在样本不足时
自动跨班次、季节或工况借样本。该上下文进入请求哈希和分析上下文，但不是单条设备
观测 HMAC 的一部分。当前平台也没有独立的事件登记、事件来源签名或工单系统验签，
所以 `approved_event_codes` 只是受治理请求快照，不能单独证明事件或审批真实。
接入方应从排班、工单或生产系统取得依据并保留审计，不能为迎合历史范围事后改写。
运行工况只参与历史分组、场景匹配和辅助解释，不进入物理 L1/MCS、容差或证据等级，
因此物理结论不受它影响。
字段、统计方法、标签和安全边界见
[算法 V2.1 说明](算法V2.1说明.md#45-operationalcontext-运行工况)。

### 3.4 签名观测

```json
{
  "source_id": "m001-main-transport",
  "observation_id": "m001-main-transport-20260720-r0",
  "value": 1000.0,
  "unit": "t",
  "observed_at": "2026-07-20T00:02:00Z",
  "received_at": "2026-07-20T00:02:05Z",
  "interval_start": null,
  "interval_end": null,
  "reset_before": false,
  "sequence_no": 202607200001,
  "revision": 0,
  "payload_sha256": "64位小写十六进制",
  "signature": "HMAC-SHA256十六进制"
}
```

约束：

- 时间必须有 UTC 偏移；窗口边界规则随 `measurement_type` 变化；
- `interval_delta` 必须同时提交 `interval_start` 和 `interval_end`，且
  `observed_at` 必须落在该签名区间内；
- 累计表和快照必须精确落在期初/期末边界；瞬时流率才允许在来源配置的陈旧
  阈值内用边界外读数插值并严格裁剪到窗口；
- `received_at` 不得早于 `observed_at`；
- 同一来源用单调、不可复用的 `sequence_no` 标识逻辑记录；
- 初始 `revision` 为 0；修订必须依次为 1、2……，不能跳号；
- 同一来源和序号的全部修订必须保持 `observation_id`、`observed_at` 与计量
  区间不变，只能修正值、接收时间或其他非身份字段；
- 同一 `source_id + sequence_no + revision` 的完全相同信封可幂等重试；
- 同一键对应不同内容会被拒绝；
- 同一请求不能重复放入相同的来源、序号和修订号；
- 修订值、时间或任何载荷字段后，必须重新计算哈希和 HMAC。

## 4. 签名算法

规范化 JSON 使用 UTF-8、键名升序、无多余空格，非 ASCII 字符不转义。业务载荷
包含 `source_id`、`observation_id`、`value`、`unit`、`observed_at`、
`received_at`、`sequence_no`、`revision`，以及非默认的 `interval_start`、
`interval_end`、`reset_before`。为兼容 V1 信封，三个新字段保持默认值时不写入
规范化载荷；一旦提交非默认值，就必须纳入哈希和 HMAC。

计算步骤：

```text
payload_json   = canonical_json(payload)
payload_sha256 = hex(SHA256(UTF8(payload_json)))
envelope       = {"payload": payload, "payload_sha256": payload_sha256}
material       = b"MINEGUARD-GOVERNED-OBSERVATION-V1\x00"
                 + UTF8(canonical_json(envelope))
signature      = hex(HMAC-SHA256(source_secret, material))
```

不同语言对浮点数和时间的 JSON 表达可能不同。设备接入前必须用固定测试向量比对，
不能把普通的 `json.dumps` 默认输出当作必然兼容。下面可执行示例直接调用当前版本
的参考实现。

## 5. 从零执行演示

以下命令假定：

- 已按 README 启动 `http://127.0.0.1:8080`；
- 当前目录是仓库根目录；
- `mineguard` 已安装，或命令中设置了 `PYTHONPATH=src`；
- 使用全新状态目录；
- Bash、curl 和 Python 3 可用。

### 5.1 管理员登录并取得 CSRF

```bash
export BASE_URL='http://127.0.0.1:8080'
export MINEGUARD_ADMIN_PASSWORD='change-this-local-password'
export ADMIN_COOKIE_JAR='/tmp/mineguard-admin.cookies'

rm -f "$ADMIN_COOKIE_JAR"
LOGIN_BODY="$(
  python3 -c 'import json,os; print(json.dumps({
    "username": "admin",
    "password": os.environ["MINEGUARD_ADMIN_PASSWORD"]
  }))'
)"
LOGIN_JSON="$(
  curl -fsS -c "$ADMIN_COOKIE_JAR" \
    -H 'Content-Type: application/json' \
    --data-binary "$LOGIN_BODY" \
    "$BASE_URL/v1/auth/login"
)"
ADMIN_CSRF="$(
  printf '%s' "$LOGIN_JSON" |
    python3 -c 'import json,sys; print(json.load(sys.stdin)["csrf_token"])'
)"
chmod 0600 "$ADMIN_COOKIE_JAR"
unset MINEGUARD_ADMIN_PASSWORD LOGIN_BODY
```

检查当前身份：

```bash
curl -fsS -b "$ADMIN_COOKIE_JAR" "$BASE_URL/v1/auth/me"
```

如果会话仍有效但需要新 CSRF：

```bash
CSRF_JSON="$(
  curl -fsS -b "$ADMIN_COOKIE_JAR" "$BASE_URL/v1/auth/csrf"
)"
ADMIN_CSRF="$(
  printf '%s' "$CSRF_JSON" |
    python3 -c 'import json,sys; print(json.load(sys.stdin)["csrf_token"])'
)"
```

### 5.5 生成五个签名观测

以下程序读取演示来源密钥，并生成
`/tmp/mineguard-governed-M001.json`：

```bash
PYTHONPATH=src python3 - <<'PY'
import json
from datetime import UTC, datetime, timedelta
from pathlib import Path

from mineguard.governance import GovernedObservation

root = Path("examples/governance")
registrations = {}
for path in sorted(root.glob("source-*.json")):
    registration = json.loads(path.read_text(encoding="utf-8"))
    registrations[registration["definition"]["source_id"]] = registration

values = [
    ("m001-production-report", 1000.0),
    ("m001-main-transport", 1000.0),
    ("m001-wash-feed", 800.0),
    ("m001-raw-sales", 100.0),
    ("m001-raw-stock-change", 100.0),
]
window_start = datetime(2026, 7, 20, tzinfo=UTC)
observations = []
for index, (source_id, value) in enumerate(values, start=1):
    registration = registrations[source_id]
    observed_at = window_start + timedelta(minutes=index)
    observation = GovernedObservation.signed(
        secret=registration["hmac_secret"],
        source_id=source_id,
        observation_id=f"{source_id}-20260720-r0",
        value=value,
        unit=registration["definition"]["unit"],
        observed_at=observed_at,
        received_at=observed_at + timedelta(seconds=5),
        sequence_no=202607200000 + index,
        revision=0,
    )
    observations.append(observation.model_dump(mode="json"))

request = {
    "mine_id": "M001",
    "window_start": window_start.isoformat(),
    "window_end": (window_start + timedelta(days=1)).isoformat(),
    "profile_id": "trusted-five-flow",
    "profile_version": "2026.1",
    "operational_context": {
        "regime_code": "longwall",
        "shift_code": "daily",
        "season_code": "summer",
        "maintenance": False,
        "approved_event_codes": [],
        "tags": ["raw-coal"],
    },
    "observations": observations,
}
Path("/tmp/mineguard-governed-M001.json").write_text(
    json.dumps(request, ensure_ascii=False, indent=2),
    encoding="utf-8",
)
print("/tmp/mineguard-governed-M001.json")
PY
```

可以先确认每条观测只有原始信封字段，没有 `tolerance_abs`、`reliability`、
`root_source_group`、`quality` 或 `parameters`：

```bash
python3 -m json.tool /tmp/mineguard-governed-M001.json
```

### 5.6 单矿可信接入

```bash
curl -fsS -b "$SUPERVISOR_COOKIE_JAR" \
  -H "X-CSRF-Token: $SUPERVISOR_CSRF" \
  -H 'Content-Type: application/json' \
  --data-binary @/tmp/mineguard-governed-M001.json \
  "$BASE_URL/v1/ingest/production" \
  > /tmp/mineguard-single-result.json

python3 -m json.tool /tmp/mineguard-single-result.json
```

首次成功返回 HTTP 201 和 `created: true`。完全相同的请求再次提交返回 HTTP 200
和 `created: false`。响应的 `governance` 应包含：

- `profile_id`、`profile_version`；
- `registry_snapshot_hash`；
- `accepted_count`、`rejected_count`；
- `quality_issues`；
- 规范化后的 `operational_context`；
- 接收时的原始 `observation_envelopes`。

持久化时，服务分别规范化并记录批次 request、response 和分析 context 的 SHA-256；
读取、幂等重试、分析运行及领导视图会校验三部分，任一不一致都不能作为可信历史
参考。当前版本新建批次标记 `integrity_origin=created`，表示三份摘要随批次创建。
升级旧库时补算摘要的批次标记 `integrity_origin=legacy_backfill`：它们仍可按权限
展示和追溯，但由于摘要不是原始创建时形成，即使当前哈希相符也不进入正常历史基线。

```bash

)
portfolio = {
```

### 5.8 提交可信异步任务

多个单矿窗口可以进入持久化队列。每个窗口仍提交完整的可信请求，后台会重新执行
来源、配置、时间、序号、修订、载荷哈希和 HMAC 校验：

```bash
python3 - <<'PY'
import json
from pathlib import Path

single = json.loads(
    Path("/tmp/mineguard-governed-M001.json").read_text(encoding="utf-8")
)
job = {
    "idempotency_key": "trusted-job-20260720-r1",
    "windows": [
        {
            "window_id": "M001-20260720",
            "request": single,
        }
    ],
}
Path("/tmp/mineguard-governed-job.json").write_text(
    json.dumps(job, ensure_ascii=False, indent=2),
    encoding="utf-8",
)
PY

curl -fsS -b "$SUPERVISOR_COOKIE_JAR" \
  -H "X-CSRF-Token: $SUPERVISOR_CSRF" \
  -H 'Content-Type: application/json' \
  --data-binary @/tmp/mineguard-governed-job.json \
  "$BASE_URL/v1/ingest/production/jobs" \
  > /tmp/mineguard-job-result.json

JOB_ID="$(
  python3 -c 'import json; print(json.load(open(
    "/tmp/mineguard-job-result.json", encoding="utf-8"
  ))["job"]["job_id"])'
)"
curl -fsS -b "$SUPERVISOR_COOKIE_JAR" \
  "$BASE_URL/v1/analysis-jobs/$JOB_ID"
```

任务状态依次为 `queued`、`running`，最终为 `succeeded`、`partial_failed`、
`failed` 或 `cancelled`。每个窗口保留独立状态、结果哈希和公开错误摘要。相同
`idempotency_key` 配相同输入返回已有任务，配不同输入会冲突。

当前通用重放接口只允许管理员。监管负责人需要再次运行可信窗口时，应更换
`idempotency_key` 重新提交 `/v1/ingest/production/jobs`。

## 6. 质量判定与常见拒绝

| 代码 | 含义 | 正确处理 |
|---|---|---|
| `unknown_source` | 来源未登记或当时未生效 | 核对来源版本和有效期 |
| `source_mine_mismatch` | 来源矿井与请求矿井不同 | 修复路由或主数据 |
| `metric_mismatch` | 来源指标不在配置必需指标中 | 用正确配置，不改观测伪装指标 |
| `unit_mismatch` | 观测单位与注册单位不同 | 在设备侧按批准规则换算并重签 |
| `source_inactive` | 来源已停用 | 停止使用，启用须走配置审批 |
| `calibration_expired` | 观测时设备校准已过期 | 完成校准并注册后续有效版本 |
| `payload_hash_mismatch` | 载荷被改或规范化算法不同 | 对照参考测试向量 |
| `signature_invalid` | HMAC 不匹配 | 核对来源密钥和签名材料 |
| `outside_analysis_window` | 观测不在窗口内 | 修复窗口或事件时间 |
| `received_before_observed` | 接收时间早于观测时间 | 校时并调查时间链路 |
| `late_observation` | 超过最大接收延迟 | 警告；调查链路，服务端降低及时性 |
| `revision_gap` | 修订缺少直接前序 | 先提交并保留前一修订 |
| `sequence_revision_conflict` | 同一键出现不同载荷 | 停止重试，调查序号复用或篡改 |
| `superseded_revision` | 已有更高修订 | 保留追溯，分析采用较高修订 |
| `aggregation_insufficient_coverage` | 计量时段覆盖不足 | 补齐原始点/区间，不能补零 |
| `aggregation_overlapping_intervals` | 区间增量重叠 | 修复切片或去重，避免重复计量 |
| `aggregation_boundary_points_missing` | 表底/快照/流率缺边界 | 补期初期末可信读数 |
| `aggregation_unexpected_register_decrease` | 累计表无标记回退 | 核实换表/清零并提交显式复位标记 |

阻断问题返回 HTTP 422 `governance_rejected`，不应通过降低质量门槛、放宽容差或改
服务端时间来“修复”。配置问题返回 `governance_configuration_rejected`；不可变
键内容冲突返回 HTTP 409。

## 7. 生产接入清单

每个来源上线前至少确认：

- 来源所有者、矿井、指标、单位、根来源和共享依赖域已经业务审批；
- 计量类型、采样频率、覆盖率、边界和累计表复位规则已确认；
- 容差有计量/校准依据，可靠性有评估方法；
- 设备时钟同步，`observed_at` 和 `received_at` 来源明确；
- 序号断电不回退，修订规则可追溯；
- 密钥不写在代码、普通配置、日志或观测 JSON 中；
- 设备和服务端密钥通过独立安全通道装载；
- TLS、网络白名单、限流和重放监控已配置；
- 密钥轮换、吊销、设备更换和历史验证方案已演练；
- 应报矿井名单来自被授权的主数据，且能区分缺报与零值；
- 运行工况、班次和季节代码非空，检修标志显式填写；审批事件和标签来自受控
  主数据并可追溯；
- 明确 `approved_event_codes` 当前不是独立签名事件凭证，场景解释仍需核对原始
  工单、审批和执行记录；
- 每个需要历史判断的精确工况至少积累 20 个合格 `verified_normal` 样本；不足时
  接受 `insufficient_history`，不得跨工况凑数、批量补贴正常标签或把
  `legitimate_exception` 混入正常基线；
- 核对批次 request/response/context 三个哈希和 `integrity_origin`；迁移回填批次
  只用于展示追溯；
- 原始设备日志、校准记录和业务凭证可按案件授权调阅；
- 明确 HMAC 只是内网完整性认证，正式证据另接公钥签名、可信时间戳和 WORM。

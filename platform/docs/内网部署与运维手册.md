# MineGuard 内网部署与运维手册

## 1. 适用范围

本手册面向部署人员、系统管理员、数据接入人员和监管领导。当前交付适合单机或
受控内网的“影子运行”：真实业务照常进行，MineGuard 并行形成技术线索，人工调阅
原始资料后再决定是否进入正式业务流程。

本版本不是互联网 SaaS、集群平台或执法认定系统。未完成本手册第 14 节的外部
条件前，不应移除页面和导出物中的“技术线索/影子运行”标识。

## 2. 运行结构与数据边界

推荐拓扑：

```text
内网浏览器/数据交换程序
          |
      HTTPS 443
          |
  反向代理与访问控制
          |
  127.0.0.1:8080
          |
  MineGuard 单进程
   |-- HTTP 请求线程
   |-- 1 个异步分析线程
   `-- 6 个 SQLite 库 + 证据 ZIP 文件缓存
```

内置 HTTP 服务应只监听回环地址。TLS、域名、客户端网络准入、限流和代理访问日志
由反向代理或内网网关负责。

统一状态目录内容如下：

| 路径 | 内容 | 六库备份 |
|---|---|---|
| `mineguard.db` | 批次、分析快照、核查事项、办理事件；算法特征、检测发现、模型快照、告警片段 | 是 |
| `auth.db` | 用户、密码摘要、会话摘要、权限审计 | 是 |
| `jobs.db` | 异步任务与窗口结果 | 是 |
| `evidence.db` | 证据包清单、文件元数据和完整 ZIP BLOB | 是 |
| `governance.db` | 来源与分析配置版本、可信观测记录 | 是 |
| `source-keys/source-keys.db` | 来源 HMAC 密钥和证据 HMAC 密钥 | 是，高敏感 |
| `source-keys/*.key` | 来源密钥的本机文件副本 | 否，数据库中有恢复副本 |
| `evidence/*.zip` | 由 `evidence.db` BLOB 生成的本机文件缓存 | 不需要另行备份 |
| `backups/<id>/` | 六库备份、清单和清单 HMAC | 不适用 |
| `backup.key` | 默认备份 HMAC 密钥 | 否，必须离线另存 |

`mineguard.db` 中对应的算法审计表为 `analysis_feature_windows`、
`detector_findings`、`algorithm_model_snapshots` 和 `alert_episodes`。服务启动时
会创建缺失表并执行兼容迁移；旧版特征行继续保留，当前特征提取版本按已有分析快照
回填。首次升级启动可能因此比日常重启更久，切流前必须等待 `/ready` 通过并核对
历史批次、算法特征和时序页面仍可正常读取。

新生成证据包的完整 ZIP 同时写入 `evidence.db`；文件缓存丢失后，服务读取证据时
会先校验数据库 BLOB 哈希再重建缓存。因此六库备份已经覆盖证据包本体。由旧版升级
且在 BLOB 字段加入前生成的历史行不会自动回填；当前版本也没有历史 BLOB 迁移
命令。此类实例必须继续单独备份旧证据目录，或另行实施经审批、经校验的一次性迁移
工具后再取消目录备份。

六库备份不加密，只做 SQLite 完整性、文件哈希和清单 HMAC 校验。由于
`evidence.db` 可能含敏感原始材料且体积增长较快，备份介质仍需由磁盘加密、权限
控制或专用备份系统保护。

## 3. 容量与前置条件

- Linux 内网主机，Python 3.11 或更高版本；
- 独立低权限系统账号；
- 仅代理能访问的后端端口；
- 独立的状态盘和备份介质；
- 准确的 NTP/时钟同步；
- 试点规模下预留至少 2 倍状态目录容量用于备份和恢复演练；
- 依赖：NumPy、SciPy、Pydantic 2、PyYAML。

SQLite 和单异步线程适合中小规模串行分析。任务最多接收 5,000 个窗口，但这只是
输入上限，不是推荐单批规模。正式试点应从几十个窗口开始，记录耗时和数据库增长，
再制定本单位批次上限。

## 4. 本机首次启动

从仓库根目录安装：

```bash
python3 -m venv .venv
. .venv/bin/activate
python3 -m pip install -c constraints.txt -e .
mineguard --version
```

`constraints.txt` 是本次验证过的运行依赖约束，不是自动更新清单。变更 Python、
NumPy、SciPy、Pydantic 或 PyYAML 版本时，应先在副本环境更新约束并完成全量回归。
发布归档还应保存
`mineguard.runtime_manifest.build_runtime_manifest()` 的 JSON 输出，便于复现
当时的应用、Python 和数值库版本。

首次一条命令启动：

```bash
MINEGUARD_ADMIN_PASSWORD='change-this-local-password' \
  .venv/bin/mineguard serve \
  --host 127.0.0.1 --port 8080 \
  --state-directory "$PWD/.mineguard"
```

密码至少 8 个字符。上述写法只用于独占本机验证，真实密码可能进入 shell 历史。
更安全的做法是由受限环境文件或秘密注入机制设置
`MINEGUARD_ADMIN_PASSWORD`。不设置变量时，程序生成并在终端一次性显示随机密码。
用户库已有账号时不会再次创建管理员。

本次已初始化的本地验收实例约定使用 `admin` / `123123123` 登录。该口令仅用于当前
受控演示，首次登录后必须立即修改；重新创建状态目录时仍使用环境变量或终端显示的
一次性随机密码，不应把 `123123123` 配置为内网生产口令。

检查：

```bash
curl -fsS http://127.0.0.1:8080/health
curl -fsS http://127.0.0.1:8080/live
curl -fsS http://127.0.0.1:8080/ready
```

`/health` 只表示 HTTP 进程响应，`/live` 表示进程存活，`/ready` 还检查业务库、
用户库、任务库、证据库、治理/密钥库和异步线程。`/ready` 不检查磁盘剩余空间、
TLS、外部原始凭证系统或备份新鲜度，这些必须在外部监控中补充。

## 5. 受控内网服务化

以下目录是示例，部署单位可按标准调整：

```bash
sudo useradd --system --home /var/lib/mineguard \
  --shell /usr/sbin/nologin mineguard
sudo install -d -m 0700 -o mineguard -g mineguard /var/lib/mineguard
sudo install -d -m 0750 -o root -g mineguard /etc/mineguard
sudo install -d -m 0755 -o root -g root /opt/mineguard
```

将代码安装到 `/opt/mineguard` 的虚拟环境。管理员首次密码可暂存在权限为 `0640`
的 `/etc/mineguard/mineguard.env`：

```text
MINEGUARD_ADMIN_PASSWORD=由秘密管理工具注入的首次密码
```

环境文件由 `root:mineguard` 持有。首次成功创建管理员后，应从环境文件删除该项；
删除不会影响已写入 `auth.db` 的密码摘要。

建议把备份认证密钥放在状态目录之外，并另行保存副本：

```bash
sudo sh -c \
  'umask 077; python3 -c "import secrets,sys; sys.stdout.buffer.write(secrets.token_bytes(32))" > /etc/mineguard/backup.key'
sudo chown root:mineguard /etc/mineguard/backup.key
sudo chmod 0640 /etc/mineguard/backup.key
```

仓库已提供可复制的
[systemd 单元](../deploy/mineguard.service.example) 和
[环境文件](../deploy/mineguard.env.example)。其核心内容如下：

```ini
[Unit]
Description=MineGuard intranet shadow service
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=mineguard
Group=mineguard
WorkingDirectory=/opt/mineguard
EnvironmentFile=-/etc/mineguard/mineguard.env
ExecStart=/opt/mineguard/.venv/bin/mineguard serve \
  --host 127.0.0.1 --port 8080 \
  --state-directory /var/lib/mineguard \
  --backup-key-file /etc/mineguard/backup.key \
  --secure-cookie
Restart=on-failure
RestartSec=5
UMask=0077
NoNewPrivileges=true
PrivateTmp=true
ProtectHome=true
ProtectSystem=strict
ReadWritePaths=/var/lib/mineguard
ReadOnlyPaths=/etc/mineguard

[Install]
WantedBy=multi-user.target
```

`--secure-cookie` 只应在浏览器确实通过 HTTPS 访问时启用；直接用 HTTP 访问时，
浏览器不会发送带 `Secure` 标志的会话 Cookie。

## 6. HTTPS 反向代理

仓库中的 [Nginx 示例](../deploy/nginx-mineguard.conf.example) 可作为起点。
下面只表示必要约束，不替代本单位的 Nginx、网关或国密 TLS 标准：

```nginx
server {
    listen 443 ssl;
    server_name mineguard.intranet.example;

    ssl_certificate     /etc/pki/mineguard/fullchain.pem;
    ssl_certificate_key /etc/pki/mineguard/private.key;
    client_max_body_size 10m;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto https;
        proxy_read_timeout 120s;
    }
}
```

防火墙只开放代理的 443，不开放 8080。当前应用不信任也不解析转发客户端 IP，
所以应用审计可能记录为代理地址；真实客户端地址应以受保护的代理访问日志为准，
并与应用审计时间关联。不要把不受信任的 `X-Forwarded-For` 直接当作证据。

## 7. 账号、角色和矿区隔离

默认会话空闲 30 分钟失效、最长 8 小时失效；退出、禁用账号或撤销会话后立即
失效。密码使用带盐 scrypt 摘要，会话令牌只存摘要。所有状态变更除登录外都要求
会话 Cookie 和 `X-CSRF-Token`。

用户可通过 `POST /v1/auth/change-password` 修改自己的密码，管理员可通过
`POST /v1/admin/users/{username}/reset-password` 重置密码；修改或重置后相关
会话失效，需要重新登录。新密码至少 12 个字符。

| 角色 | 主要权限 | 矿区范围 |
|---|---|---|
| `admin` | 用户、配置、全域数据、直接分析、任务、备份 | 全部矿区 |
| `supervisor` | 范围内可信接入、分派、办理、批准/退回、审计 | 必须指定 |
| `reviewer` | 范围内查看、办理、提交结论、生成证据包 | 必须指定 |
| `viewer` | 范围内只读总览、趋势、案件和分析 | 必须指定 |

非管理员账号至少有一个 `mine_scopes`。矿区范围同时用于总览、趋势、批次、案件、
分析结果、任务结果和证据下载，不能用页面隐藏代替服务端授权。

管理员可在页面维护用户，也可调用：

```text
GET  /v1/admin/users
POST /v1/admin/users
POST /v1/admin/users/{username}/status
POST /v1/admin/users/{username}/access
POST /v1/admin/users/{username}/reset-password
```

页面会要求为账号停用、恢复和权限调整填写原因，并将原因写入权限审计。接口调用方也
应分别随 `active` 或 `role`、`mine_scopes` 提交 `reason`，避免形成无法解释的权限
变更记录。

初始配置至少准备两个不同自然人的账号：一个 `reviewer` 提交结论，一个
`supervisor` 审批或退回。不得由同一共享账号完成双人复核。

## 8. 首次业务配置

首次上线按以下顺序：

1. 管理员登录并建立实名映射的个人账号；
2. 为账号分配最小角色和矿区范围；
3. 管理员注册已审批分析配置；
4. 管理员逐一注册来源及其版本、有效期和 HMAC 密钥；
5. 以一个历史窗口验证单矿可信接入；
6. 以完整应报名单验证辖区批量接入和缺报展示；
7. 两个不同账号完成一次结论提交与审批；
8. 生成、下载并验证一次证据包；
9. 完成六库备份、校验和恢复演练；
10. 业务、安全和运维责任人共同签署影子运行清单。

登录、CSRF、配置和签名观测的完整命令见
[可信数据接入说明](可信数据接入说明.md)。

## 9. 监管领导使用口径

领导首页应按以下顺序阅读：

1. 先看应报数、实报数和缺报数，缺报绝不能当作产量为零；
2. 再看重复异常、P1/P2、待审批和超期积压；
3. 点入矿井或案件查看来源、时间、质量问题、算法假设和建议核查动作；
4. 要求办理人员调阅设备日志、原始报表、视频或业务凭证；
5. 只有不同账号完成结论和审批后，案件才关闭；
6. 对外使用材料前下载证据包并核验完整性，同时引用原始业务凭证。

“风险分”用于排序，“证据等级”表示多源技术支撑强弱，
`minimum_reported_gap`/`unreported_output_upper` 是给定模型与容差下的敏感性
结果。三者都不能直接解释为违法金额、少报认定或处罚依据。

趋势接口是 `GET /v1/dashboard/trends?days=30&timezone=Asia/Shanghai`，`days`
允许 1 至 365。统计结果始终按当前账号的矿区范围重新计算。

## 10. 异步任务

任务接口：

```text
POST /v1/ingest/production/jobs
POST /v1/analysis-jobs
GET  /v1/analysis-jobs
GET  /v1/analysis-jobs/{job_id}
POST /v1/analysis-jobs/{job_id}/cancel
POST /v1/analysis-jobs/{job_id}/replay
```

每个任务有调用方唯一的 `idempotency_key`，每个窗口有任务内唯一的
`window_id`。相同幂等键与相同输入返回已有任务；相同键配不同输入会冲突。窗口失败
不会抹去已成功窗口，进程中断时运行中的窗口会在重启后返回队列。

日常真实数据使用 `/v1/ingest/production/jobs`：每个窗口提交
`GovernedProductionRequest`，后台线程执行与同步可信入口相同的来源、配置和 HMAC
校验，范围内 `supervisor` 可以提交。`/v1/analysis-jobs` 的窗口 `payload` 是
调用方自带的原始 `ProductionAnalysisRequest`，因此启用认证时只允许管理员提交。
当前通用 `replay` 也只允许管理员；监管负责人需要重跑可信窗口时，应使用新的
幂等键重新提交可信任务。不要让业务调用方通过原始任务接口自报容差、可靠性或
质量分。

## 11. 核查、双人复核与证据包

典型状态：

```text
pending -> reviewing -> waiting_data -> reviewing
                       \-> pending_approval
pending/reviewing/waiting_data -> pending_approval
pending_approval --另一账号 approve--> closed
pending_approval --另一账号 reject--> reviewing
closed --reopen--> reviewing
```

每次动作都带当前 `expected_version`；别人已更新时返回版本冲突，操作者必须刷新后
重试。启用认证时兼容动作 `close` 被接口禁止，必须先 `submit_conclusion`，再由
不同账号 `approve` 或 `reject`。审批人不能是结论提交人。

证据包接口：

```text
POST /v1/cases/{case_id}/evidence
GET  /v1/evidence/{bundle_id}
GET  /v1/evidence/{bundle_id}/verify
```

证据包固定包含当时案件、事件和分析快照的清单与哈希。对同一案件版本重复生成会
返回已有包。下载和验证继续执行案件矿区授权。

证据包 HMAC 是共享密钥认证：可检测内容变化并确认生成方持有同一密钥，但不能证明
某个自然人签名，也不具备不可否认性、可信时间戳或 WORM 属性。离线验证需要在受控
验证环境中使用包含同一证据 HMAC 密钥的状态目录：

```bash
mineguard verify-evidence /secure/export/bundle_id.zip \
  --state-directory /var/lib/mineguard
```

命令校验 ZIP 结构、清单、各文件哈希和清单 HMAC，成功返回 `status: valid` 和
退出码 0，失败返回 `status: invalid` 和退出码 1。该状态目录的
`source-keys/source-keys.db` 含高敏感密钥，只应让授权验证人员访问；命令不会把
密钥导出给普通用户。正式证据保全仍应接入 KMS/HSM、公钥签名、可信时间戳和对象
锁存储。

## 12. 六库备份、校验与恢复

### 12.1 在线备份

以下命令逐库使用 SQLite 备份 API，并校验每个副本：

```bash
sudo -u mineguard /opt/mineguard/.venv/bin/mineguard backup \
  nightly-20260726 \
  --state-directory /var/lib/mineguard \
  --backup-directory /srv/mineguard-backups \
  --key-file /etc/mineguard/backup.key
```

在线备份保证每个 SQLite 文件各自事务一致，但六个独立库不是同一时刻的分布式
快照。对案件、证据和配置要求严格同一检查点的归档，应先停止写入或短暂停服，再
执行上述 CLI 备份。管理页面/API 发起的在线备份会在单进程内串行化写请求并暂停
后台分析线程，完成六库备份后恢复线程再返回成功；它仍不能协调同一状态目录上的
第二个进程，因此不得让多个 MineGuard 进程共享状态目录。

验证：

```bash
sudo -u mineguard /opt/mineguard/.venv/bin/mineguard verify-backup \
  nightly-20260726 \
  --state-directory /var/lib/mineguard \
  --backup-directory /srv/mineguard-backups \
  --key-file /etc/mineguard/backup.key
```

备份标识不可复用。`backup.key` 不在备份中，丢失后不能验证或恢复该备份。至少在
另一受控介质保存密钥副本，并记录 `key_id`；不要把密钥放入同一备份目录。

新生成证据包的 ZIP BLOB 已随 `evidence.db` 进入六库备份，
`/var/lib/mineguard/evidence/` 只是可重建缓存，不要求另做一致性备份。由旧版升级
且尚未把历史 ZIP 纳入 BLOB 的实例例外：必须继续备份原目录，除非已用另行审批的
迁移工具回填并逐包验证；当前 CLI 不提供历史回填命令。
还应备份反向代理配置、TLS 证书恢复流程和部署版本，但不要把私钥混入普通应用
备份。

### 12.2 恢复到新目录

恢复不会覆盖现有状态目录，目标必须不存在或为空：

```bash
sudo systemctl stop mineguard

sudo -u mineguard /opt/mineguard/.venv/bin/mineguard verify-backup \
  nightly-20260726 \
  --state-directory /var/lib/mineguard \
  --backup-directory /srv/mineguard-backups \
  --key-file /etc/mineguard/backup.key

sudo -u mineguard /opt/mineguard/.venv/bin/mineguard restore-backup \
  nightly-20260726 \
  --state-directory /var/lib/mineguard-restored \
  --backup-directory /srv/mineguard-backups \
  --key-file /etc/mineguard/backup.key
```

修改服务的 `--state-directory` 指向新目录后启动。恢复命令会建立空的证据缓存
目录；首次读取某个证据包时，服务从 `evidence.db` BLOB 校验并重建对应 ZIP。然后
执行：

```bash
curl -fsS https://mineguard.intranet.example/ready
```

随后用测试账号完成登录、矿区隔离、历史案件审计校验、证据包下载，并执行：

```bash
mineguard verify-evidence /secure/export/restored-bundle.zip \
  --state-directory /var/lib/mineguard-restored
```

再完成一笔新可信观测接入。全部通过后再宣布恢复完成，原目录先只读保留到变更
窗口结束。

## 13. 日常巡检、升级与故障处理

每日：

- 检查 `/ready` 为 `ready`；
- 检查代理 5xx、登录限速、权限拒绝和应用异常日志；
- 检查状态盘、证据盘、备份盘空间；
- 检查任务是否长期 `queued/running`、是否有 `partial_failed`；
- 检查缺报、待审批和超期积压；
- 确认最新备份已验证，并抽查证据下载及 `verify-evidence` 通过。

每月或按制度：

- 用新目录完成恢复演练；
- 复核账号、角色、矿区范围和离岗禁用；
- 复核来源有效期、校准有效期、配置审批和密钥轮换计划；
- 抽查案件哈希链、分析输入/结果哈希和证据包 HMAC；
- 校时、更新依赖并完成漏洞扫描。

升级前先停服或冻结写入，记录 `mineguard --version` 和运行时版本清单，并完成可
校验的六库备份；从没有证据 BLOB 的旧版升级时，还要独立归档旧证据目录，直到经
审批的迁移和逐包验收完成。在状态副本上用新代码启动，等待算法审计表迁移和特征
回填完成，再执行 `pytest`、`/ready`、历史案件哈希、证据包及恢复验收。

SQLite 架构在启动时向前迁移，**不支持把旧程序直接指向已经迁移的状态目录来
降级**。需要回退时：

1. 停止新版本并保留失败后的状态目录为只读调查副本；
2. 用升级前已验证的六库备份恢复到另一个全新目录；
3. 让旧版本服务指向该恢复目录，重新执行就绪、登录、矿区隔离、案件和证据验收；
4. 验收通过后再切换流量，禁止把迁移后的单个数据库复制回旧状态目录拼接使用。

因此旧程序、`constraints.txt`、升级前状态归档、备份密钥和回退判断必须作为同一
发布变更包保留。

常见故障：

| 现象 | 先检查 | 处理原则 |
|---|---|---|
| `/ready` 为 `not_ready` | `checks` 中失败项、磁盘、权限、进程日志 | 不接流量，修复后再就绪 |
| 登录 401 | 账号、密码、账号是否禁用、会话是否过期 | 不绕过认证 |
| 写操作 403 `csrf_invalid` | 是否带 Cookie 和最新 CSRF | 重新获取 `/v1/auth/csrf` |
| `permission_denied` | 角色与 `mine_scopes` | 按授权审批调整，不给共享管理员 |
| `governance_rejected` | 来源、单位、时间、序号、修订、哈希/HMAC | 修复数据源，不降低门槛 |
| `version_conflict` | 案件是否被他人更新 | 刷新案件后再决定动作 |
| 任务长期运行 | 单线程、窗口规模、求解日志 | 先取消后拆小任务；保留失败记录 |
| 证据校验失败 | ZIP 是否缺失/变化、密钥是否来自同一恢复点 | 停止使用该包并调查 |
| 备份校验失败 | 清单 HMAC、文件哈希、SQLite 完整性、密钥 | 不执行恢复，换已验证副本 |

## 14. 正式业务前必须外接的能力与授权

以下不是当前代码可以自行完成的部署动作：

- TLS 证书、内网域名、反向代理、网络分区、WAF/限流；
- 组织 SSO/IAM、多因素认证、人员离岗同步和机构/矿井主数据；
- KMS/HSM、设备侧独立密钥、公钥签名、密钥轮换与吊销；
- WORM/对象锁、可信时间戳、异地备份和生产级高可用数据库；
- 原始视频、设备日志、生产报表、销售/库存凭证的只读授权接口；
- 集中监控、磁盘/备份新鲜度告警、代理客户端 IP 审计和安全日志平台；
- 数据分类分级、个人信息最小化、留存/删除期限和跨部门调阅审批；
- 算法配置审批人、来源责任人、案件办理人、复核人、备份人和恢复批准人名单；
- 影子运行、正式业务辅助和执法使用各阶段的业务、安全、保密和法律授权。

外部条件清单未完成时，系统仍可在受控内网进行影子运行，但不得宣称已经具备
法律数字签名、不可篡改证据保全、集群高可用或自动执法能力。

## 15. 数据生命周期与删除策略

领导工作台和管理页面采用“状态变更、保留历史”的处置方式，不把硬删除作为日常
业务动作：

| 对象 | 日常处置 | 恢复与审计 |
|---|---|---|
| 账号 | 管理员停用账号；当前账号不能自行停用，最后一个有效管理员不能停用或降级 | 可恢复账号；停用、改权和重置密码均撤销相关会话并写入权限审计 |
| 案件 | 结论提交人可在待审批阶段说明原因后撤回；双人审批关闭后可归档 | 可恢复已归档案件；撤回、关闭、重开、归档和恢复均保留追加式事件 |
| 异步任务 | 排队或运行任务可取消；终态任务可说明原因后归档 | 可恢复已归档任务；取消、归档和恢复均保留任务结果及操作审计 |
| 分析批次 | 错误批次可说明原因后作废；可集中隔离历史 `pilot-*` 演示批次 | 可恢复已作废批次；默认总览、趋势、案件、特征和校准统计排除已作废批次 |
| 证据包、审计、备份 | 业务前端不提供硬删除 | 按既定留存期保管；到期销毁须走经批准的离线运维流程并记录范围、审批和校验结果 |

相关接口如下；所有写操作仍须满足登录、CSRF、角色和矿区范围校验：

```text
GET  /v1/cases?include_archived=1
POST /v1/cases/{case_id}/actions
GET  /v1/analysis-jobs?include_archived=1
POST /v1/analysis-jobs/{job_id}/cancel
POST /v1/analysis-jobs/{job_id}/archive
GET  /v1/analysis-batches?include_invalidated=true
POST /v1/analysis-batches/{batch_id}/status
POST /v1/admin/analysis-batches/isolate-pilots
```

归档和作废只改变默认查询与统计范围，不抹除原始记录、证据快照或历史链。误操作时
应先核对对象、原因和版本号再恢复，不得直接修改 SQLite 文件绕过审计。

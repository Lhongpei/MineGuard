# 生产运行五量月报分析说明

> **历史版（Legacy）**：本文保留早期单文件/月报算法说明，其中旧 API 和独立算法
> 入口不得用于当前部署。当前求解器、历史和时序分析全部位于唯一政府十量 V3 引擎；
> 准确口径见 [十量 V3 部署与运行](../../docs/十量V3部署与运行.md)。旧五量样表仅
> 可只读展示，不能补造开采、销售、运输、洗煤或开票数据。

## 1. 能力边界

本功能分析的“五量”是：

- 风量；
- 用工量；
- 总用电量；
- 雷管、炸药使用量；
- 产量。

它与 MineGuard 物理主模型中的“产、运、洗、销、存”五流不是同一概念。月报
分析只生成辅助核查事件，不进入加权 L1 物料平衡，不修改物理主结论。

月报中的用电量若没有生产分区电表，也没有完整剔除通风、排水、压风、提升和
洗选等干扰负荷，只能称为“总电量/产量比”，不能称为生产吨煤电耗。

## 2. 分析流程

```text
ET/OLE2 安全解析
→ 空白、零值、单位和公式缓存识别
→ 显式报表月份与完整自然日校验
→ 日统计与三班合计重算
→ 未闭账日排除
→ 自然日连续性及产量对账门控
→ 非生产运行 / 复产爬坡 / 生产状态候选分段
→ 状态内稳健比值和回顾性变点分析
→ 连续异常合并为核查事件
→ 领导可读的事实、候选解释和核查建议
```

状态名称都带“候选”含义。算法不能仅凭表内数值确认停产、检修、复产、电表
故障、漏采或违规；这些事实必须由工单、设备日志、原始凭证和现场记录确认。
日期缺口后的首日，或产量日报与三班合计不一致/无法核对的日期，运行状态固定
为 `unknown`，并清空此前连续零产和复产爬坡计数，防止跨缺口误报复产。

月报分析固定返回：

```json
{
  "analysis_mode": "retrospective",
  "lookahead_used": true
}
```

这表示状态内 median/MAD 和变点会查看当前整月，不是只使用当日之前数据的在线
预警。单变点还会与线性趋势模型进行 BIC 比较；可以被线性趋势更简洁解释的
平滑增长或下降，不再标成阶跃突变。

## 3. 对账口径与覆盖率

日报和三班重算不一致时，结果不会悄悄选择其中一个：

- `days[].metric_reconciliations` 并列保存日报值、三班重算值、差额、状态和
  实际分析口径；
- 争议日不进入稳健参考基线；但班次完整时，该日作为待检测候选点可明确采用
  三班重算值，日报值和重算值仍并列保留；
- 月度 KPI 只汇总日报与三班重算一致的日期，争议日和无法对账日分别计数；
- `metric_reconciliation_summaries` 并列给出日报累计、三班重算累计和仅对账
  一致日累计，三个累计的覆盖日数也分别返回。

覆盖率同时区分核心日报值齐全、模板全部必填字段齐全，以及五项班次合计全部
一致。兼容字段 `complete_closed_day_count` 仅表示“风量、用工、电量、产量
核心日报值齐全”，不能解释为整张表无缺失或全部对账通过。

## 4. 数据安全与信任等级

- 文件只在内存中解析，不调用 WPS、Excel 或 LibreOffice；
- 只支持本版明确校验的 OLE2/BIFF8 五量模板；
- 宏和活动内容会被拒绝；
- 文件大小、Workbook 流、BIFF 记录数、公式单元格数、工作表数、数据行数和
  单元格类型都有硬上限；结构预扫按物理工作表线性完成；
- 矿井身份必须由请求中的 `mine_id` 显式绑定，文件标题不能覆盖；
- 空白不会转换为数值零；
- `NaN`、正负无穷以及溢出到无穷的超长数字都会被稳定拒绝；
- 公式不会执行，只读取已保存缓存，并独立重算班次合计；
- 浏览器临时分析不落库、不建案、不进入历史基线。

API 响应固定标记：

```json
{
  "trust": {
    "input_class": "operator_uploaded_untrusted",
    "persisted": false,
    "audit_metadata_persisted": true,
    "persistence_statement": "input_and_analysis_result_not_persisted",
    "audit_metadata_scope": "metadata_only_no_file_or_daily_payload",
    "eligible_for_history": false,
    "creates_case": false,
    "regulatory_effect": "none"
  }
}
```

其中 `persisted=false` 明确指上传文件和分析结果正文不落库。库函数和 CLI
直接运行时 `audit_metadata_persisted=false`；生产 API 只有在成功写入不含文件
内容和逐日正文的最小审计事件之后，才会把它改为 `true`，用于追踪谁在何时对
哪个矿井运行过该临时功能。

## 5. 前端使用

以管理员或具有对应矿井范围的监管负责人登录，在“监管专业模式 → 临时分析”
中选择“生产运行五量月报”：

1. 输入监管侧矿井编号；
2. 选择报表月份；系统据此检查从月初到闭账日是否缺整日；
3. 选择最后一个已完成填报并闭账的日期；
4. 选择 `.et` 或兼容 BIFF8 文件；
5. 开始分析；
6. 先看合并事件，再按建议核对原始凭证。

当天仍在填报的行应放在 `closed_through` 之后。系统会保留该行用于展示，但不会
把它作为漏报或历史异常。

## 6. CLI

```bash
mineguard operational-monthly /path/to/七月五量月报.et \
  --mine-id M001 \
  --report-month 2026-07 \
  --closed-through 2026-07-30
```

源表没有单位时，结果会明确显示单位未知。确认单位后可以附加：

```bash
mineguard operational-monthly /path/to/七月五量月报.et \
  --mine-id M001 \
  --report-month 2026-07 \
  --closed-through 2026-07-30 \
  --electricity-unit kWh \
  --production-unit t \
  --labor-unit 人次
```

## 7. HTTP API

```text
POST /v1/analyze/operational-five-quantity-monthly-file
```

请求使用 JSON 和 Base64 文件内容，要求登录会话、CSRF 令牌及
`analysis.run` 权限。管理员可分析全部矿井；监管负责人只能分析自己授权范围内
的矿井。复核人员和只读人员不能运行该临时分析。

请求示例：

```json
{
  "mine_id": "M001",
  "source": {
    "source_id": "operator-upload",
    "filename": "七月五量月报.et",
    "received_at": "2026-07-31T08:00:00+08:00"
  },
  "report_month": "2026-07",
  "closed_through": "2026-07-30",
  "units": {
    "electricity": "kWh",
    "production": "t",
    "labor": "人次"
  },
  "content_base64": "..."
}
```

生产接口必须显式提交 `report_month`，且 `closed_through` 不能早于该月月初。
导入库为兼容旧的离线调用仍可由表内日期推断月份，但正式 HTTP 路由不会采用
隐式推断。调用方提交 `validation` 或 `analysis_parameters` 会被拒绝，防止通过
放宽容差或抬高阈值压掉告警。

响应中的 `configuration` 完整回显实际导入校验参数、分析参数、方法版本和
SHA-256 配置指纹。事件编号同时绑定文件指纹与配置指纹；因此相同输入和配置可
确定性复算，配置变化后不会误用旧事件编号。成功响应只有在
`operational_five_quantity_analysis_completed` 最小审计事件写入成功后才会
放行；审计只记录操作者、矿井、月份、文件指纹、配置指纹、方法版本和事件计数，
不记录 Base64 文件、文件名、表内逐日数据或分析正文。

## 8. 当前基线与后续历史学习

当前月报工具使用“当前文件内、同状态日期”的回顾性 median/MAD 基线，因此可以
发现月内明显偏离，但不能冒充长期正常历史。

正式历史模型应只接纳：

- 同一矿井、同一指标和同一统计口径；
- 同一工作面、班制、季节及运行状态；
- 来源和摘要可追溯；
- 时间上早于当前分析窗口；
- 已经人工复核为正常；
- 未被作废或确认存在数据错误。

历史模型、生产运行五量模型与产运洗销存 L1 物理模型保持并列，最终只在保守
风险融合层相互佐证。

# 90 天合成演示数据设计与验收

> **历史版（Legacy）**：本文描述旧 V1 多算法读模型和独立 `edge-agent` 演示数据，
> 不适用于当前双产品 V2。当前演示必须经一矿一 `agent/` 报送并由 `platform/` 唯一
> 五量算法重算；部署与验收以 [V2 部署手册](../../docs/V2部署与运行.md) 和
> [V2 验收清单](../../docs/V2验收清单.md) 为准。

本文约束“多矿、90 天测试版”的数据生成方式。演示数据必须进入与正式数据相同
的 SQLite 读模型并由后端算法重新计算；禁止在前端写死图表、统计数或预警结果。
所有页面和导出必须明显标注“合成演示数据，不得用于监管认定”。

## 0. 企业端和监管端的职责边界

企业端不是监管分析后台。它负责把本企业的原始材料组织成草稿，提示缺项和口径
冲突，保留来源摘要与人工确认记录，并在有权限的人员确认后提交。企业端不能查看
其他企业数据、辖区风险排序、监管案件结论或监管处置过程，也不能替领导作监管
认定。

监管领导端接收多企业报送和矿端只读采集数据，独立执行物理、历史、时序和来源
健康交叉核对，再由监管人员分派、复核、审批和留痕。现场设备的连续自动采集由
独立的 `edge-agent/` 承担；企业填报智能体不是唯一数据来源，也不应代替设备
网关自动造数或补签。

## 1. 领导端各功能真正读取什么

| 功能 | 接口 | 持久化来源 | 决定时间位置的字段 | 演示数据最低要求 |
|---|---|---|---|---|
| 辖区最新总览 | `GET /v1/dashboard/overview` | `batches`、`cases`、`analysis_runs` | 最新批次按 `batches` 写入顺序选取 | 最后一笔批次必须包含完整应报矿井清单和各矿结果 |
| 近 30 日覆盖、风险和积压 | `GET /v1/dashboard/trends` | `batches`、`cases`、`case_events` | `batches.created_at`、`cases.created_at`、`case_events.created_at` | 只改分析请求的 `window_end` 不够；必须写入历史接收和办理时间 |
| 近 90 日算法时序 | `GET /v1/dashboard/temporal` | `analysis_feature_windows`，并通过批次和特征哈希校验 | `analysis_feature_windows.observed_at`，其值由分析请求 `window_end` 派生 | 特征版本必须是当前版本；特征须通过哈希校验，且兼容性为完整的 `governed` 模式 |
| 安全驾驶舱和矿井点位 | `GET /v1/dashboard/safety` | `mine_registry`、`edge_observations`、`safety_alerts`、责任路由及边缘复算队列表 | 指标用 `observed_at`、修订号和序号选最新；预警使用 `detected_at`、`last_seen_at`、`due_at` | 矿井必须先登记；最新指标必须是 `analytic_accepted=1` 的真实入库观测 |
| 产量核验偏差热力图 | `GET /v1/dashboard/safety` 的 `verification_heatmap` | `production_verification_runs` | 每矿按 `window_end` 和 `created_at` 取最新一条 | 每矿至少一条核验结果；该热力图是“每矿最新状态”，不是 90 日矩阵 |
| 矿井分布示意 | `GET /v1/dashboard/safety`、`GET /v1/map/boundary` | `mine_registry.longitude/latitude` 和可选 GeoJSON | 不适用 | 每矿提供合成经纬度；无正式边界时仍明确是相对位置示意 |
| 月报、季报 | `GET /v1/reports/regulatory` | 上述领导分析、案件、预警、核验和矿井名录的只读组合 | 批次按 `created_at`；核验按 `window_end`；预警按 `[detected_at,last_seen_at]` 与报告期相交 | 报告期内必须同时存在批次；需展示核验覆盖时还要有同期间核验结果 |

补充约束：

- 一旦授权范围内存在 `context.kind` 以 `governed_` 开头的批次，领导统计只采用
  这类批次，普通管理员试算批次不会混入。
- 90 日接口只接受 `feature_json` 哈希有效、`feature_version` 为当前版本、
  `compatibility.trusted_mode == "governed"` 且
  `compatibility.governance_complete == true` 的特征。
- 90 日算法接口会返回每条序列的 `points` 和 `episodes`。若页面只展示事件而
  不展示 `points`，即使数据库有 90 天记录，也不能算完成“时序曲线”体验。
- 月季报的安全快照是生成报告时的当前状态；它不会伪装成历史报告期末快照。

## 2. 安全的最小注入路径

演示环境使用独立状态目录，例如 `.mineguard-demo`，不得直接清理或覆盖
`.mineguard`。推荐提供一个受控命令：

```bash
mineguard seed-demo \
  --state-directory .mineguard-demo \
  --days 90
mineguard serve \
  --state-directory .mineguard-demo \
  --host 127.0.0.1 \
  --port 8080
```

生成器应遵循以下路径，而不是直接拼接数据库行：

1. 默认锚点取今天 UTC 零点，代表截至前一完整自然日；允许用
   `--anchor-date YYYY-MM-DD` 固定最后窗口结束日，保证测试可复现。
2. 通过 `EdgeTelemetryRepository.upsert_mine` 写入矿井名录。
3. 每个自然日构造一个完整辖区批次，通过
   `LocalRepository.save_portfolio_batch(..., created_at=历史接收时间)` 写入。
   该调用会一并生成分析运行、不可变算法特征和案件。
4. 批次 `context.kind` 使用专用 `governed_demo_seed`，每矿提供固定的
   `profile_id`、`profile_version` 和 `registry_snapshot_hash`，同时写入：

   ```json
   {
     "demo_seed": true,
     "demo_dataset": {
       "active": true,
       "dataset_id": "qinyuan-leadership-90d-v1",
       "schema_version": "mineguard-demo-seed-v1",
       "anchor_date": "YYYY-MM-DD",
       "days": 90,
       "mine_count": 6,
       "classification": "synthetic_demo_only",
       "regulatory_use": "prohibited"
     }
   }
   ```

   `demo_seed` 的显示优先级必须高于“可信治理批次”，防止演示数据被页面
   误写成真实可信数据。
5. 历史案件通过仓储层状态机办理，显式传入演示事件发生时间；HTTP 办理接口
   不应允许客户端回填历史时间。这样才能真实产生首次响应、闭环时长、重开次数
   和每日积压曲线。
6. 最新安全指标走 `EdgeTelemetryBatch` 校验和
   `ingest_batch(received_at=...)`。演示预警通过平台预警账本生成，但全部保持
   `operational=false` 的影子模式，规则快照和详情均标记 demo；不冒充经双人审批
   的正式规则，不进入外部消息投递。
7. 每矿使用稳定的 `request_id` 保存生产交叉核验结果；`window_end` 落在相应
   月份，保证月季报可以选中。
8. 生成结束后写一份清单，记录数据集编号、锚点、矿井数、批次数、特征数、
   案件数、预警数、核验数，以及批次哈希和生命周期链校验状态。

重复执行同一数据集和锚点时应当幂等；不同锚点或生成器版本必须使用不同
`dataset_id`。若目标状态目录已有非演示数据，命令必须失败关闭，不得自动删除。

## 3. 多矿 90 天场景

按日序号 `0..89` 生成。六座矿均进入完整 90 日应报名录，矿名、坐标、数值和
人员姓名均为合成信息。

| 矿井 | 90 天行为 | 领导端预期体验 |
|---|---|---|
| `DEMO-M001` 演示一矿 | 物理关系和时序基线稳定 | 展示正常日波动和稳定控制范围 |
| `DEMO-M002` 演示二矿 | 中段以后上报量逐步偏离其他来源 | 展示缓慢漂移、风险积累和生产影子线索 |
| `DEMO-M003` 演示三矿 | 前段稳定，约三分之二处出现固定变化点 | 展示突发结构变化、P1 技术线索和甲烷影子预警 |
| `DEMO-M004` 演示四矿 | 每隔约两周出现连续三日异常 | 展示重复异常片段、人卡不一致影子预警 |
| `DEMO-M005` 演示五矿 | 每周间歇缺报且最后一天固定缺报 | 最新覆盖率为 5/6、趋势空档和补报案件；吨煤核验历史不足 |
| `DEMO-M006` 演示六矿 | 生产序列稳定，但甲烷来源心跳超时、连续失败和缺数 | 展示来源健康、甲烷/通风影子安全线索 |

实际每日批次规则：

- `DEMO-M001` 全程保持物理一致。
- `DEMO-M002` 从第 30 天后逐步扩大偏离，末段最大约 19%。
- `DEMO-M003` 在第 60 天后切换为约 19% 的固定偏离。
- `DEMO-M004` 从第 20 天起，每 14 天形成一个连续三日异常片段。
- `DEMO-M005` 从第 8 天起按每 7 日连续缺报两天，并强制最后一天缺报。
- `DEMO-M006` 生产批次保持稳定，来源缺失和安全线索由边缘读模型展示。

基础时序值使用固定周期扰动，而不是随机数。例如：

```text
稳定值 = 基线 + [0.00, 0.03, -0.02, 0.01, -0.01] 按日循环
持续抬升 = 稳定值 + max(0, 日序号 - 59) × 0.18
突发值 = 稳定值 + 6.00
```

这样同一锚点每次生成的状态、排名和异常事件可重现，也避免靠随机噪声碰巧触发
检测器。

## 4. 后端验收断言

验收脚本应登录领导账号后直接请求接口，并至少检查：

### 总览和 30 日趋势

- `/v1/dashboard/overview` 返回 6 座矿，最新批次覆盖率为 `5/6`。
- 最新批次包含 `P1`、`DATA` 和 `NONE`，且存在可进入核查台账的案件。
- `/v1/dashboard/trends?days=30&timezone=Asia/Shanghai` 的
  `daily_trend` 覆盖 30 个有数据自然日，至少 2 天覆盖率低于 1。
- `mine_risk_ranking` 包含全部有报告或积压的矿井，M002、M003、M004 位于
  前列，稳定的 M001 不应因数据量多而被排成高风险。
- `repeated_anomalies` 至少包含生产冲突和缺报两类。
- `case_performance` 的新建数、已关闭周期、当前积压、首次响应和闭环时长均为
  非零；至少有一个 `reopened_cycles`。

### 90 日算法时序

- `/v1/dashboard/temporal?days=90` 的 `status` 为 `anomalous`。
- 至少 6 条 `balance.raw_anomaly` 序列，且 `health.point_count >= 400`。
- 缓慢漂移、变化点和重复异常矿至少各有一个事件；事件包含起止时间、异常点数
  和检测器名称。
- `health.rejected_feature_row_count == 0`、
  `health.feature_limit_reached == false`。
- 返回的序列点均来自数据库特征；删除或作废某个演示批次后，对应点应从结果中
  消失，证明页面不是静态假图。

### 安全驾驶舱、地图和核验热力图

- `/v1/dashboard/safety` 返回 6 座已启用矿井和有效经纬度。
- 影子预警包含红、橙、黄三色，正式开放预警为零；影子结果单独统计且不投递。
- 最新指标含人员、甲烷、通风和来源健康中的多个指标，且展示观测时间和来源。
- `verification_heatmap` 至少有 5 个 ready 结果和 1 个
  `insufficient_history` 结果；同向偏离矿排在正常矿之前。
- 地图点击矿点后使用同一个 `mine_id` 过滤预警，不泄漏范围外矿井。

### 月报和季报

- 当前月和包含锚点的季度报告均可生成，范围固定为 6 座授权矿井。
- 月报的应报数、实收数、缺报矿数、核验覆盖和安全预警数均非零。
- 至少一座矿为 `attention`，至少一座为 `incomplete` 或 `blocked`。
- 报告 `delivery.automatically_sent == false`，且保留合成演示免责声明。

### 权限和隔离

- 仅授权 `DEMO-M001`、`DEMO-M002` 的 viewer 在总览、趋势、时序、预警、
  热力图和报告中都只能看到这两座矿。
- 企业端只能生成、校验、人工确认并提交自己的材料；不能读取领导排名、其他
  企业数据、监管案件结论或安全处置状态。
- 演示数据的 `dataset_id` 和合成标识在页面、API 和报告中可追踪，不允许只靠
  启动日志说明。

## 5. 当前实现需特别注意

1. 普通分析 API 保存历史 `window_end` 并不等于历史报送；30 日趋势使用
   `batches.created_at`。
2. 90 日接口已有真实检测点，但前端若丢弃 `series[].points`，领导只能看到事件
   摘要。完整体验应增加矿井/指标筛选、观察值折线、基线和异常点，同时限制一次
   展示的序列数量。
3. 核验“热力图”当前是每矿最新结果的色块排序，不应描述成时空热力图。
4. 数据缺日不会自动变成时序算法的 `missing=true` 点；缺报由领导趋势明确展示。
   若未来需要检测采样缺口，应由后端按应报计划生成缺测标记，不能由前端补零。
5. 合成数据只能写入独立演示状态目录。现场历史数据必须通过来源治理、证据摘要
   和审批流程接入，不能复用演示种子旁路。

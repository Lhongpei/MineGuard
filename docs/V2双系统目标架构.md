# 五量监管 V2：双系统目标架构

> **Legacy 五量 V2 架构。** 当前正式主线是
> [十量 V3](十量V3部署与运行.md)；本文只供历史只读、迁移和审计参考。

状态：已确认，作为本轮重构的产品与技术边界。

## 1. 运行产品

系统只包含两个可部署的软件：

- `agent/`：部署在单座煤矿的一矿一智能体；
- `platform/`：政府监管平台。

`contracts/` 只保存双方共同实现的版本化协议、样例和测试向量，不是运行产品，
也不成为任何一方的运行时依赖。两个软件不互相导入源码，不共享数据库、领域模型、
文件目录或密钥。

原 `edge-agent/` 不再作为第三套产品。仍有价值的只读目录采集、稳定文件判断、哈希
去重和断网重试能力并入企业智能体的 connector/worker；旧实现仅作为迁移期归档。

## 2. 唯一业务主线

```text
煤矿原始材料或设备数据
  -> 企业智能体导入、解释结构并规范化
  -> 企业人员确认
  -> 签名、幂等报送
  -> 政府验签、可靠接收
  -> 唯一五量监管引擎自动分析并留痕
       -> normal_candidate：记入正常候选台账
       -> insufficient_data：形成数据不足风险
       -> risk：形成结构化风险报告
  -> 企业智能体主动领取风险
  -> 绑定风险的对话、原因分析、证据和措施草稿
  -> 企业人员确认回复
  -> 政府自动记录回复
  -> 如有修订数据，作为新修订重新运行同一算法
  -> 政府只读大屏实时刷新业务状态
```

企业的文字解释只会形成 `explanation_recorded`，不能消除数值风险。只有新修订数据
经过同一算法重算通过，风险才能成为 `cleared_by_reanalysis`。所有输入、结果、风险、
回复和状态迁移都必须留痕；“留痕”和“进入正常历史基线”严格分开。

## 3. 五量口径

正式五量固定为：

1. 风量；
2. 电量；
3. 火工品量；
4. 入井人员量；
5. 产量。

业务口径是五类，数据层不是把雷管和炸药误列为两类“量”。火工品量以雷管数量
（`count`）、炸药质量（`kg`）等带有各自单位的子项表达；各子项分别分析，不能直接
相加。当前规范人员字段为 `mine_entry_persons`，只表示对应日报或班次统计范围内实际
发生的入井人次，值必须为整数，聚合方式固定为 `sum`；它不是泛用工、在册/排班人数，
也不是某一时点的井下人数。由此形成六个规范原子字段，但六原子字段不等于六量。

报文保留月度统计窗口、逐日值、班次值与日报合计。缺失使用 `null` 和明确质量状态，
不得以零代替缺失。原“产、运、洗、销、存”模型不再作为正式产品的第二算法入口。

人工导入和设备/API/固定目录直采是并列合法的采集方式。系统可以保留采集方式、原件
摘要和单元格/字段定位用于追溯，但不得建立“人工来源较低、设备直采较高”的信任等级，
也不得因为采集方式不同改变算法权重。

## 4. 企业智能体边界

每个智能体实例只绑定一座煤矿、一个 `mine_id`、一组企业身份和一套传输密钥；不同
煤矿属于相互独立的经营主体，数据库、原件库、用户、对话、风险收件箱和 outbox 均
不得跨矿共享。

企业端负责：

- 人工上传 ET/XLS/XLSX/CSV/JSON；
- 监听白名单固定目录，或通过只读 API connector 采集；
- 安全解析、列和单位映射、日期/班次识别、缺项追问；
- 保留原值、规范值、换算、来源定位、模型参与和人工修订；
- 在人工确认后可靠报送；
- 主动轮询本矿风险，使用绑定风险的煤炭对话进行解释；
- 形成人工确认的原因、事实、证据、措施和修订声明回复。

模型只能提出映射、解释和回复草稿，不能编造缺失数值、原因、证据，不能自动代表企业
确认或提交。

## 5. 政府平台边界

领导和普通监管业务用户的前端完全只读，只提供查看、筛选、搜索、钻取、趋势、导出和
展示。不能代企业上传或修改数据，不能手工修改算法结论，不能删除风险，不能在大屏上
改变算法参数。

系统自动执行验签、接收、排队、分析、发出风险、接收回复、重算和追加留痕。账号、
企业通信密钥、算法配置版本、同类矿分组和备份由独立运维面或配置文件维护，不进入领导
大屏的业务操作区。

## 6. 唯一五量监管引擎

政府只公开一个版本化算法产品。内部管线包含：

1. 契约、完整性、单位、日期、班次与日报算术检查；
2. 停产、复产、爬坡和稳产工况分段；
3. 基于本矿正式准入历史的 Rolling MAD、EWMA、CUSUM、Page-Hinkley、稳健基线、
   连续异常、漂移和变化点；
4. 基于同产能、工艺、班制、煤种、季节和工况且按截止日冻结的匿名同类矿参考；
5. 加权 L1 联合协调、软区间偏离和最小冲突集（MCS）；
6. 经验校准和保守的三态决策。

L1/MCS 不再硬套“产运洗销存”的物料平衡。规则层按聚合语义完成班次、非负和单位
确定性检查；主 L1 将日报和可比班次汇总作为带容差观测，将本矿历史及同类矿作为软
参考。MCS 阶段才把这些容差/参考带硬化，用于计算最少待解释指标、日期和证据组合，
不单独作监管认定。

时序能力保留并升级，但不再暴露为第二套可选算法。历史或同类矿不足时可以形成不进入
正式基线的冷启动正常候选；求解失败或数据覆盖不足必须显式留痕。若同时存在确定性风险，
风险优先，不能通过少报数据把风险降成单纯 `insufficient_data`。

## 7. 多矿与实时大屏

政府平台分别保存和分析每座煤矿的数据。综合分析只使用同类矿匿名统计和辖区共同变化，
不会把多个独立煤矿的数据混成一座矿的历史，也不会向企业泄露其他矿明细。仅凭当前五量
不宣称能够完成矿际运输、购销和收货物理勾稽。

报表以月度窗口承载逐日和班次事实；固定目录有新文件、报送、风险或回复落库后，大屏在
秒级刷新。界面必须显示明确的数据截至时间，不能把日报或月报包装成传感器级实时数据。

## 8. 迁移与兼容

V2 使用新契约、新表和新状态机。现有数据库与哈希链不修改、不清空，作为 Legacy 只读
档案保留。新版验收前可以保留旧代码用于比对，但旧浏览器写入口、旧多算法入口和第三套
边缘产品不得出现在正式主线或默认启动说明中。

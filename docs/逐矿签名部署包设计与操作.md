# MineGuard 逐矿签名部署包设计与操作

## 1. 目标

正式部署采用“统一签名程序 + 一矿一对受控配置包”，不再为每家企业编译不同代码，也不
要求现场人员手工编辑大段 `agent.env` 或 `clients.json`。

```text
同一批签名 Enterprise Agent 安装包
                  +
某矿 Enterprise Agent 配置包（.mgprov）

同一批签名 MineGuard Platform 安装包
                  +
同一矿 Platform 注册包（.mgreg）
```

两个配置包具有相同的 `pair_id`，把一个煤矿、一个经营主体、一个 Agent 系统身份、政府
HTTPS origin、同类矿分组以及两把逐矿 HMAC 精确绑定。程序代码和算法对所有企业保持
一致；企业差异只存在于签名配置，不形成企业专用代码分支。

## 2. 能锁定和不能封装的内容

Agent 包可以锁定：

- 生产模式、四眼复核、Secure Cookie 和企业端 HTTPS origin；
- 煤矿、经营主体和 Agent 系统身份；
- 时区和五项同类矿比较口径；
- 政府 Platform HTTPS origin、私有 CA 文件路径和发送者身份；
- 政府系统/主体身份、双方应用 key ID；
- 企业应用消息 HMAC 和另一把 HTTP 运输 HMAC；
- 经批准的短期换钥重叠配置。

以下内容禁止进入逐矿包：

- LLM、新闻搜索或其他模型服务 API Key；
- 用户明文密码、密码摘要和浏览器会话；
- 数据库路径、可执行命令、服务参数和任意环境变量；
- 自动采集监听目录、任意 URL 或上游设备账号；
- 演示账号、演示数据和合成样本。

模型和上游数据源凭据属于另外的受控配置域。核心 CSV 导入、人工复核、报送、政府分析
和回执在不配置模型 API 时仍必须完整工作。

## 3. 密钥与信任边界

部署包和 Windows Setup 使用不同的签名用途：

- Authenticode 代码签名证明安装程序的发布者和文件完整性；
- Ed25519 部署包签名证明逐矿配置由获批签发者生成；
- 每矿应用消息 HMAC 验证业务报文；
- 每矿运输 HMAC 验证 HTTP 请求；
- HTTPS 证书验证实际连接的政府服务器。

这五类材料不得互相替代。两把 HMAC 由生成器使用操作系统 CSPRNG 创建，内容不同、不同矿
不复用，也不进入 EXE、前端、日志或命令行。`.mgprov` 和 `.mgreg` 使用各自独立的高熵
激活码，经 scrypt 派生 AES-256-GCM 密钥后加密；激活码通过与配置包不同的受控渠道交接。

签发私钥使用口令加密的 PEM 保存，并应位于离线签发机或单位密钥系统。企业和 Platform
导入前还必须通过独立审批记录核对签发公钥指纹；统一算法是 Ed25519
SubjectPublicKeyInfo DER 的 SHA-256（64 位小写十六进制），不是 raw key 或 PEM 文件
摘要。把公钥和配置包放在同一个可写 U 盘，不能单独构成可信根。

## 4. 包格式与运行锁

中立合同为 `mineguard-provisioning-bundle-v1`，权威格式见
[`contracts/specs/provisioning-bundle-v1.md`](../contracts/specs/provisioning-bundle-v1.md)。
信封采用确定性 JSON、AES-256-GCM、scrypt 和 Ed25519。签名覆盖受保护元数据和完整密文；
解密后还要核对 payload SHA-256、锁定配置 SHA-256、`bundle_id`、`pair_id`、版本、矿井和
系统身份。

首次导入或更新必须发生在 `expires_at` 之前，且签发时间最多允许 5 分钟正向时钟偏差。
该时间只限制包的安装窗口：已经成功导入的
运行配置不会因为原包后来过期而突然停止。撤销、换钥或改地址必须由更高
`profile_version` 的新签名包显式完成。

导入器保存受保护锁记录。此后每次 Agent 启动和正式 `config-check` 都重新验证签名及当前
锁定值摘要；手工修改矿井身份、政府地址、分组或 HMAC 会直接阻断启动。Platform 对由
`.mgreg` 导入的客户端项执行同样的注册摘要复核。已有手工配置可以继续运行并显示
`unmanaged`，但所有新部署默认使用受管配置。

## 5. 更新、重复导入和错矿规则

- 相同 `bundle_id`、相同内容重复导入是幂等操作，不重复创建注册项；
- 同一 `mine_id`、`system_id` 和 `party_id` 只允许显式导入更高
  `profile_version` 的签名更新；更新保持原 `pair_id` 和完整主体、版本精确加 1，并保留
  紧邻上一版 message/transport secret；
- 降级、相同版本不同内容、跨矿覆盖、跨企业覆盖和发送者不一致全部拒绝；
- Agent 的 `PLATFORM_V3_SENDER_ID` 必须等于 `ENTERPRISE_SYSTEM_ID`；
- Platform 注册项与 Agent 包的身份、分组、key ID 和两把 HMAC 必须来自同一个
  `pair_id`；
- 部署包过期、签名错误、激活码错误、密文被改、未知签发者或配置键不在白名单时，导入
  必须不写入任何部分状态；
- 导入采用同卷临时文件、刷盘和原子替换，失败不得留下半配置。

## 6. 推荐现场流程

1. 在离线签发机填写一矿 profile，核对正式身份、域名、CA 路径和同类矿分组；
2. 分别选择企业包、政府注册包、企业激活码、政府激活码四个互不包含的目录，生成
   `.mgprov`、`.mgreg`、签发公钥、两份清单和两个不同激活码；
3. Platform 管理员先导入 `.mgreg`，再检查生产 `config-check` 与 `/readyz`；
4. 企业管理员在本矿 Agent 实例导入 `.mgprov`，现场另建经办与复核账号；
5. Agent 执行 `config-check --production`，两端分别安装服务；
6. 用一个已核对月份完成“经办保存 → 另一人确认报送 → 政府分析 → 报告送达确认”；
7. 记录 `pair_id`、`bundle_id`、profile 版本、签发公钥指纹、安装包摘要和验收 ID，不记录
   激活码、HMAC、密码或完整业务数据；
8. 激活码文件和已解密临时材料按单位介质制度销毁，签名包与非秘密审计信息归档。

Platform 导入必须输入介质外 expected SPKI 指纹与 issuer key ID。正式服务另在受保护配置
中启用 `MINEGUARD_PROVISIONING_MANAGED_REQUIRED=true`，并固定受信 PEM、expected 指纹
和 key ID，防止删除注册锁或追加手工客户端后静默降级。

Agent 导入不能只相信包内 CA 目标路径：还要选择独立 CA 源文件并输入介质外批准的原始
PEM SHA-256。导入器验真后复制到锁定路径、设置服务 ACL，并在运行时持续校验内容摘要。

## 7. Platform 命令行固定接口

初始化离线签发密钥时，私钥口令通过本机无回显交互或受保护文件读取：

```text
mineguard provision issuer-init --private-key <issuer-private.pem> --public-key <trusted-public.pem>
```

初始 `profile_version=1` 生成成对包。正式操作必须使用四个彼此不相等、也不互为父子目录
的输出区，防止把政府 `.mgreg` 或政府激活码一起交给企业：

```text
mineguard provision create-pair --profile <approved-profile.json> \
  --issuer-private-key <issuer-private.pem> \
  --enterprise-bundle-directory <enterprise-delivery> \
  --platform-registration-directory <government-registration> \
  --enterprise-activation-directory <enterprise-secret-channel> \
  --platform-activation-directory <government-secret-store>
```

企业交付区只包含 `.mgprov`、从本次签发私钥派生的 `issuer-public.pem` 和
`enterprise-handover.json`；政府注册区只包含 `.mgreg` 和完整
`provisioning-manifest.json`。企业交接清单不引用 `.mgreg`；两份清单都不出现激活码
字段、文件名或摘要。签发公钥条目同时记录 PEM 文件 SHA-256 和 SPKI-DER SHA-256，后者
仍必须与介质外审批值独立核对，不能因公钥与企业包同盘而跳过信任验证。

`--output-directory` 与 `--activation-directory` 只为已有自动化和测试保留；两者必须同时
提供、不得与四区参数混用。正式 Windows 向导不使用该共享布局。

更新时必须额外提供上一版 Platform 包和其激活文件。生成器从受签名旧包恢复 pair/主体和
紧邻上一把 key，拒绝手工伪造版本跳跃：

```text
--previous-registration-bundle <previous.mgreg>
--previous-registration-activation-code-file <previous-platform.activation>
```

政府机导入 `.mgreg` 的固定接口如下；expected 两项必须来自介质外审批记录：

```text
mineguard provision import-registration --bundle <mine.mgreg> \
  --activation-code-file <platform.activation> \
  --issuer-public-key <trusted-public.pem> \
  --expected-public-key-sha256 <64-lowercase-spki-der-sha256> \
  --expected-issuer-key-id <approved-key-id> --clients-file <clients.json>
```

更高版本再显式增加 `--allow-update`。命令返回非秘密的 `platform_identity`，Windows
控制中心据此写入政府 system/party/key ID；不得要求现场人员再次手抄这些值。

接口尚未确定不影响这一流程。企业可以先人工上传十量 CSV；自动监听目录和连接器等上游
采集配置待接口明确后单独审批，不改变 Agent ↔ Platform 的逐矿身份和 V3 合同。

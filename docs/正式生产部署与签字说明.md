# MineGuard 正式生产部署与签字说明

本说明适用于政府集中部署的 Platform 和每矿独立部署的 Enterprise Agent。
“不用 demo 账号”只是正式化条件之一，不等于软件已经成为正式版。

当前正式业务合同是十量 V3，字段、CSV、V2 只读迁移和环境变量以
[十量 V3 部署与运行](十量V3部署与运行.md)为准。所有现场签字必须覆盖 11 个原子字段；
`invoiced_quantity_t` 只允许非负正常/蓝字发票吨数，红票、退票等辅助事件在企业来源
系统独立留存并另算净额；当前 V3 主报文不承载这些事件。

本轮源码候选版本为 Platform `0.6.1`、Enterprise Agent `0.4.2`。版本号表示源码与
配置门禁已经进入生产候选阶段，不代表当前已有的旧安装包自动升级为正式介质；最终交付
仍必须从同一个干净提交重新构建，并选择“带 Authenticode 签名”或
“`INTERNAL-UNSIGNED` 受控内网无签名”其中一条完整发行链，核验后完成现场验收。

## 1. 正式版的四个层次

1. **受控发行介质**：两份安装包必须来自同一个干净提交，各自版本与本批发行清单一致，
   并采用以下一种不可混用的模式：
   - `signed-production-candidate`：具有单位认可的 Authenticode 代码签名和 RFC 3161
     时间戳，执行前按介质外记录核对签名者指纹和 SHA-256；
   - `unsigned-internal-release`：文件名明确包含 `INTERNAL-UNSIGNED`，没有 Windows
     发布者身份；执行前必须用目标机已受信任的 Windows `Get-FileHash`，按介质外记录
     核对 Setup SHA-256，安装正式服务时再核对整个子发行清单 SHA-256。

   两种模式都必须随附发行清单。包内界面、脚本或同一 U 盘里的 `SHA256SUMS.txt` 只能做
   纵深检查，不能认证执行它们自身；无签名模式的真实性依赖交付人与接收人的介质外摘要
   交接和执行前核验。
2. **正式运行配置**：必须显式启用生产模式，使用正式账号、HTTPS、逐矿身份、两把不同
   HMAC、独立状态目录、Secure Cookie、最小权限和四眼复核。
3. **现场技术验收**：必须在实际 Win10 1809+/Server 2019+ x64 目标机上完成安装、服务、
   断网恢复、端到端交换、备份恢复、时钟和证书验收。
4. **业务上线签字**：真实字段映射、单位、统计窗口、同类矿分组、算法参数和处置口径必须
   由企业、监管、信息化、算法/数据治理和运维责任人签字。

软件正式运行后仍只生成辅助核查线索，不自动形成违法事实、责任或处罚结论。执法使用还需
部署单位另行完成法律、证据和行政流程授权。

## 2. 以下情况一律不能称为正式版

- 安装包文件名含 `UNSIGNED-TEST-ONLY`，或发行清单既不是
  `signed-production-candidate` 也不是 `unsigned-internal-release`；
- 把普通未签名测试包改名为 `INTERNAL-UNSIGNED`，或无签名正式包没有通过介质外 Setup
  SHA-256、批次和源码修订号核验；
- Platform 或 Agent 使用 `123123123`、演示账号、旧策略/默认待换密凭据或
  常见弱密码。Platform 可为新用户分配符合当前强度策略的一次性初始密码，
  但该用户在自行改密前只能进入改密流程，不得访问监管业务；
- 把演示状态目录、太岳/梗阳随包样表或合成教学数据复制到正式状态库；
- 直接向办公网开放 8080/8090 明文端口，或远程 Platform 地址使用 HTTP；
- 多矿共用 Agent 数据库、账号、系统身份或 HMAC；
- 企业端同一账号同时拥有经办和复核报送权限；
- 只看 `/healthz` 或 `/api/v1/health` 为 200，未检查 `/readyz`、身份和完整交换链；
- 未做备份恢复、断网重试、时钟偏差、证书到期和密钥泄露演练。

## 3. 部署单位必须提前准备的材料

### 3.1 发行与主机

- Platform 和 Agent 同批次的已签名安装包，或名称含 `INTERNAL-UNSIGNED` 的受控内网
  安装包，以及 `release-manifest.json`、`SHA256SUMS.txt`；
- 通过另一受控渠道交付的两份安装包 SHA-256、两份对应的
  `child_release_manifest_sha256` 和批准的发布批次/源码修订号；签名模式还要交付签名
  证书 40 位 SHA-1 指纹。上述值不得从待验安装包或同一 U 盘自动采信；
- 受支持且仍在安全更新期的 x64 Windows 目标机、固定本机 NTFS 数据盘、
  现代 Edge/Chrome；优先使用 Windows Server 2019/2022 或 Windows 11。Windows 10
  技术兼容不等于仍获得安全更新；2026 年使用普通 Windows 10 22H2 必须
  另行核对已激活组织 ESU，或确认具体 LTSC 版本仍在生命周期内；
- 经批准的 WinSW x64 及其预先取得的 SHA-256，用于长期 Windows 服务；
- 代码签名证书与 HTTPS 服务证书是两类不同证书。选择 `INTERNAL-UNSIGNED` 可以不购买、
  不配置代码签名证书，但不取消跨机器访问的 HTTPS、DNS 和传输安全要求。

### 3.2 网络与证书

- 政府 Platform 的正式 HTTPS origin，例如 `https://mineguard.example.gov.cn`；
- 每矿 Agent 浏览器入口的 HTTPS origin；
- 内网 CA 根/中间证书、DNS、443 端口策略、NTP/W32Time 来源；
- 8080/8090 只监听 `127.0.0.1`，由 IIS/Caddy/Nginx 等反向代理提供 HTTPS；
- 企业 Agent 只需出站访问政府 HTTPS，政府无需主动连接矿区内网。

### 3.3 每矿身份与密钥

每座矿必须审批并冻结以下值：

| 项目 | Platform `clients.json` | Agent 配置 |
| --- | --- | --- |
| Agent 系统身份 | `sender_id` | `ENTERPRISE_SYSTEM_ID`、`PLATFORM_V3_SENDER_ID` |
| 企业主体 | `party_id` | `ENTERPRISE_OPERATOR_ID` |
| 煤矿 | `mine_id`、`mine_name` | `ENTERPRISE_MINE_ID/NAME` |
| 应用消息 key ID | `active_message_key_id` | `ENTERPRISE_EXCHANGE_KEY_ID` |
| 应用消息密钥 | `message_keys[key_id]` | `ENTERPRISE_EXCHANGE_HMAC_SECRET` |
| 运输密钥 | `transport_secrets` | `PLATFORM_V3_TRANSPORT_HMAC_SECRET` |

同一矿的对应值必须完全一致；两把 HMAC 必须不同、至少 32 字节；不同矿不得复用。
秘密应在受控部署机上用 CSPRNG/密钥系统生成，通过受控介质交接，不能发到聊天、邮件、
Git 仓库、前端或普通日志。

企业应用消息 key 轮换时，Platform `message_keys` 在批准窗口内保留新旧 key；Agent
将退役企业 key 写入单行 `ENTERPRISE_HISTORICAL_EXCHANGE_KEYS_JSON`，仅用于按报文
key ID 验证不可变历史前序。新消息始终由当前 key 签发。该企业历史密钥环不能用
`REGULATORY_PREVIOUS_*` 代替；后者只验证政府发给企业的入站消息。应用 HMAC 为双向
共享，协调换钥时同一退役 secret 要在两个方向分别登记，但仍按各自 key ID 选择。删除
旧 key 前必须确认相关历史版本不再允许更正，或已有满足保留期与恢复要求的受控密钥归档。

还必须填写并审批 `capacity_band`、`mining_method`、`shift_system`、`coal_type` 和
`operating_regime`，不能保留 `unclassified` 或占位值。

### 3.4 账号

- Platform 至少一个已完成改密的具名管理员；领导账号使用只读角色和明确矿井范围；
- Agent 至少两个姓名不同的具名账号：
  - 经办账号：`read`、`write`，不得有 `confirm`、`submit`；
  - 复核报送账号：`read`、`confirm`、`submit`，不得有 `write`；
- 正式密码至少 12 位，包含大小写字母、数字、符号中的至少三类；
- Platform 从旧版本升级后，会把无法证明符合当前密码策略的历史账号标为旧凭据策略，
  即使原密码不在常见弱口令字典中也会拒绝正式启动。账号本人应在服务器本机交互终端运行
  `mineguard user change-password <账号> --state-directory <正式状态目录>`，先验证旧密码，
  再输入两遍新密码；不得通过临时改用非生产模式启动来绕过；
- 先前在聊天、终端或仓库出现过的模型 API Key 必须撤销重发。模型 API 不是核心填报、
  报送和监管分析的前置条件；未完成联网和数据合规审批时应留空。

## 4. 推荐上线顺序

### 4.1 冻结与核验发行

1. 冻结干净 Git revision，执行契约、两端全量测试、前端语法、Windows 打包和安装生命周期；
2. 在受控 Windows 构建机生成同一种发行模式的 Platform 与 Agent 安装包；选择
   `INTERNAL-UNSIGNED` 时构建机不需要 SignTool、代码签名证书或时间戳服务；
3. 在执行任何 Setup/PowerShell 之前，由交付人和接收人根据介质外记录独立核验文件
   SHA-256、版本和 source revision；签名模式还要核验签名状态、时间戳和签名者指纹；
4. 将同一批次安装包和清单写入不可变正式归档。

正式交付只执行已完成上述外部核验的 signed Setup.exe 或明确标记的
`INTERNAL-UNSIGNED` Setup.exe。直接解包 staging 后运行 `Install-*.ps1` 只能用于受控
构建/兼容性测试；即使脚本能校验包内 EXE，也不能证明它自身在执行前未被替换。

### 4.2 先部署政府 Platform

1. 使用全新正式状态目录，不复制任何演示库；
2. 准备包含所有拟接入煤矿的正式 `clients.json`；
3. 在 Platform 控制中心选择“正式内网配置”，填写正式管理员和 HTTPS 配置；
4. 安装低权限 Windows 服务，确认 8080 仅回环、443 可从批准网段访问；
5. 检查 `/healthz` 存活及 `/readyz` 就绪；正式模式下审计链、Schema 或客户端注册异常会
   使 `/readyz` 返回 503。

### 4.3 再逐矿部署 Agent

1. 一矿创建一个独立实例、状态库、端口、账号、收件目录和密钥；
2. 配置 `ENTERPRISE_AGENT_PRODUCTION_MODE=true` 与
   `ENTERPRISE_AGENT_FOUR_EYES_REQUIRED=true`；
3. 用 `enterprise-agent hash-password --production --json` 生成不含明文的正式密码配置字段；
4. 配置政府 HTTPS、CA、逐矿身份、双 HMAC 和同类矿分组；
5. 执行 `enterprise-agent config-check --production`，任何错误都必须修正，不能使用
   `-AllowIncompleteDemo` 绕过；
6. 安装服务后检查 `/api/v1/health` 和登录后的 `/api/v2/status`。

Platform 必须使用 `NT SERVICE\MineGuardPlatform`，每个 Agent 实例必须使用
`NT SERVICE\MineGuardEnterpriseAgent-<实例名>`。安装脚本会将服务 SID 设为
`unrestricted` 并复核实际服务账号/SID；共享 `LocalService` 的旧服务必须先按迁移流程卸载再重建。

### 4.4 做一条真实但受控的完整链路

使用已由业务人员核对的一个月报测试：

1. 企业上传/只读目录采集；
2. 经办账号核对、补充并保存草稿；
3. 退出经办账号，由复核报送账号独立确认；
4. Agent 签名入 outbox，并通过 HTTPS/HMAC 发送；
5. Platform 返回签名接收回执并只分析一次；
6. Agent 拉取分析报告并发送 delivery ack；
7. 企业形成结构化回复，再由独立复核账号发送并取得回复回执。

验收记录应保存脱敏截图、时间、message/report/run/response ID 和文件摘要，不保存真实
口令、Cookie、HMAC、API Key 或完整企业原始数据。

### 4.5 灾备与故障验收

- Platform 备份、`verify-backup` 和恢复到新目录成功，`backup.key` 分离保管；
- 每矿 Agent 备份包含 DB、outbox/inbox、cursor、回复、审计与 quarantine，并恢复成功；
- 验证断网后原 message ID/idempotency key 重试、服务重启不重复分析；
- 验证磁盘接近满、证书到期、时钟偏差和密钥轮换/泄露处置；
- Windows 数据盘与备份介质使用单位认可的静态加密。

SQLite 内审计链能发现服务运行期的非法追加、结构/触发器变化和链断裂，但不能单独抵御
拥有本机管理权限的攻击者在服务完全停止后同时改写数据并重算未签名的本地链。若项目威胁
模型要求抵御本机管理员，还必须增加独立追加见证服务、离线签名检查点或 TPM/HSM 信任锚。

## 5. 试点与正式上线的边界

没有 Authenticode 代码签名证书时，必须从干净提交使用严格的
`-InternalUnsignedRelease` 构建，产物文件名含 `INTERNAL-UNSIGNED`，并按介质外摘要完成
执行前核验；这样可以进入受控内网正式运行。它仍不会让 Windows 显示“已验证的发布者”，
若单位策略禁止执行所有未签名 EXE，就只能修改单位策略或改用代码签名，软件不能绕过该策略。

若缺少远程访问所需的 HTTPS、现场审批材料、正式账号/双 HMAC、备份恢复或端到端验收，
则无论安装包是否有代码签名，都只能用于隔离兼容性验收或影子运行，并明确标注
“不得监管认定”。不得通过删除文件名中的 `UNSIGNED-TEST-ONLY`、改版本文字或只更换
账号来提升发行级别。

全部 P0、十量现场映射和恢复演练通过后，按
[十量 V3 部署与运行](十量V3部署与运行.md#6-正式上线门槛)完成多方签字，
才能把同一批已签名候选介质，或同一批已完成介质外摘要核验的
`INTERNAL-UNSIGNED` 候选介质，批准为该现场的正式生产版本。

# 企业模型凭据签发与轮换

> **历史设计，不用于当前 Windows 新部署。** 当前版本已取消 `.mgllm` 现场流程；
> 模型 API 由固定 `api_admin` 在企业端页面配置，Windows DPAPI 加密保存。
> 以 [Agent Windows 部署说明](../agent/deploy/windows/README.md) 为准。

本文说明 MineGuard 企业 Agent 正式环境如何取得、安装、轮换和吊销模型访问凭据。
目标是做到“一企业一 Key、一实例一授权、供应商可控、政府端不可见”，同时明确本机
管理员能够控制本机这一不可绕过的安全边界。

本文只使用占位符，不包含任何真实 API Key、私钥、口令或激活码。

## 1. 适用范围与结论

正式环境采用签名的企业专属 `.mgllm` 模型授权包：

1. MineGuard/模型运营方在隔离签发机上为每个企业申请一把独立的上游 API Key；
2. 签发机把企业身份、供应商地址、模型、能力、有效期和 API Key 加密绑定，并用
   Ed25519 私钥签名；
3. 企业通过两个独立渠道分别取得 `.mgllm` 和激活码文件；
4. 企业 Agent 验证发行版固定的签发公钥、企业实例身份和有效期后，生成本机 lock、
   secret store 与防回退状态；
5. 正式服务的普通环境文件只保存 lock/store 两个绝对路径，不保存 API Key、接口地址、
   模型参数或可替换的信任根；
6. 政府 Platform 不接收 `.mgllm`、激活码、API Key、lock、secret store 或防回退状态，
   也不需要访问模型供应商。

十量采集、人工复核、报送、验签和确定性风险工具不依赖模型授权。模型失效时，这些主线
能力仍可运行；依赖模型的对话、抽取或新闻检索按能力和错误状态降级。

## 2. 角色、材料和信任边界

| 材料 | 产生方 | 到达企业 | 到达政府 Platform | 保密要求 |
| --- | --- | --- | --- | --- |
| 模型供应商 API Key | 模型运营方 | 仅以受管 secret store 形式落地 | 否 | 每企业独立，最高等级 |
| Ed25519 签发私钥 | MineGuard 离线签发机 | 否 | 否 | 仅签发机，口令加密 |
| 签发公钥 trust store | MineGuard 发行构建 | 随签名 Agent 发行版 | 否 | 公共材料，但必须防替换 |
| 非秘密 profile | MineGuard 签发流程 | 通常不交付 | 否 | 可审计，不得包含 API Key |
| `.mgllm` | MineGuard 离线签发机 | 是，渠道 A | 否 | 内含密文，仍按敏感材料管理 |
| 激活码文件 | MineGuard 离线签发机 | 是，渠道 B | 否 | 必须与 `.mgllm` 分开 |
| lock | 企业导入工具 | 是，本机实例目录 | 否 | 不含明文 API Key，防篡改 |
| secret store | 企业导入工具 | 是，本机实例目录 | 否 | Windows DPAPI 或 Linux `0600` |

`.mgllm` 与激活码任何一项单独泄露都不应足以恢复 API Key；两项同时泄露则应按 API Key
泄露处理。不要把二者放在同一个 U 盘目录、压缩包、邮件、即时通信会话或工单附件中。

模型凭据链与企业向政府报送使用的 `.mgprov`、HMAC 消息密钥、运输密钥完全分离。不要
互相复用 key、激活码、签发密钥或目录。

## 3. 本机管理员边界

加密授权包可以防止普通配置查看、误复制、前端读取和随意替换供应商配置，但不能在企业
完全控制的机器上对抗该机器的最高权限管理员：

- Windows 的 DPAPI LocalMachine 和实例 ACL 能阻止普通用户及离线复制到另一台机器后
  解密，但本机 Administrator、SYSTEM，或能控制服务进程/调试器的人，最终可能取得运行
  中的凭据；
- Linux 的当前兼容 secret store 依赖服务账号属主 `0600`，不是硬件密钥库；`root` 可读
  文件或检查进程；
- 加密 API Key 的目的不是宣称“企业永远无法看到”，而是禁止普通人员从 env、GUI、日志、
  命令行和配置包中直接复制，并阻止未经签名的自定义 Key/模型替换正式配置。

若商业模式要求即使企业管理员也不能取得上游厂商主 Key，应让 `.mgllm` 中保存每企业的
MineGuard Gateway 凭据，而不是供应商主 Key，并在网关侧实施短有效期令牌、mTLS/IP
白名单、模型白名单、请求签名、速率限制、用量上限和即时吊销。客户端加密与服务端控制
应同时使用，不能互相替代。

## 4. 签发机准备

离线签发工具是 `mineguard-model-issuer`。它只部署在 MineGuard/模型运营方控制的签发
工作站，不安装在政府 Platform 主机，也不交给普通企业用户。

签发账号和目录至少满足：

- 专用操作系统账号，磁盘加密，默认 `umask 077`；
- API Key 文件、私钥口令文件、上一版激活码文件以及签发私钥均由当前账号拥有，POSIX
  权限为 `0600`；
- secret 文件只含一项值，可有一个末尾换行，不得带 BOM、多行说明或 `KEY=` 前缀；
- 所有输入输出使用绝对路径；输出文件必须事先不存在，工具按 CreateNew 语义拒绝覆盖；
- API Key 和私钥口令不得写在命令参数、shell 历史、profile、环境变量、CI 日志或工单中；
- 正式签发建议断开普通办公网络，签发结果经审批后再进入交付区。

API Key 文件至少 16 字节；签发私钥口令至少 12 字节。应由批准的密码管理器或 HSM 辅助
流程写入文件，再核对属主与 `0600`，不要在本文命令中替换成真实 secret 文本。

可先检查命令面：

```bash
mineguard-model-issuer --help
mineguard-model-issuer issuer-init --help
mineguard-model-issuer profile-create --help
mineguard-model-issuer create --help
mineguard-model-issuer trust-check --help
mineguard-model-issuer trust-compose --help
```

## 5. 初始化模型签发方

每个签发 key ID 初始化一次：

```bash
mineguard-model-issuer issuer-init \
  --private-key-output /secure/mineguard-model-issuer/model-issuer-private.pem \
  --public-key-output /secure/mineguard-model-issuer/model-issuer-public.pem \
  --trust-store-output /secure/mineguard-model-issuer/model-credential-trust.json \
  --issuer-id mineguard-model-authority \
  --issuer-key-id model-ed25519-2026q3 \
  --issuer-key-epoch 1 \
  --passphrase-file /secure/mineguard-model-issuer/issuer-passphrase.secret
```

正式流程必须使用 `--passphrase-file`。工具虽然支持省略该参数后从终端隐藏输入，文件方式
更适合双人复核、备份恢复和避免误输；无论哪种方式，口令都不会成为命令行参数。

命令产生：

- 口令加密的 Ed25519 私钥；
- 公钥 PEM；
- 单一签发方的 `mineguard-model-issuer-trust-store-v1` trust store；
- 不含 secret 的 JSON 摘要和公钥 SHA-256 指纹。

随后校验 trust store：

```bash
mineguard-model-issuer trust-check \
  --trust-store /secure/mineguard-model-issuer/model-credential-trust.json
```

将 trust store 和经独立渠道核准的 SHA-256 交给 Agent 正式发行构建。正式 Agent 只信任
签名发行版 `release-metadata/model-credential-trust.json` 中的公钥；现场不得通过
`MINEGUARD_AGENT_MODEL_TRUST_STORE` 指向另一文件。签发私钥和口令绝不能进入源码仓库、
CI 变量、安装包、企业配置或政府端。

## 6. 为企业创建非秘密 profile

必须从该企业已验签的 provisioning 记录取得以下四项，逐字复制，不由现场人员猜测：

- `mine_id`：煤矿标识；
- `system_id`：企业 Agent 实例标识；
- `party_id`：经营主体标识，对应 Agent 的 `ENTERPRISE_OPERATOR_ID`；
- `pair_id`：已验签 `.mgprov` 中的 UUIDv4 配对标识。

首次签发可省略 `--credential-id`，工具会生成 UUIDv4 并在安全摘要中返回。必须把该值写入
授权台账；后续轮换沿用同一 credential ID。示例：

```bash
mineguard-model-issuer profile-create \
  --output /secure/model-issues/mine-001-v1.profile.json \
  --credential-version 1 \
  --mine-id <approved-mine-id> \
  --system-id <approved-agent-system-id> \
  --party-id <approved-operator-id> \
  --pair-id <approved-provisioning-pair-uuidv4> \
  --provider-id <approved-provider-id> \
  --base-url https://<approved-model-origin>/v1 \
  --model <approved-model-name> \
  --capability chat \
  --capability extraction \
  --capability coal-news-search \
  --timeout-seconds 20 \
  --max-retries 2 \
  --install-before 2026-09-01T00:00:00Z \
  --runtime-not-after 2027-09-01T00:00:00Z \
  --issuer-id mineguard-model-authority \
  --issuer-key-id model-ed25519-2026q3 \
  --issuer-key-epoch 1
```

时间必须是精确到秒的 UTC `Z` 时间，且签发时间早于 `install_before`，安装截止时间不晚于
`runtime_not_after`。只声明企业实际购买并批准的能力；当前可选值为 `chat`、`extraction`
和 `coal-news-search`。profile 不允许出现 `api_key` 或其他额外字段。

审批人至少复核企业四元身份、credential ID/version、供应商 HTTPS 地址、模型、能力、
安装窗口和运行截止时间。`base_url`、模型和能力会随签名锁定，现场不能在 env 中覆盖。

## 7. 首次签发 `.mgllm`

先在模型供应商或 MineGuard Gateway 为该企业创建独立 Key，并写入属主 `0600` 的专用
文件。不同企业、测试/生产、灾备实例均不得共用 Key。然后执行：

```bash
mineguard-model-issuer create \
  --profile /secure/model-issues/mine-001-v1.profile.json \
  --api-key-file /secure/model-secrets/mine-001-v1-api-key.secret \
  --issuer-private-key /secure/mineguard-model-issuer/model-issuer-private.pem \
  --issuer-trust-store /secure/mineguard-model-issuer/model-credential-trust.json \
  --issuer-passphrase-file /secure/mineguard-model-issuer/issuer-passphrase.secret \
  --bundle-output /secure/model-delivery-a/mine-001-v1.mgllm \
  --activation-output /secure/model-delivery-b/mine-001-v1.activation
```

工具会生成随机 256 位激活凭据，用 scrypt 派生 AES-256-GCM 密钥加密 payload，并对
保护头与密文做 Ed25519 签名。输出摘要包含 bundle/credential/version、企业身份、
provider、有效期、路径和公钥指纹，但不返回 API Key、激活码或私钥口令。
`--issuer-trust-store` 必须是准备嵌入正式发行版的批准文件；工具会拒绝 profile 的
issuer ID/key ID、公钥与当前签发私钥不一致，防止生成现场永远无法信任的包。

签发完成后进行四项检查：

1. `.mgllm` 与 `.activation` 是两个不同的普通文件，且未覆盖既有文件；
2. profile、命令历史、stdout/stderr 和审批记录中均没有 API Key 或激活码内容；
3. 摘要中的企业四元身份、credential ID/version、issuer key ID 和有效期与审批单一致；
4. `.mgllm` 和激活码分别进入渠道 A、渠道 B，API Key 原始文件留在签发密钥区，不交付。

## 8. 双通道交付

建议的交付方式如下：

- 渠道 A：签名发布介质、受控文件交换区或登记的加密 U 盘交付 `.mgllm`；
- 渠道 B：另一名人员、另一介质或独立的端到端加密通道交付 `.activation`；
- 在介质外传递文件名、企业标识、版本、SHA-256 和交接单号，接收人先核对再导入；
- 两个渠道的访问审批人、介质编号和交付时间进入授权台账；
- 导入成功后清理临时落地点和介质缓存，但按审计策略保留受控签发归档；
- 不向政府 Platform 上传任一文件，也不把激活码粘贴到企业前端。

如果任一文件错发，立即停止导入；如果两项可能同时泄露，先在上游吊销该企业 API Key，
再以新 Key 和递增版本重签，不能只重新发送同一份材料。

## 9. Windows 企业端导入

前置条件是企业接入包已成功导入、正式实例已创建、实例专用 Windows 服务及 ACL 已安装，
且当前 Agent 发行版包含正确的固定 trust store。

以本机管理员身份从开始菜单运行“MineGuard 模型授权导入向导”：

1. 选择已验签的企业实例；
2. 选择渠道 A 的本矿 `.mgllm`；
3. 选择渠道 B 的激活码文件；
4. 核对向导显示的矿井、经营主体、系统、版本、provider、模型和截止时间；
5. 点击导入，等待正式配置自检和服务健康检查完成。

向导不提供 API Key、`base_url`、模型、签发公钥或 trust store 编辑框。它固定使用签名安装
目录的 `release-metadata\model-credential-trust.json`，验证签名、激活解密、企业四元身份、
安装窗口和版本后，把 API Key 转换为 DPAPI LocalMachine 密文。实例 `agent.env` 最终只含：

```text
MINEGUARD_AGENT_MODEL_CREDENTIAL_LOCK_FILE=C:\ProgramData\MineGuard\EnterpriseAgent\instances\<instance>\config\model-credential-lock.json
MINEGUARD_AGENT_MODEL_CREDENTIAL_SECRET_STORE=C:\ProgramData\MineGuard\EnterpriseAgent\instances\<instance>\config\model-credentials.dpapi
```

lock 还固定派生同目录的 `model-credential-lock.state.json` 防回退水位文件；它不增加第三个
env 指针。导入和轮换会在逐实例事务锁下停止服务、准备新文件，并把 DPAPI store、防回退
state、lock 和 `agent.env` 四者作为同一发布/回滚事务，随后执行正式检查并恢复原运行状态；
三份凭据文件不一致或 state 不是由 lock 路径固定派生都会在发布前拒绝。失败时自动回滚，
回滚不完整则保持服务停止。不要手工编辑水位或复制 DPAPI 文件到另一台机器；灾备换机应
签发并导入新版本，同时吊销旧机器使用的上游 Key。

管理员自动化入口及故障恢复见
[Enterprise Agent Windows 部署说明](../agent/deploy/windows/README.md)。普通现场人员应优先
使用 GUI。

## 10. Linux 企业端导入

Linux 当前使用属主 `0600` 的 POSIX secret store 兼容方案。它不提供 DPAPI 等价的
机器绑定，因此必须使用实例专用服务账号、受控本地磁盘、最小 sudo、全盘加密和主机审计。

首次导入步骤：

1. 停止该实例服务；
2. 确认当前正式 env 中尚无两个模型凭据指针，也无任何明文模型变量；
3. 把 `.mgllm` 和激活码分别放入服务账号可读的临时受控目录，激活码属主为服务账号且
   权限 `0600`；
4. 以实例服务账号执行导入，输出直接使用不存在的版本化最终路径；
5. 把两个新路径同时写入服务 env，执行正式配置检查，再启动服务；
6. 查看不含 secret 的状态并清理临时交付文件。

示例命令中的路径和身份必须替换为该实例真实审批值：

```bash
sudo -u <agent-service-account> enterprise-agent \
  --env-file /etc/enterprise-agent/enterprise-agent.env \
  model-credential-import \
  --bundle /run/enterprise-agent-delivery/mine-001-v1.mgllm \
  --activation-code-file /run/enterprise-agent-secret/mine-001-v1.activation \
  --trust-store /opt/mineguard/enterprise-agent/release-metadata/model-credential-trust.json \
  --lock-output /var/lib/enterprise-agent/model-credential-v1.lock.json \
  --lock-env-path /var/lib/enterprise-agent/model-credential-v1.lock.json \
  --secret-store /var/lib/enterprise-agent/model-credential-v1.secret.json \
  --secret-store-env-path /var/lib/enterprise-agent/model-credential-v1.secret.json \
  --secret-protection posix-0600 \
  --expected-mine-id <approved-mine-id> \
  --expected-system-id <approved-agent-system-id> \
  --expected-party-id <approved-operator-id>
```

正式模式要求 `--trust-store` 精确等于当前发行版固定路径，不能另选公钥。导入结果采用
CreateNew，不会覆盖同名 lock/store，并从 `--lock-output` 固定派生并新建相邻的
`.state.json` 防回退状态；例如 `model-credential-v1.lock.json` 对应
`model-credential-v1.lock.state.json`。以 root 运行再把这些 `0600` 文件留给非 root 服务会
造成服务不可读，因此应直接以实例服务账号创建。

导入成功后，在受保护的服务环境文件中只增加：

```text
MINEGUARD_AGENT_MODEL_CREDENTIAL_LOCK_FILE=/var/lib/enterprise-agent/model-credential-v1.lock.json
MINEGUARD_AGENT_MODEL_CREDENTIAL_SECRET_STORE=/var/lib/enterprise-agent/model-credential-v1.secret.json
```

两项指针必须同时变更，且 lock/store/派生 state 三个文件必须作为同一停服发布单元，不得
写 `MINEGUARD_AGENT_MODEL_TRUST_STORE`。确认没有
`MINEGUARD_AGENT_API_KEY`、`MINEGUARD_AGENT_BASE_URL`、`MINEGUARD_AGENT_MODEL`、
重试参数或任何 `DEEPSEEK_*` 模型变量，然后执行：

```bash
sudo -u <agent-service-account> enterprise-agent \
  --env-file /etc/enterprise-agent/enterprise-agent.env \
  config-check --production

sudo -u <agent-service-account> enterprise-agent \
  --env-file /etc/enterprise-agent/enterprise-agent.env \
  model-credential-status
```

普通 `--env-file` 模式下，进程已有环境变量优先于文件。运维账号应清除遗留模型变量，避免
旧 shell 环境干扰检查。服务启动后不会热加载新凭据路径；导入或轮换均须重启。

## 11. API Key 轮换

建议在到期前预留发布、双通道交付和现场维护窗口。标准轮换顺序如下：

1. 在上游为同一企业创建一把全新的 Key，暂不吊销旧 Key；
2. 创建新 profile：沿用 `credential_id`、`mine_id/system_id/party_id/pair_id` 和
   `issuer_id`，把 `credential_version` 精确加一；
3. 用新 API Key、上一版 `.mgllm`、上一版激活码签发新包；工具会拒绝版本跳号、企业身份
   变化或复用同一 API Key；
4. 按双通道交付新 `.mgllm` 和新激活码；
5. 企业导入新版本并提供当前 lock，完成健康验证；
6. 确认新版本产生正常模型调用后，在上游吊销旧 Key；
7. 更新授权台账、额度监控和事件响应联系人。

轮换 profile 示例：

```bash
mineguard-model-issuer profile-create \
  --output /secure/model-issues/mine-001-v2.profile.json \
  --credential-id <same-credential-uuidv4> \
  --credential-version 2 \
  --mine-id <same-approved-mine-id> \
```

Linux 导入 v2 时使用新的版本化输出路径，并增加当前 lock：

```bash
sudo -u <agent-service-account> enterprise-agent \
  --env-file /etc/enterprise-agent/enterprise-agent.env \
  model-credential-import \
  --bundle /run/enterprise-agent-delivery/mine-001-v2.mgllm \
  --activation-code-file /run/enterprise-agent-secret/mine-001-v2.activation \
  --trust-store /opt/mineguard/enterprise-agent/release-metadata/model-credential-trust.json \
  --lock-output /var/lib/enterprise-agent/model-credential-v2.lock.json \
  --lock-env-path /var/lib/enterprise-agent/model-credential-v2.lock.json \
  --secret-store /var/lib/enterprise-agent/model-credential-v2.secret.json \
  --secret-store-env-path /var/lib/enterprise-agent/model-credential-v2.secret.json \
  --secret-protection posix-0600 \
  --expected-mine-id <approved-mine-id> \
  --expected-system-id <approved-agent-system-id> \
  --expected-party-id <approved-operator-id> \
  --current-lock /var/lib/enterprise-agent/model-credential-v1.lock.json
```

随后确认 v2 lock 旁的 `.state.json` 已随导入生成，再原子地把 env 中两个指针一起切到
v2，执行 `config-check --production`，再启动服务。lock、secret store 与 state 必须作为
一个变更单元备份和回滚；不能只恢复旧 lock/store 而留下较新的最高版本状态。保留 v1
的受控回滚材料直到 v2 验收结束；旧 API Key 一旦吊销，回滚到 v1 将不能恢复模型访问，
因此吊销时点必须由变更单明确。

签发 Ed25519 key 轮换不是现场换公钥。先用相同 `issuer_id`、新的 `issuer_key_id` 和严格
增加的 `--issuer-key-epoch` 执行 `issuer-init`，再由离线签发机把当前发行 trust store 与新 key 的单项 trust store
合成为 CreateNew 输出：

```bash
mineguard-model-issuer trust-compose \
  --input /secure/model-trust/current-release-trust.json \
  --input /secure/model-trust/new-key-only-trust.json \
  --output /secure/model-trust/issuer-rollover-overlap.json

mineguard-model-issuer trust-check \
  --trust-store /secure/model-trust/issuer-rollover-overlap.json
```

`--input` 至少重复两次；合并器会拒绝 issuer/key/fingerprint 冲突、同一 issuer 重用 key
epoch，并规范排序。把合并结果及
独立核准的 SHA-256 放入新的签名 Agent 发行版，先部署并验证该重叠发行版，再用新
`issuer_key_id` 和更高 `issuer_key_epoch` 签发；`create --issuer-trust-store` 此时指向已批准的重叠文件，轮换校验的
`--previous-trust-store` 也应能验证旧 key。正式现场仍不能选择自定义 trust store。所有
企业完成凭据轮换和观察期后，才可通过下一版签名发行物移除旧公钥；旧签发私钥退役按
密钥管理制度执行。

Windows 正式 runtime 安装器会把这条顺序做成升级安全门：在创建/adopt 目录、重写实例
ACL 或切换 runtime 与 `release-metadata/model-credential-trust.json` 之前，遍历全部现有
实例的活动模型 lock，并让候选 Agent 只用候选 trust 验证签名 envelope 与 lock 中的 issuer
绑定。预检不会打开 DPAPI secret store、不会解密或输出 API Key，也不会因
`runtime_not_after` 已过而阻止 runtime 升级。只要任一 lock 仍引用候选 trust 已删除的 key
ID/epoch/fingerprint，整个升级在旧安装未改动时失败。旧发行版尚无模型 trust、且实例没有
活动 lock/store 指针时可直接升级到带 trust 的新发行版。不要通过删除指针或 lock 绕过；
正确处置是先发布保留旧 key 的重叠 trust，轮换受影响企业凭据，再发布移除旧 key 的版本。

## 12. 配额、监控与吊销

每企业独立 Key 至少配置以下上游控制：

- 独立项目/子账号或 Gateway principal，不与其他企业、内部研发或政府端复用；
- 仅允许批准的模型和接口能力，禁止模型管理、文件管理、充值等无关权限；
- 每分钟请求数、并发数、日/月 token 和费用硬上限，并设置 50%/80%/100% 告警；
- 企业维度用量台账，记录 credential ID、版本、provider key ID、签发/安装/到期/吊销时间；
- 条件允许时设置企业出口 IP、mTLS、请求签名或 Gateway 设备绑定；
- 对异常地域、突增用量、连续认证失败、过期凭据调用和越权模型请求告警；
- API Key 只出现在上游密钥系统、签发机临时 `0600` 文件和企业受管 secret store。

`.mgllm` 是离线授权，不包含在线吊销列表。需要立即阻断时，最可靠措施是在模型供应商或
MineGuard Gateway 吊销该企业的上游 Key，并按需在出口防火墙阻断模型 origin。之后生成新
Key、新版本凭据并重新导入。仅删除企业端 `.mgllm` 交付文件不会吊销已经安装的 Key。

下列事件必须触发吊销或紧急轮换：

- `.mgllm` 和激活码可能同时泄露；
- 企业主机、管理员账号、服务账号或备份失陷；
- 上游账单/用量异常；
- 企业撤销授权、合同终止、主体或矿井实例变更；
- API Key 被误写入日志、env、截图、源码、工单或聊天；
- 灾备换机、`pair_id` 变化或重新做企业 provisioning；
- 签发私钥疑似泄露。此时还须停止该 issuer 的新签发并发布新的固定 trust store。

`runtime_not_after` 到达后 Agent 会拒绝继续使用凭据，但到期控制不能代替上游吊销；两者
都应配置。为了避免静默停服，应至少在到期前 30、14、7、1 天告警。

## 13. 常见失败与处置

| 现象 | 常见原因 | 处置 |
| --- | --- | --- |
| `trust store` 不匹配 | 包由未进入当前发行版的签发 key 签名 | 核对发行版和签发台账；不得现场换 trust store |
| 企业身份不一致 | `.mgllm` 属于另一矿、系统、主体或旧 `pair_id` | 停止导入，按当前 provisioning 身份重签 |
| 激活或认证解密失败 | 激活码与包不配对、文件损坏 | 核对双通道文件名/SHA-256；不要反复猜测 |
| 超过安装窗口 | `install_before` 已到 | 使用新窗口和新版本重新审批签发 |
| 运行已过期 | `runtime_not_after` 已到 | 轮换并检查到期告警流程 |
| 更新版本被拒绝 | 未精确加一、credential/subject/issuer 改变 | 从当前 lock 和签发台账重新生成 profile |
| 模型防回退状态失败 | lock/store 被单独恢复、state 缺失或三文件版本不一致 | 保持模型停用并恢复同一事务的三文件备份；无可信备份时先由供应商吊销旧 Key，再走受控重新初始化，禁止删除 state 后直接降级 |
| 更新要求换 Key | 新旧上游 API Key 相同 | 在上游创建真正的新企业 Key |
| 正式配置检查发现明文模型变量 | env 或进程继承了 API/URL/model/retry/`DEEPSEEK_*` | 删除全部明文变量，只保留 lock/store 指针 |
| 正式配置检查拒绝 trust override | 设置了 `MINEGUARD_AGENT_MODEL_TRUST_STORE` | 删除变量，使用发行版固定文件 |
| Windows runtime 升级在候选 trust 预检失败 | 至少一个活动 lock 仍由候选发行已删除的 issuer key 签名 | 保持旧安装；发布含新旧 key 的重叠 trust，完成逐企业凭据轮换后再移除旧 key |
| Linux 服务读不到 secret store | 以错误账号创建、属主或权限不对 | 停服后由实例服务账号重新导入，保持 `0600` |
| 输出文件已存在 | CreateNew 防覆盖生效 | 使用新版本化路径，绝不手工覆盖当前文件 |
| Windows 换机后 DPAPI 解密失败 | 密文绑定旧机器 | 上游换 Key并为新机重签/导入，不复制密文 |

错误输出和 `model-credential-status` 只应包含安全元数据。排障时禁止打印 secret store、激活
码、API Key 文件或解密后的请求头。

## 14. 上线与轮换检查表

签发侧：

- [ ] 企业使用独立上游 Key，额度、模型白名单和告警已设置；
- [ ] 企业四元身份来自已验签 provisioning 记录；
- [ ] credential ID/version、issuer ID/key ID 和有效期经双人复核；
- [ ] API Key、私钥口令、上一版激活码文件均为属主 `0600`；
- [ ] profile、命令行、日志和返回摘要中没有 secret；
- [ ] trust store 指纹与正式发行审批值一致；
- [ ] `.mgllm` 与激活码通过两个独立渠道交付。

企业侧：

- [ ] 已完成企业接入包导入，mine/system/party/pair 身份有效；
- [ ] 当前签名发行版包含批准的固定 trust store；
- [ ] Windows 使用管理员 GUI，Linux 使用实例服务账号 CLI；
- [ ] 正式 env 仅新增成对的 lock/store 绝对路径；
- [ ] lock 旁的派生 `.state.json` 存在，并与 lock/store 一起纳入事务备份；
- [ ] env 中没有 API Key、provider/model/retry 或 trust-store override；
- [ ] `config-check --production` 和 `model-credential-status` 通过；
- [ ] 服务重启后模型能力健康，十量主线在模型不可用时仍能运行；
- [ ] 临时交付文件已按审批策略清理，审计台账已更新。

轮换/吊销：

- [ ] 新版本严格加一并使用新的上游 Key；
- [ ] 新版本安装验证完成后再吊销旧 Key；
- [ ] 旧 Key 吊销、额度和告警状态已在上游确认；
- [ ] 回滚窗口、旧材料保留期和最终销毁由变更单记录；
- [ ] 泄露事件已检查其他企业 Key，未发生跨企业复用。

# 五量监管 V2 验收清单

本清单用于开发发布、单矿试点和正式上线验收。验收对象严格限定为：

- 每座煤矿各自独立部署的 `agent/`；
- 政府集中部署的 `platform/`；
- 双方独立实现、由 `contracts/` 定义的 V2 交换边界。

`contracts/` 不是服务；独立 `edge-agent` 不是当前产品。带业务写入和故障注入的项目
必须在隔离环境使用合成数据执行。任一 P0 项失败，不得签署上线结论。

Windows 原生上线还必须先完成 [Windows 原生部署与运维](Windows原生部署与运维.md#13-上线验收清单)
中的 Python x64/时区、PowerShell 5.1、NTFS ACL、WinSW、回环端口、HTTPS、W32Time
和备份恢复门槛。本清单中的 Bash 命令在 Windows 上由仓库
`.github/workflows/windows-native.yml` 所列的双虚拟环境命令执行等价验证。

## 2. P0 发布门

- [ ] Platform 不 import `enterprise_agent`。
- [ ] Agent 不 import `mineguard`。
- [ ] 任一产品运行时不 import `contracts` 作为 Python 包。
- [ ] 默认生产入口只有 `platform/` 和 `agent/`；没有第三个 edge 服务。
- [ ] 政府 `mineguard` 入口只公开 `serve`、隔离演示数据命令 `seed-v2-demo`、

- [ ] Python 编译、全量测试、Ruff、前端语法和 `git diff --check` 通过。
- [ ] `seed-v2-demo` 仅写入空目录或自身拥有的演示目录；8 座教学矿标注程序合成，

### 2.2 两产品和身份隔离

- [ ] 一个 Agent 进程固定一个 `mine_id`、一个经营主体和一个 `sender_id`。
- [ ] 不同矿使用不同 Agent 数据库、状态目录、账号、监听目录、cursor 和密钥。
- [ ] 政府注册表中 `sender_id` 与 `mine_id` 都是唯一绑定，拒绝 `*` 和一实例多矿。
- [ ] HTTP sender、消息 sender、party、payload mine、路径资源和关联报告逐层一致。
- [ ] Agent A 不能读取、确认、回复或推测 Agent B 的报告和存在性。
- [ ] Agent 与 Platform 不共享 DB、文件目录、Cookie 或账号。
- [ ] 政府无需主动连接矿区内网；企业端仅出站访问政府 HTTPS。

| 隔离用例 | 预期 |
|---|---|
| A 身份上报 A 矿 | 接收并只分析一次 |
| A 身份在 payload 填 B 矿 | 拒绝，不产生业务分析 |
| A 拉取 B 的 `report_id` | 404 或不泄露式拒绝 |
| A 对 B 的报告发 ack/response | 拒绝并留安全审计 |
| 未登记 sender 或错误 key ID | 认证失败，不泄露注册信息 |

## 4. 采集与规范化

### 4.1 两种来源同等合法

- [ ] 人工导入和直采都能生成同一 V2 规范草稿。
- [ ] `acquisition_mode` 只用于来源追溯。
- [ ] 相同数值、口径和上下文仅改变 `acquisition_mode` 时，算法权重、阈值和结果不变。
- [ ] 页面和报告不出现“人工来源=较低信任”或类似分级。
- [ ] 两种来源都必须经过字段校验和企业人工确认后才能发送。

### 4.2 文件和字段

- [ ] 支持 ET/XLS/XLSX/CSV/JSON/JSONL 中已批准的格式。
- [ ] 文件摘要、大小、导入时间、解析结果和原字段位置可追溯。
- [ ] 保存日报合计和零点、八点、四点三班，不只保留一个企业选定值。
- [ ] 五量业务口径固定为风量、电量、火工品量、入井人员量和产量。
- [ ] 六个规范原子字段完整表达上述五量；雷管数量与炸药质量归属同一火工品量，
      不得在界面、报告或接口说明中误称为两个独立“量”。
- [ ] 固定单位分别为 m³/min、kWh、count、kg、person、t；不同量纲的火工品子项
      不得直接相加。
- [ ] `mine_entry_persons` 只接收统计范围内实际入井人次，必须为整数并按 `sum`
      聚合；不得填入泛用工、在册/排班人数或时点井下人数。
- [ ] 缺失为 `null + 原因`，不以 0、估算、平滑或模型生成值代替。
- [ ] 模型或规则只能给出映射建议；人工确认前不得静默改写事实。
- [ ] 确认后修改必须产生更高修订，旧版本不可覆盖。

### 4.3 固定目录和受控直采

- [ ] 只扫描配置白名单中的普通文件，不递归、不跟随符号链接。
- [ ] 半写文件在大小和 mtime 稳定前不读取。
- [ ] 相同 SHA-256 重扫不生成重复草稿；同名不同内容形成新记录而非覆盖。
- [ ] 解析失败复制到 Agent 状态目录的 quarantine，来源原件不删除、不移动、不写回。
- [ ] 文件、表、行列、压缩和单元格限制生效，恶意文件不能拖垮服务。
- [ ] 设备/API 连接器使用固定 allowlist、origin/path、CA、凭据、超时和响应上限。
- [ ] 不存在由普通用户输入任意 URL 的抓取能力。
- [ ] 路径、原件、设备凭据和 HMAC 不进入模型 prompt 或普通日志。

## 5. V2 报文、签名与血缘

- [ ] 七条交换路径与 OpenAPI 完全一致。
- [ ] 应用消息与 HTTP 运输使用不同签名域和内容不同的两把密钥。
- [ ] 两把密钥都至少 32 字节；不同矿不复用。
- [ ] 实际收到的原始 body 做摘要和验签，不经对象重序列化后代替原文验签。
- [ ] GET 的原始 path/query 和空 body 摘要进入运输签名。
- [ ] 篡改 body、path、query、sender、key ID、时间、nonce 或签名均被拒绝。
- [ ] 同 nonce 重放在重启后仍拒绝；过期和未来超窗时间戳拒绝。
- [ ] 相同 `message_id + idempotency_key + body` 重试返回同一业务效果。
- [ ] 相同幂等键配不同 body 返回 409，且原记录不变并留安全审计。
- [ ] 初始消息 correlation 自洽、无 predecessor；修订严格 `revision + 1`。
- [ ] 修订 predecessor 指向直接前版 message ID 和 payload SHA-256。
- [ ] ack/response causation 只能指向所属矿已发出的准确报告。
- [ ] 更正报表必须是触发报告原报表的严格后代，不能拿原版本冒充更正。
- [ ] Platform 响应使用 `application/problem+json`、稳定错误码和 trace ID。

密钥轮换验收：

- [ ] 政府消息 `message_keys` 同时接受新旧 key ID 的重叠窗口通过。
- [ ] 运输 `transport_secrets` 新旧重叠窗口通过。
- [ ] Agent 可用当前和上一把政府应用签名密钥验收报告。
- [ ] 切换发送密钥前先扩展验签集合；存量 outbox 清空后才删除旧密钥。
- [ ] 相同的应用消息密钥和运输密钥会导致启动失败。

## 6. 唯一算法验收

- [ ] 对外只有 `mineguard-five-quantity-engine`；前端和企业不能选择内部算法模块。
- [ ] 日报—班次、非负、日期、单位和完整性确定性核对正确。
- [ ] 风量按班次实际持续时间加权；电量、雷管、炸药、实际入井人次和产量等可加
      原子字段按班次求和，但雷管与炸药之间不得跨单位相加。
- [ ] 停产、检修、复产爬坡和稳产状态连续识别。
- [ ] 本矿历史采用同工况、合格基线和稳健 Median/MAD，不被单个极值主导。
- [ ] 既有连续异常、漂移、SSE/BIC 变化点等时序能力仍在同一引擎内。
- [ ] HiGHS 加权 L1 仅求满足硬约束且接近软区间的最小标准化调整。
- [ ] MCS 定位最少应复核的日期、指标和冲突组，不单独认定违法、责任或真实产量。
- [ ] 求解器失败或数据不足时显式降级，不伪装正常。
- [ ] `acquisition_mode` 不参与算法权重、阈值、配置摘要差异或结论。
- [ ] 分析结论与基线准入分离；暂未发现风险不等于自动进入历史基线。
- [ ] 风险、数据不足、缺完整日期、求解失败或有复核级信号的数据不进入正常基线。
- [ ] 首期仅凭本期整体分布不能自证并进入正式基线；无独立历史/冻结匿名 peer 锚点时只进入隔离参考候选。
- [ ] 匿名 peer 快照有截止日、内容哈希且同报告期冻结，同期煤矿先到后到不改变结果。
- [ ] 相同 input/config/history/peer snapshot 重跑得到相同结论和摘要。

至少执行下列固定合成集：

| 数据集 | 预期 |
|---|---|
| 完整、日报班次一致、稳定且历史充分 | `normal_candidate` |
| 日报与三班显著冲突 | `risk`，定位日期和指标 |
| 核心日期、单位或必需值缺失 | 对外 `data_insufficient` |
| 同一数据只切换人工/直采来源 | 数值分析结果完全一致 |
| 多日缓慢偏移 | 时序漂移证据出现 |
| 明显结构变化 | 变化点证据出现 |

## 7. 历史和跨矿分析

- [ ] 每矿历史只读取本矿已准入记录，不混入其他矿原始数据。
- [ ] 正常结论和历史基线准入是两个可追溯状态。
- [ ] 基线至少要求 14 个完整日、求解/MCS 成功、无复核级/风险级信号且具独立锚点。
- [ ] 基线准入/拒绝均追加留痕，不能靠改表回写。
- [ ] 同类矿按产能带、开采工艺、班制、煤种和工况五个治理维度匹配。
- [ ] 至少三座可比矿才形成匿名区间，每座矿等权，避免大矿用日期数支配结果。
- [ ] 样本不足时显式不使用 peer band，不从少量矿反推出他矿数据。
- [ ] 企业报告不泄露其他矿名称、ID、单日值或可识别组合。
- [ ] 跨辖区共同变化不会简单记作某一矿独有异常。
- [ ] 多矿综合只增加匿名证据，不改变任何矿的原始事实。

仅凭五量不得宣称完成运输、购销、收货、地磅或资金流的物理闭环核验。

## 8. 主业务状态机

### 8.1 接收和正常候选

- [ ] 企业确认后形成不可变 `five_quantity_submission` 并进入持久 outbox。
- [ ] 接收回执只表示已受理，`regulatory_outcome=not_determined_at_intake`。
- [ ] 每份有效报送恰好生成一个 run 和一份不可变分析报告。
- [ ] 报告包含引擎版本、输入/配置/历史/同类矿快照摘要和真实开始完成时间。
- [ ] `normal_candidate` 不生成虚构 finding。
- [ ] Agent 先持久保存报告 inbox，再发送 delivery ack，成功后才推进 cursor。

### 8.2 风险、解释和回复

- [ ] `risk` finding 包含日期、指标、事实、严重度和可解释依据。
- [ ] `data_insufficient` 清楚列出缺项，不冒充风险已消失或数据为零。
- [ ] delivery ack 只表示 Agent 已持久化报告，不代表企业接受结论。
- [ ] 风险对话严格绑定本矿 `report_id/finding_id`，不读取其他矿资料。
- [ ] 模型只能生成原因、追问、证据索引和措施草稿，不能自动确认或发送。
- [ ] 企业具名人员确认后才形成 `enterprise_risk_response`。
- [ ] 政府回复回执为 `explanation_recorded`，不表示风险解除。
- [ ] 解释、承诺、附件或送达状态都不能单独把 finding 改为已清除。

### 8.3 更正复算

- [ ] 更正是严格高修订、完整签名血缘和不可变新 input snapshot。
- [ ] 更正仍调用相同的版本化唯一算法，不能绕过时序或求解器。
- [ ] 更正仍异常时保持风险，不因已经解释而关闭。
- [ ] 只有更正版本通过同一算法，原风险才追加 `cleared_by_reanalysis`。
- [ ] 旧报表、run、报告、finding、回复和状态迁移全部保留。

## 9. 崩溃恢复和可靠投递

以下位置逐一故障注入：

1. Agent 固化消息后、发 HTTP 前；
2. Platform 入库后、HTTP 响应前；
3. Platform 生成报告后、Agent 拉取前；
4. Agent inbox 入库后、delivery ack 前；
5. Platform 记录回复后、回复回执前。

每次恢复均需满足：

- [ ] 原 message ID、idempotency key 和签名 body 不变；
- [ ] 只有一份业务记录、一个分析效果和一个报告，可重复读取原回执；
- [ ] Agent outbox/inbox 在重启后继续，cursor 不丢失、不跳过；
- [ ] 同一矿同时只有一个分析执行，竞争请求受控重试而不重复运行；
- [ ] A 矿的网络或分析故障不阻塞 B、C 矿。

## 10. 留痕、数据库与备份

- [ ] 原始交换 body、摘要、验签、接收、分析、报告、ack、回复和重算均追加保存。
- [ ] run 保存 input/history/peer/config SHA-256 和算法版本。
- [ ] 核心 V2 记录通过触发器或等效机制禁止 UPDATE/DELETE。
- [ ] 审计链可从头验证到最新事件；直接改表能被发现。
- [ ] 技术留痕不等于历史基线准入。
- [ ] 政府 `mineguard backup` 产生一致性备份，`verify-backup` 验证通过。
- [ ] `restore-backup` 只恢复到不存在或为空的新目录，不覆盖在线状态。
- [ ] `backup.key` 与业务备份分离保管。
- [ ] Agent 停机一致性备份或经验证的 SQLite backup API 覆盖 DB、outbox/inbox、
  cursor、回复、审计和 quarantine。
- [ ] 恢复后继续发送原 outbox，不重复分析；记录实测 RPO/RTO。

恢复演练命令以 [V2 部署与运行](V2部署与运行.md#10-数据备份与恢复) 为准。

## 11. 安全和模型边界

- [ ] 两端仅回环监听，由 HTTPS 反向代理对外提供服务。
- [ ] 代理不改写签名 path/query/body，不缓存鉴权响应，不记录秘密。
- [ ] Agent 拒绝任何 HTTP 重定向；远程 Platform 地址必须 HTTPS。
- [ ] 私有 CA、证书有效期、NTP 和磁盘余量均受监控。
- [ ] 文件、JSON、Excel、风险报告和模型输出都按不可信输入处理并有硬上限。
- [ ] LLM 不接触 HMAC、Cookie、密码、设备凭据、其他矿数据或政府内部算法配置。
- [ ] 未配置/不可用 LLM 时，导入、校验、报送、监管分析、收件和人工回复仍可用。
- [ ] 模型不得编造企业事实、证据、监管认定或提交动作。
- [ ] 页面动态文本安全渲染，无 HTML/脚本注入。
- [ ] 日志可用 request/message/run ID 关联，但不含完整 payload 和秘密。

## 12. 现场数据与上线签字

自动测试不证明现场数据真实。正式上线还必须完成：

- [ ] 各矿五量对应的六个规范原子字段、日期、日报/班次、时区和单位与真实上游
      一一映射并由业务人员签字；签字材料明确六原子字段不等于六量。
- [ ] 固定目录或设备 API 只读权限、文件完成标志和异常隔离经过现场联调。

# MineGuard 十量 V3 部署与运行

本文是当前正式主线的部署、字段和 CSV 使用入口。新建草稿、企业确认、政府接收和
算法报告统一使用 `ten-quantity-submission-v3`、`analysis-report-v3` 与
`/v3/ten-quantity-submissions`。五量 V2 只用于读取、验签和审计既有历史报文；不得
从 V2 历史记录补造 V3 新字段，也不得把 V2 草稿重新确认成正式 V3 报文。

## 1. 两套软件与边界

```text
每矿独立 enterprise-agent                     政府集中 mineguard platform
CSV/工作簿/固定目录/受控连接器
        → 确定性规范化 → 经办复核 → 负责人确认
        → 十量 V3 HTTPS + 双 HMAC ───────────→ 验签、幂等接收、唯一算法
                                                → 领导只读总览与风险钻取
        ← 报告拉取、送达确认、企业回复 ────────┘
```

- 一个 Agent 实例只能绑定一个煤矿和一个经营主体；每矿数据库、用户和密钥独立。
- Platform 集中保存多矿报文和分析，但领导账号只能查看授权范围，不能替企业改数。
- 两端不共享数据库、目录或 Python 运行时代码，只按中立 V3 合同交换 JSON。
- 自动采集只能生成待复核草稿，不能代替具名人员确认，也不能自动形成监管认定。

## 2. 十量与 11 个原子字段

“火工品量”必须同时保留雷管数量和炸药质量，两者单位不同、绝不能相加。因此业务上
是十量，报文中是以下 11 个原子字段：

| 业务量 | V3 原子字段 | 固定单位 | 日报聚合 | 班次要求与口径 |
| --- | --- | --- | --- | --- |
| 风量 | `ventilation_m3_min` | `m3/min` | `time_weighted_average` | 必填；统计窗时间加权平均 |
| 电量 | `electricity_kwh` | `kWh` | `sum` | 必填；窗口耗电量 |
| 火工品量（雷管） | `detonators_count` | `count` | `sum` | 必填；整数发数 |
| 火工品量（炸药） | `explosives_kg` | `kg` | `sum` | 必填；质量 |
| 入井人员量 | `mine_entry_persons` | `person` | `sum` | 必填；实际入井人次，不是在册人数 |
| 产量 | `production_t` | `t` | `sum` | 必填；企业生产报表产量 |
| 开采量 | `extraction_t` | `t` | `sum` | 必填；工作面/采掘计量，不能与产量混为一列 |
| 销售量 | `sales_t` | `t` | `sum` | 日合计必填；销售交付实物量 |
| 运输量 | `transport_t` | `t` | `sum` | 日合计必填；出矿/外运净吨数，不是矿内皮带量 |
| 洗煤量 | `wash_feed_t` | `t` | `sum` | 日合计必填；进入洗选环节的原煤量 |
| 开票量 | `invoiced_quantity_t` | `t` | `sum` | 日合计必填；本期正常/蓝字发票对应实物煤量 |

前七个原子字段需要日报和零点、八点、四点班数据；销售、运输、洗煤、开票以日报为
强制口径，班次可选。空白必须保持 `null + missing`，不能用 0 冒充缺失，也不能由
Agent 或模型猜测。

`invoiced_quantity_t` 必须为非负数，只记录本期正常/蓝字发票对应的实物吨数。红字
发票、退票、作废、折让和退货必须作为带原单引用、发生时间、原因与吨数的辅助明细
在企业来源系统独立留存；需要“净开票量”时由这些明细另行派生。当前 V3 主报文不
承载这些辅助事件，平台不会假装已经逐笔核验。不得把红票写成 V3 主字段的负数，也
不得把销售量、运输量和开票量简单相加或重复扣减。

当前 V3 主报文同样不承载期初/期末库存、洗后产品/矸石/损耗、在途批次及逐批开票
日期。因此平台本版只对 11 个主量执行确定性、同期间软关系、历史/同类矿和通用
L1/MCS 分析；高级原煤平衡、洗选物料平衡、逐批凭证账龄和窗口流网络会明确跳过。
这些能力只能通过后续独立版本的辅助证据合同启用，不能由模型或平台从主量猜测。

## 3. 最简单的 CSV 填报

企业端“数据收件箱”可直接下载日汇总模板。标准文件为 UTF-8 CSV，每行一天，共
12 列；保持下面表头不变最稳妥：

```csv
日期,风量(m3/min),电量(kWh),雷管(发),炸药(kg),入井人员量(人次),产量_企业报表(t),开采量_采掘计量(t),销售量(t),运输量(t),洗煤量_入洗原煤(t),开票量(t)
```

使用步骤：

1. 经办人下载模板或选择企业已有 CSV；日期使用 `YYYY-MM-DD`，数字单元格只填数值。
2. Agent 先预览日期、表头、单位和映射；陌生列由已批准映射、本地规则及可选模型给出
   建议，模型只接收表头和脱敏类型统计，不接收业务数值。
3. 经办人逐列确认或明确忽略，重复目标、歧义单位、非法数字和公式文本会被阻止或提示。
4. 生成待复核草稿后核对日报；需要时展开班次，补充前七个原子字段的三班明细。
5. 经办人保存后退出，由另一具名 `confirm + submit` 账号复核并确认入队。
6. 等待政府接收回执和分析报告；“已接收”不等于“无风险”或“监管认可”。

已有 ET/XLS/XLSX/JSON/JSONL 也可导入。自动识别只产生建议，不改变原始文件、不做
插值；自动目录和连接器同样只能生成草稿。旧五量 CSV 可导入作历史复核，但缺少的
开采、销售、运输、洗煤和开票字段保持空缺，不能据此形成新 V3 正式报送。

## 4. 本机联调

需要 Python 3.11+。先启动政府端：

```bash
cd /home/sevan/coral/platform
python3 -m venv .venv
. .venv/bin/activate
python3 -m pip install -c constraints.txt -e .
mineguard demo
```

浏览器打开 <http://127.0.0.1:8080/>。演示账号是 `admin / 123123123`，只允许本机
展示。演示种子中既有五量 V2 历史样表时，页面会明确标成 Legacy，不会伪造五个新增
业务字段。

另开终端启动单矿企业端：

```bash
cd /home/sevan/coral/agent
python3 -m venv .venv
. .venv/bin/activate
python3 -m pip install -e .
enterprise-agent serve --host 127.0.0.1 --port 8090
```

浏览器打开 <http://127.0.0.1:8090/>。未配置正式用户时，`demo / 123123123` 只能
体验查看和编辑，不能确认或报送。命令持续占用终端表示服务正在等待请求，不是卡死。

## 5. Agent 连接正式 Platform

生产推荐使用 V3 变量名；程序暂时接受 `PLATFORM_V2_*` 作为迁移别名，但新部署不要
继续复制旧名。每矿至少配置：

```text
ENTERPRISE_MINE_ID=MINE-QY-001
ENTERPRISE_MINE_NAME=示例一号煤矿
ENTERPRISE_OPERATOR_ID=operator-qy-001
ENTERPRISE_OPERATOR_NAME=示例一号煤业有限公司
ENTERPRISE_SYSTEM_ID=agent-mine-qy-001

PLATFORM_V3_BASE_URL=https://regulator.example
PLATFORM_V3_SENDER_ID=agent-mine-qy-001
ENTERPRISE_EXCHANGE_KEY_ID=enterprise-key-v3
REGULATORY_EXCHANGE_KEY_ID=regulator-key-v3
ENTERPRISE_EXCHANGE_HMAC_SECRET=<应用消息高熵密钥>
PLATFORM_V3_TRANSPORT_HMAC_SECRET=<另一把运输高熵密钥>
PLATFORM_V3_CA_BUNDLE=/etc/enterprise-agent/regulatory-ca.pem
```

`PLATFORM_V3_SENDER_ID` 必须等于 `ENTERPRISE_SYSTEM_ID`。两把 HMAC 密钥必须不同，
均不得写入仓库、CSV、前端或日志。远程地址必须是 HTTPS origin；客户端拒绝重定向。
当前正式提交入口是：

```text
POST /v3/ten-quantity-submissions
```

报告拉取、报告详情、送达确认、企业回复及回复回执也使用 `/v3/` 路径。企业网页自身
仍使用 `/api/v2/*` 作为本机浏览器 API；这只是稳定的前端路由名，不代表它发送五量
V2 报文。

政府侧客户端注册配置当前仍沿用 `MINEGUARD_V2_CLIENTS_FILE/JSON` 这一稳定运维变量
名；其注册内容同时用于验证 V3 客户身份和双 HMAC。变量名保留不表示接收接口仍是 V2，
是否正式就绪应以 `/readyz`、实际 V3 联调和审计结果共同判断。

## 6. 正式上线门槛

仅停用 demo 账号不等于正式版。上线前至少完成：

- 逐矿唯一身份、经营主体、同类矿分组和两把独立密钥双人核对；
- 企业 `production mode + four eyes`，经办 `read/write` 与复核
  `read/confirm/submit` 分离；
- HTTPS、私有 CA、NTP、反向代理请求限制和访问控制；
- 十量字段口径、单位、班次、上游来源与开票辅助明细由业务人员签字确认；
- 自动采集至少一个完整结算周期影子运行，缺失、跨月、红票/退票和停复产场景通过；
- Agent 与 Platform 分开备份并完成恢复演练、全链审计校验和 V3 端到端重放；
- 旧 V2 数据保持只读，迁移过程中不更新原报文、签名、哈希或算法结论。

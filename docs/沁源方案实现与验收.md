# 沁源县决策式 AI 智能体辅助监测平台：一期实施与验收手册

> 依据：[《沁源县决策式AI智能体辅助监测平台建设方案》](../沁源县决策式AI智能体辅助监测平台建设方案.docx)<br>
> 代码基线：本仓库 2026-07-28 工作区<br>
> 适用范围：试点矿井的一期建设、影子运行、现场联调和验收<br>
> 安全定位：系统只形成辅助监管技术线索，绝不执行断电、复电、停产、复产、风机控制、撤人或其他生产控制。

## 1. 当前结论和验收口径

当前仓库已经形成三套代码独立的服务：

1. 县级监管平台 `platform/`；
2. 企业可信填报智能体 `agent/`；
3. 矿端只读边缘智能体 `edge-agent/`。

安全规则核心、生产多源交叉验证、吨煤电耗/炸药核验算法、企业填报、监管接收、
PC 安全工作台、预警台账和办理动作已经有代码及自动测试。它们构成可继续现场
建设的试点底座，但**截至本基线不能直接按原方案宣布一期生产验收通过**。

正式试点前至少必须关闭以下阻断项：

1. 完成人员定位、安全监测、主通风机、产量监测、市能源局用电和公安火工品的
   现场字段映射与只读接口联调；仓库里的通用 JSONL、目录投递、HTTP GET
   适配器不等同于厂商系统已经接入。
2. 由安全、通风、机电、生产和法规人员审批每矿规则快照、点位、核定人数、
   风量基准、去抖策略和处置时限；仓库默认参数只能用于回放和联调。
3. 完成主通风机 `running/fault/changeover` 三项二值指标与现场 PLC/厂商系统的
   只读映射，审批点位、状态语义和倒机业务规则；标准契约和平台独立复算已有，
   但不能用测试数据代替现场联调。
4. 如果严格执行原方案第一阶段范围，还必须提供经主管单位确认来源、坐标系和
   精度的真实 GIS/测绘数据，对接具体短信、企微或政务消息网关，并明确原生
   手机 APP 是否可由当前可安装 PWA 替代。当前代码已有跨矿偏差热力图、可选
   GeoJSON 边界、账号级责任路由/已读/备岗升级、附件反馈和 PWA；但通用
   webhook 的 HTTP 2xx 只证明网关接收，不能冒充短信到达或自然人已读。若将
   原生 APP、真实消息渠道或正式 GIS 延期，须形成范围变更单。

`edge-telemetry-batch-v1` 报文、HMAC 和两个真实进程的黑盒互通已经在当前代码
基线通过；现场发布仍须用正式制品、正式密钥和实际网络重复执行第 7.4、9.2 节
验收。

本手册使用以下状态：

| 标记 | 含义 |
|---|---|
| `I` | 代码已经实现，且有自动测试覆盖；仍需按本手册做部署验收 |
| `S` | 必须进行现场系统接入、数据映射或真实网络联调 |
| `R` | 规则、阈值、责任人、时限或数据口径必须经主管单位审批 |
| `B` | 当前阻断项；未关闭前不得声明相应能力通过验收 |
| `P2` | 原方案第二阶段或明确建议在历史数据积累后上线 |
| `P3` | 原方案第三阶段全县推广项 |

“自动测试通过”只证明代码行为符合测试样例，不证明现场来源真实、规则合法、
网络可用、消息送达或模型在某座矿井达到业务效果。

## 2. 三方架构和权责边界

```text
人员定位 / 安监 / 通风机 / 电表 / 产量等既有系统
                    │ 只读
                    ▼
              edge-agent
       归一化、留存、断网续传、本地提示
                    │ HTTPS + edge-telemetry-batch-v1 + HMAC
                    ▼
                platform
   独立验签、原始归集、独立复算、模型、预警台账、监管办理
                    ▲
                    │ HTTPS + enterprise-submission-v1 + HMAC
                    │
                 agent
      企业导入、追问、预检、人工确认、可信报送
```

### 2.1 县级监管平台

监管平台拥有最终的接入信任边界和监管规则：

- 独立登记矿井、企业客户端、边缘客户端、来源、指标、单位和权限；
- 验证传输 HMAC、时间、nonce、客户端矿井范围、批次幂等和原始摘要；
- 保存边缘原始观测、本地预警提示和平台独立复算结果；
- 使用自己批准的规则版本重新计算安全线索，不能直接采信矿端预警等级；
- 执行物理关系、历史、时序、电耗和炸药等分析；
- 管理预警的已阅、分派、办理、复核、关闭、重开和追加式审计；
- 根据账号角色和矿井数据域限制查看、配置和处置权限；
- 只输出技术核查线索，不由算法作出违法、责任或处罚认定。

### 2.2 企业可信填报智能体

企业智能体负责企业侧数据准备，不是监管判断主体，也不是矿井设备控制器：

- 导入 JSON/CSV 等来源数据，保留字段级来源和内容摘要；
- 对缺项、单位、时间窗口、数值范围和多维关系进行提示；
- LLM/OCR 只能提出建议，不能发明、补齐、平滑或修改事实数字；
- 修改来源签名覆盖的业务字段会使签名失效；
- 必须由有权限的企业账号完成逐项核对、确认和提交；
- 只能在人工确认后通过 `enterprise-submission-v1` 向监管平台报送；
- 不持有设备来源签名密钥，不替监管平台验真；
- 不连接或控制井下生产系统。

原方案把“人工填报入口”描述在矿端智能体内。本实现将其拆成独立 `agent/`，
使企业责任、设备采集和监管判断相互隔离。这是功能等价但边界更清楚的实现。
验收时应分别验证企业填报链和矿端自动采集链，不能用其中一条替代另一条。

### 2.3 矿端边缘智能体

边缘智能体只承担现场只读采集和可恢复上报：

- 支持 JSONL、只读目录投递和 HTTP GET 轮询适配器；
- 归一化时间、单位、矿井、点位、来源和修订号；
- 使用 SQLite 原子保存观测、提示和待发队列；
- 重复数据幂等，修订保留，断网指数退避，成功后仍保留审计记录；
- 人工补录必须记录操作人、原因和凭证，不能伪装成自动采集；
- 可在矿端形成低延迟本地提示，但监管端必须独立复算；
- 没有设备写接口，拒绝 `PUT/PATCH/DELETE`，不提供风机或生产控制路由。

通用适配器只是接入框架。OPC UA、Modbus、MQTT、厂商数据库、专有 WebService
等协议必须按现场系统另做只读适配器，并由矿方和厂商确认不会影响既有系统。

### 2.4 代码独立要求

三套服务不得：

- 互相 import Python 包或共享 ORM/数据库文件；
- 读取对方内部状态目录；
- 让企业端或边缘端覆盖监管端规则、容差、来源可靠性或结论；
- 将平台、LLM、设备和运输密钥混用。

允许共享的只有版本化、可复制的中立契约文件和固定测试向量。运行时双方各自
实现契约，通过 HTTP 互操作。架构边界测试必须保留在三套测试集中。

## 3. 一期六类数据底座

原方案标题写“五星量”，正文又写“6 类核心数据以及通风辅助数据”，表 1 实际
列出六类。本手册以表 1 为准，将**出煤、用电、人员、甲烷、火工品、通风**
作为六类，不把通风遗漏或重复计数。

| 类别 | 监管标准指标/单位 | 计划频率 | 当前实现 | 一期仍需完成 |
|---|---|---:|---|---|
| 出煤 | `production.output_t`，t；皮带瞬时产量 t/h、速度 m/s、运行/故障 0/1 | 实时或日报 | `I` 总量和四项皮带细化指标已完成边缘归一化、V1 契约和监管接收；原有产运洗销存分析可继续使用 | `S/R` 产量监测厂商接口、班/日/月/年及累计口径和点位语义仍须现场映射、审批 |
| 用电 | 总电、生产分区电及通风/排水/压风/提升/选煤厂电量，kWh | 小时或日报 | `I` 契约指标和核验算法已具备 | `S` 市能源局接口/矿端电表；确认表计边界、倍率、分区和日界线；`R` 干扰项口径 |
| 人员 | 井下/区域人数 person；异常入井、无卡、人卡不符、超时 count | 不低于 5 分钟 | `I` 超员规则、平台复算、台账及四项聚合非 PII 细化指标已结构化 | `S/R` 人员定位与唯一性门禁、真实字段映射和异常定义待接待批；V1 不传姓名、卡号或轨迹明细 |
| 甲烷 | `methane.concentration_percent`，% | 不低于 5 分钟，异常加密 | `I` T1/T2/回风中部/总回风规则及状态机 | `S` 安监系统点位映射、设备状态和异常加密策略；`R` 每矿瓦斯类别和适用阈值 |
| 火工品 | 炸药领/用/余 kg，雷管领/用/余 count，使用地点 | 日报 | `I` 契约和炸药核验已有；边缘端已将雷管严格按 count 非负整数归一化并拒绝 kg/小数 | `S/R` 公安系统和企业日报、领退库、跨日库存及使用地点口径待接待批 |
| 通风 | 风量 m³/min、风压 Pa、风速 m/s；主通风机运行/故障/倒机二值状态 | 不低于 5 分钟，设备状态变化即时采集 | `I` 风量骤降、瓦斯联合算法和主通风机三项 V1 指标已具备；平台按监管规则独立复算停机/故障为红、倒机为黄 | `S/R` 现场 PLC/厂商接口、点位和 0/1 语义待映射；倒机窗口、维护旁路及处置规则待审批 |

三项 `source.*` 是独立的技术健康遥测，不计入六类业务数据：
`heartbeat_age_seconds`（秒）、`consecutive_failures`（整数）和
`missing_state`（0/1）。合同、两端模型和归一化已具备，并强制
`location_code == source_id`；多源调度器已按独立周期合成并经同一持久 outbox
上送，监管端对 `missing_state=1` 形成黄色数据质量技术预警，且只有同一来源
有效、时钟同步的恢复状态才能清除。健康观测与业务记录计数隔离，不能把调度器
仍在运行误当成来源已有业务数据。

### 3.1 每条观测的最低证据

自动观测至少应保留：

- `mine_id`、`source_id`、`observation_id`；
- 指标、值、统一单位和 `location_code`；
- 带时区观测时间、接收时间、序号、修订号；
- 可选统计窗口的起止、时区、聚合口径和班次编码；
- 自动/文件/轮询/认证人工等采集方式；
- 原来源记录标识和 SHA-256；
- 完整性、及时性、设备健康、时钟同步和阻断标记；
- 原值、原单位和必要的来源定位。

人工补录还必须有操作账号、操作时间、原因和凭证引用。缺失不能填零，未知单位
不能猜测，自动数据和人工数据不能覆盖成同一条无来源记录。

### 3.2 时间和采样验收

- 所有服务使用 UTC 存储和传输，页面按批准时区展示；
- 矿端、平台、反向代理和来源系统启用 NTP；
- 人员、甲烷、通风按原方案验证不低于每 5 分钟一次；
- 用电验证小时聚合及日报之间可重算；
- 出煤、火工品、电量日报必须使用同一统计日边界；
- 未来数据、迟到数据、低质量数据和来源异常必须明确隔离，不能把“无数据”
  展示成“正常”。
- 带 `interval` 的观测必须验证 `end > start` 且 `end <= received_at`；
  不带窗口的既有观测继续按原格式接收。

## 4. 安全四色规则和治理

### 4.1 当前规则核心

监管平台的默认规则快照为 `qinyuan-safety-2026.07-v2`，并对完整内容计算
SHA-256 指纹。规则输入、状态和输出使用严格、不可变模型；跨批状态携带同一
规则版本和指纹，版本不同的状态不能静默混用。

当前已实现：

- 人员达到核定人数 80% 为蓝、90% 为黄、100% 为橙；
- 低/高瓦斯矿井按 T1、T2、高瓦斯回风巷中部和总回风点位差异化判断；
- 高瓦斯回风巷 0.75% 趋势提示；
- 甲烷相邻有效读数变化**超过** 0.2 个百分点形成重大变化线索；
- 风量相对上一有效值骤降**超过** 15% 形成线索；
- 风量下降且批准时间窗内甲烷同步上升时上调一级；
- 主通风机 `running=0` 或 `fault=1` 形成红色线索，
  `changeover=1` 形成黄色线索；
- 甲烷持续超限、严重风量下降、去抖、降级、清除和复电条件提示；
- 数据时效、质量、来源、顺序和未来时间门禁；
- 所有结果固定为 `technical_warning_clue`、`advisory_only=true`、
  `production_control_permitted=false`。

### 4.2 甲烷基础边界

以下值来自原方案并已进入默认代码快照，但正式使用仍须根据生效的《煤矿安全
规程》、矿井类别、采掘布局和点位重新复核：

| 矿井/点位 | 趋势 | 报警 | 断电提示 | 复电条件提示 |
|---|---:|---:|---:|---:|
| 低瓦斯 T1 | — | ≥1.0% | ≥1.5% | <1.0% |
| 低瓦斯 T2 | — | ≥1.0% | ≥1.0% | <1.0% |
| 高瓦斯 T1 | — | ≥1.0% | ≥1.5% | <1.0% |
| 高瓦斯 T2 | ≥0.75% | ≥1.0% | ≥1.0% | <1.0% |
| 高瓦斯回风巷中部 | ≥0.75% | ≥1.0% | ≥1.0% | <1.0% |
| 各类矿井总回风 | — | ≥0.75% | — | — |

“断电提示”和“复电条件提示”只是提示人工执行法定流程。平台不连接控制回路，
也不授权任何人员绕过矿井原有安全监控系统。

### 4.3 必须审批的本地参数

原方案没有给出以下完整数值，因此代码默认值不能直接成为正式规则：

- “持续超限”需要连续多少个有效点；当前开发默认是 3；
- 激活、清除和降级分别需要多少个连续点；当前开发默认激活 1、清除 2；
- “严重通风异常”的数值边界；当前开发默认风量下降超过 30%；
- 通风—瓦斯联合时间窗；当前开发默认 300 秒；
- 蓝黄橙红各级办理期限；当前台账默认红 1 小时、橙 4 小时、黄 12 小时、
  蓝 24 小时；
- 每个点位的最低风量、核定人数、设备量程、采样频率、维护状态和替代数据策略；
- 主通风机每个 PLC 点位的 0/1 语义、故障和倒机保持时间、检修旁路及多机组合
  状态；
- 谁接收哪一级预警、谁可关闭、谁审批规则和谁负责复核。

审批产物至少包括规则版本、有效期、法规依据、适用矿井/点位、完整参数 JSON、
内容 SHA-256、起草/复核/批准人、批准时间、回放报告和回滚版本。

当前代码已具备规则治理后台和管理员页面：

- `POST /v1/admin/safety-rules` 登记 `proposal` 或 `draft`，同一版本不能静默
  替换成不同内容；
- 审批和退役动作必须同时提交预期 SHA-256 指纹和不少于规定长度的决定说明；
- 已批准规则的有效期不得相互重叠；
- 平台按决策时间选择已批准且处于有效期的快照，并保存版本、指纹、审批人和
  决定说明；
- 没有已批准规则时，内置方案仅用于辅助回放，结果同时产生
  `safety_rule_approval_required` 数据质量警告，不能伪装为正式规则结论。

内置 `qinyuan-safety-2026.07-v2` 初始状态是 `proposal`，不是已批准规则。
V2 增加主通风机策略字段，因此绝不沿用 V1 版本名或静默改写旧指纹；升级时若
发现缺少该字段的旧批准快照，平台保留记录但按“待审批”失败关闭，须先退役旧版
再按完整 V2 指纹审批。
现有动作由具有配置管理权限的账号执行，并有登录、CSRF、指纹和审计约束；它
不能替代线下法规复核、起草/复核/批准人员的职责分离、电子签章或有权单位审批
文件。当前也没有原子化的“一键回滚”：回滚须在受控变更窗内退役现行版本、
批准上一经复核版本并重新回放，具体见第 11.3 节。

### 4.4 矿端规则与监管规则

边缘端 `.env.example` 中的 0.5/0.8/1.0/1.5 等参数是演示参数，不是原方案完整
的分矿井、分点位规则。只要
`MINE_EDGE_THRESHOLDS_CALIBRATED=false`，页面就必须持续显示未校准警告。

矿端提示用于减少网络延迟，监管平台的最终技术线索必须依据原始观测和监管端
批准快照重新计算。验收不得把矿端 `local_alerts` 直接写入监管结论。

### 4.5 预警处置

当前监管端已支持：

- 预警创建、重复出现、升级、重新打开；
- 开放、已阅、办理中、已复核、已关闭状态；
- 分派、备注、复核、关闭和重开；
- 乐观版本冲突检查、逾期计算和追加式哈希事件链；
- 按角色和矿井范围读取与操作；
- PC 工作台的四色概览、矿井卡、实时指标、筛选和处置操作；
- 主通风机停机、故障和倒机的监管端独立预警；
- 跨矿生产核验偏差热力图，以及基于登记经纬度的相对位置示意；部署方可选
  提供经严格校验的 Polygon/MultiPolygon GeoJSON 边界；
- 可安装 PWA 外壳，移动端可查看态势、办理预警和上传核查附件；服务工作线程
  不缓存鉴权 API 或监管数据；
- 按矿井、预警类别和最低级别配置责任路由；全部匹配路由并行知会，最具体
  路由保持唯一主责，每一路由分别记录账号级已读并在未读超时后独立升级备岗；
  蓝黄橙红办理时限从平台生成正式预警起算，逾期只升级一次，重开后进入新周期；
- 平台安全复算的持久队列、退避重试、死信台账、运维列表和受控重算按钮；
- 可选的通用安全通知 webhook：HMAC 签名、级别下限过滤、持久化 outbox、
  逐目标独立状态与重试、失败终态、禁止重定向、管理员死信重试和按矿井权限
  查询投递状态。
- 安全预警核查附件：按矿井授权上传、目录查询和强制下载，大小/哈希/媒体特征
  校验、文件名净化、不可变 BLOB 留存及预警哈希事件链审计。

目标级 webhook“已送达”只表示该接收服务返回 HTTP 2xx；事件汇总级“已送达”
表示所有符合级别条件的网关目标都已接收。它不是短信或政务消息的终端回执，
不能证明自然人已读。平台内部“已读”则表示具体登录账号主动执行已阅动作，
两类回执严格分开。

仍未实现或须现场接入：

- 短信、企微或政务消息的真实发送、厂商终端送达回执和值班表/班次轮换；
- 原生手机 APP（当前交付是可安装 PWA；能否替代须由验收范围确认）；
- 经正式测绘数据、坐标系转换和空间分析验收的真实 GIS；可选 GeoJSON 代码
  支持不等于正式边界数据已经交付。

附件链已经具备平台侧安全留存能力，但现场仍须落实上传前脱敏、终端防病毒、
材料真实性复核和法定留存制度；白名单与强制下载不能替代这些组织措施。

## 5. 吨煤电耗与吨煤炸药核验

### 5.1 已实现算法

监管端提供 `POST /v1/analyze/verification`，输入
`VerificationRequest`，输出 `VerificationResult`。主要过程是：

1. 只选择同矿井、完整工况完全相同的历史样本；
2. 训练截止时间固定为当前窗口开始，历史窗口、数据可用时间和人工核查时间
   都不得越过截止点，防止时间泄漏；
3. 只接纳来源摘要有效、质量达标、人工核查完成且标签为
   `verified_normal` 的样本；
4. 默认每个指标至少 20 个合格样本、最多取最近 500 个；不足时明确返回
   `insufficient_history`，不扩大到其他工况并冒充正常；
5. 使用 median/MAD 建立吨煤电耗和吨煤炸药稳健基准，设置绝对及相对最小尺度，
   避免 MAD 为零时过度敏感；
6. 在固定物理阈值之外，对当前值计算“方向性有限样本经验尾概率”：只与上述
   已核验正常样本排序比较，并使用加一校正，永不输出零概率；默认尾概率不高于
   0.10 形成历史罕见性关注、不高于 0.025 形成较高线索；
7. 保存每个参考样本编号、参考值、样本量、经验分位、参数版本和完整参数快照，
   结果可以重放。

经验尾概率表示“在受治理的同矿同工况正常参考分布中同向且同等或更极端的
值有多常见”，**不是违法、瞒报、虚报或责任概率**。加一校正也意味着小样本
不可能产生虚假的极小概率；样本不足仍返回冷启动，而不是降低门槛。

历史样本的“来源摘要有效、已经人工复核”不能由分析调用方自行声明后直接获得
信任。启用生产鉴权时，每个历史样本必须先进入平台参考样本注册表，并同时绑定
产量、用电、火工品三类原始材料的 SHA-256 摘要和至少一项证据引用。注册后状态
为草案，必须由不同账号按预期样本摘要批准；样本正文、证据绑定、决定和前后事件
哈希链均不可静默改写。正式分析只接纳与已批准记录规范化 JSON 逐字节等价且摘要
一致的样本，未注册、未批准、被替换或审计链损坏均以 `409` 失败关闭。关闭鉴权的
本地开发模式仍允许算法试算，但结果明确标记
`history_governance.mode=caller_supplied_untrusted`，不能作为生产受治理结果。

### 5.2 电量口径和失败关闭

电量计算遵循：

1. 有可信的生产分区电量时优先使用分区电量；
2. 只有总电量时，必须逐项提供通风、排水、压风、提升、选煤厂电量；
3. 五类干扰项必须全部可识别、有数值且有来源；
4. 任一项缺失或不可识别、或剔除后生产电量不大于零，则状态为 `blocked`，
   不计算电耗结论；
5. 每类剔除量、总剔除量、计算基础和阻断原因进入结果。

这比“算法自动猜测干扰电量”更保守。不能识别时失败关闭，禁止利用回归或 LLM
虚构分项电量。

### 5.3 电耗比值

核验比值为“当前吨煤生产电耗 ÷ 同矿同工况历史基准中位数”：

| 比值 | 系统技术线索 |
|---:|---|
| `<0.8` | 极端偏低，提升核查优先级 |
| `0.8 ≤ x < 0.9` | 偏低，关注 |
| `0.9 ≤ x ≤ 1.1` | 在本参数版本正常区间 |
| `1.1 < x ≤ 1.3` | 偏高，关注 |
| `>1.3` | 极端偏高，提升核查优先级 |

原方案把低/高区间直接描述为“疑似瞒报/虚报”。当前实现有意使用“偏低/偏高
技术线索”，要求核对产量分母、表计边界、倍率、干扰项和工况变化，避免算法
越权认定。

### 5.4 炸药偏差和联合升级

- 当前吨煤炸药量与历史中位数比较；
- 稳健分数使用带最小尺度保护的 MAD，默认绝对稳健分数达到 3 为关注、达到 5
  为高偏差；这两个阈值必须经试点审批；
- 电耗和炸药各自同时给出已核验正常样本的经验分位、方向性尾概率及样本量；
  即使固定物理区间尚未越界，窄工况历史分布中的罕见偏移也可形成技术关注，
  但不会覆盖数据质量门禁或升级为违法认定；
- 基准中位数为零时仍可计算绝对稳健偏差，但不伪造相对偏差；
- 电耗和炸药都异常且同向时，技术核查优先级上调一级；
- 方向相反、不完整、冷启动或电量被阻断时不做联合升级；
- 结果固定包含“非法律/责任认定”声明。

### 5.5 从算法到业务上线仍缺的链路

算法 API 已实现，但以下不是当前已有能力：

- 自动从边缘小时电量、企业日报和公安台账组成每日核验请求；
- 自动把办理结果转成合格训练标签；
- 经审批的自动增量训练、候选模型评估、发布和回滚；
- 市能源局与公安系统的真实接口。

领导端跨矿偏差热力图和一矿一档中的核验摘要已经实现；它展示最后一次受治理
核验结果，不会在上游每日编排尚未完成时伪造“实时核验”。

原方案把模型训练和核验上线列入第二阶段。试点应先积累 1—3 个月数据，并保证
每个“矿井 + 工况”达到合格样本门槛。历史不足是正确的冷启动状态，不得降低
门槛或借用其他矿井数据以追求页面显示“正常”。

## 7. HMAC、契约与部署配置

### 7.1 HMAC 不能替代 TLS

生产流量必须使用 TLS 1.2 或更高版本。HMAC 保护请求身份、原始 body 完整性和
短期重放，TLS 保护传输机密性和服务端身份。所有主机必须同步 UTC 时间。

禁止把密钥写入：

- Git 仓库、前端 JavaScript、LLM prompt、业务 JSON；
- 普通日志、错误消息、截图和操作手册示例；
- 企业草稿、来源凭证或共享 shell 历史。

### 7.2 监管端 `MINEGUARD_EDGE_CLIENTS_JSON`

平台只有配置边缘客户端注册表后才接受边缘批次；未配置时返回 503。格式为：

```json
{
  "clients": [
    {
      "client_id": "QY-MINE-001-EDGE-01",
      "mine_ids": ["QY-MINE-001"],
      "secrets": [
        "<当前密钥的 Base64，不是示例明文>",
        "<轮换期上一把密钥的 Base64，可省略>"
      ]
    }
  ]
}
```

部署时由 systemd `EnvironmentFile`、容器 secret 或密钥管理系统注入为单行 JSON：

```bash
MINEGUARD_EDGE_CLIENTS_JSON='{"clients":[{"client_id":"QY-MINE-001-EDGE-01","mine_ids":["QY-MINE-001"],"secrets":["<BASE64_SECRET>"]}]}'
```

约束：

- Base64 解码后的每把密钥至少 32 字节；
- `secrets[0]` 是当前密钥，后续值只用于短期轮换；
- 客户端只能报送 `mine_ids` 中的矿井；生产环境不使用 `"*"`；
- 每矿至少独立一个客户端，不与企业提交、设备来源或证据包密钥复用；
- 换钥完成后删除旧密钥，并保存换钥审批和验证记录；
- 当前平台运行时允许时间偏差 300 秒，nonce 至少保留 600 秒；
- 同一 `client_id + batch_id` 同内容返回幂等回执，不同内容必须冲突。

### 7.3 监管端权威边缘 HMAC 形式

当前 `contracts/specs/edge-telemetry-hmac-v1.md` 和平台实现使用七个
`X-Edge-*` 请求头。签名材料是以下八行，以 LF 连接，末尾无换行：

```text
MINE-EDGE-TELEMETRY-HTTP-HMAC-SHA256-V1
POST
/v1/edge-telemetry-batches
{client_id}
{timestamp}
{nonce}
edge-telemetry-batch-v1
{body_sha256}
```

服务端依次检查请求大小、唯一请求头、版本、时间窗、body 摘要、HMAC、nonce、
客户端矿井范围、严格 JSON、批次幂等和观测序列。认证错误不能区分“未知客户端”
和“签名错误”以免泄露注册信息。

### 7.4 边缘互通已验证及剩余边界

当前 `edge-agent/`、权威契约和监管平台已经对齐：

| 项目 | 当前统一实现 |
|---|---|
| 签名材料 | 8 行，首行为固定 edge HMAC 上下文 |
| 请求头 | 7 个全量 `X-Edge-*` 请求头 |
| 密钥解释 | 推荐两端配置同一个 Base64 字符串，各自解码成相同原始 bytes |
| 批次 | 固定 10 字段，含序列起止和规则快照引用 |
| 观测 | 边缘本地对象投影为严格合同对象，包含质量对象、来源记录、可选统计窗口和人工证明 |
| 本地预警 | 严格投影并固定 `advisory_only=true` |

黑盒脚本 [verify_edge_pipeline.py](../scripts/verify_edge_pipeline.py) 不 import
两套应用源码，分别启动真实 `mineguard` 和 `mine-edge-agent` 进程。当前验证结果：

- 平台离线时边缘队列保留 4 条 outbox 记录和稳定批号；
- 平台恢复后回执接受 3 条原始观测；
- 矿端使用故意不同的本地容量计算出红色提示；
- 平台按监管档案独立复算为橙色，且来源为
  `platform_recalculation`，证明没有直接采信矿端等级。

可重复执行：

```bash
python scripts/verify_edge_pipeline.py --verbose --timeout 45
pytest -q scripts/test_verify_edge_pipeline.py
```

仍需明确以下能力边界：

- 边缘默认批量为 100，代码硬上限 1000，低于平台单批 10000；容量测试按边缘
  上限执行，不能假定每批可发 10000；
- 边缘可上送主通风机运行、故障和倒机三个 V1 二值指标；`airflow_ratio` 因
  V1 没有对应 `metric_code`，目前只在本地使用；
- 皮带、区域/异常人员和雷管计数的 V1 字段已具备，但真实厂商字段、点位和
  统计口径仍须逐矿映射验收；调度器已自动合成并持久上送 `source.*` 健康观测，
  监管端会对明确缺数生成数据质量预警并只在可信恢复后清除；
- 甲烷来源达到配置的预警阈值比例或形成本地甲烷提示时，矿端会在有界窗口内
  自动缩短只读轮询周期；窗口、原因和实际阈值持久留痕，失败、空结果或低值
  不会提前被解释为恢复。该能力不改变设备自身采样参数，也没有设备写权限；
- 边缘尚未主动请求 capabilities，契约升级必须通过受控发布同步更新；
- 边缘只有在 HTTP 2xx 且严格回执的批号、客户端、矿井和 body 摘要全部匹配时
  才标记送达；当前不持久化完整回执正文，平台回执仍可独立查询；
- 静态 capabilities 示例与运行时限制必须在定版时核对，现场验收以真实
  `GET /v1/edge-telemetry-capabilities` 为准，不能只照抄示例。

### 7.6 可选安全通知 webhook

平台可把安全预警的创建、升级、降级、重开、自动解除等变化写入持久化 outbox，
再向一个或多个通用接收服务发送签名 JSON。配置示例：

```bash
MINEGUARD_SAFETY_WEBHOOKS_JSON='{"webhooks":[{"webhook_id":"county-gateway-01","url":"https://notify.example.internal/mineguard","secret_base64":"<至少32字节随机密钥的Base64>","minimum_level":"yellow","timeout_seconds":5}]}'
```

生产 URL 必须使用 HTTPS；只有 `localhost` 或 IP 字面量表示的环回地址可用
HTTP。URL 必须是无控制字符和反斜杠的 ASCII 地址，不得包含用户口令、查询串或
片段；国际化域名应先写为 IDNA/Punycode。`webhook_id` 只能使用字母、数字、
点、下划线和连字符。`minimum_level` 只能是 `blue/yellow/orange/red`，超时
范围为 0.5—30 秒。投递时禁止跟随 3xx 重定向，避免签名目标被切换。

接收方须验证 body SHA-256 和以下六行签名材料，行间用 LF，末尾无换行：

```text
MINEGUARD-SAFETY-WEBHOOK-HMAC-SHA256-V1
POST
{webhook URL 的 path，空 path 按 /}
{webhook_id}
{notification_id}
{body_sha256}
```

请求头为 `X-MineGuard-Webhook-Id`、`X-MineGuard-Notification-Id`、
`X-MineGuard-Content-SHA256`、`X-MineGuard-Signature-Version` 和
`X-MineGuard-Signature`。失败后从 5 秒开始指数退避，最长间隔 3600 秒，最多
尝试 12 次后进入 `dead`。事件 outbox 是兼容汇总层，实际投递按
`notification_id + webhook_id` 逐目标持久化：部分目标成功、另一目标失败时，
只重试失败目标，已成功目标不再发送。管理员可在系统管理页查看每个目标的总尝试
次数、当前重试周期、人工重试次数和稳定错误码，只对 `dead` 目标人工重新排队；
人工重试重置该目标的 12 次周期但保留总尝试次数和审计记录。接收方仍必须按
`notification_id` 幂等去重，以应对“远端已处理但响应在网络中丢失”的不可判定
情况。低于所有接收方 `minimum_level` 的通知没有外发目标，并在事件汇总层完成。
进程在 `sending` 状态中断时，该目标启动后恢复为 `retry`，已送达目标保持不变。
若保留部分 webhook 配置但移除了某个尚未完成的目标，该目标会显式进入
`dead/webhook_not_configured`，不会悄悄丢弃；恢复配置后由管理员受控重试。

接收服务必须另行完成矿井、预警类别、值班表和责任人的路由，并把厂商送达/
自然人已读回执写入其自身或后续约定接口；当前平台没有伪造这一级回执。

### 7.7 安全预警核查附件

复核人员、监管负责人和管理员可以在预警卡上传核查材料；查阅人员只能查看目录
和下载本人矿井范围内的材料。请求使用 JSON Base64，必须同时提交客户端计算的
小写 SHA-256；平台解码后重新计算并比对。单文件上限为 5 MiB，允许：

- PDF、JPEG、PNG；
- UTF-8 TXT/CSV；
- 无宏 XLSX/DOCX。

平台同时检查文件签名；OOXML 还检查 ZIP 路径、条目数、展开总量、类型根目录和
宏/可执行成员。文件名经过 Unicode 规范化、路径剥离、控制字符替换和安全扩展名
修正。内容存为 `safety_alert_attachments.content` BLOB，不落入 Web 静态目录；
同一预警相同 SHA-256 拒绝重复，不提供更新、覆盖或删除接口。上传成功会增加预警
版本，并把附件编号、净化后文件名、类型、大小和哈希作为 `attachment_added`
追加到预警事件哈希链。

目录接口不返回 BLOB。下载前重新核对数据库中的大小和 SHA-256；失败返回
`409 safety_attachment_integrity_failed`。成功响应固定使用
`application/octet-stream`、`Content-Disposition: attachment`、
`X-Content-Type-Options: nosniff`、CSP sandbox 和同源资源策略，PC 页面不创建
对象 URL，不内联展示附件。

这套控制防止平台把附件当页面或程序执行，但不能证明材料真实、无恶意内容或已经
脱敏。正式部署仍应在上传前后接入本单位病毒扫描/内容检查流程，并按档案制度决定
保留期限和依法导出方式。

## 8. 一期部署顺序

### 8.1 准备

1. 确定一个试点矿井及业务、机电、通风、安全、信息化责任人。
2. 建立矿井主数据：统一矿井编号、名称、瓦斯类别、核定人数、坐标、核定产能。
3. 列出六类来源系统、厂商、版本、协议、点位、表计、账号和网络负责人。
4. 固化统计日、班次、时区、单位、累计表复位、修订和缺失值规则。
5. 完成规则审批草案、密钥申请、TLS 证书、NTP、端口和防火墙审批。
6. 给三个服务分别创建不可登录系统用户、独立目录和最小文件权限。

### 8.2 监管端

1. 在县级内网安装固定依赖版本和监管平台发布包。
2. 将平台置于 HTTPS 反向代理后，后端监听内网或回环地址。
3. 通过密钥系统注入管理员、企业客户端和边缘客户端配置。
4. 创建真实矿井档案、角色、矿井数据域、来源和算法配置。
5. 登记规则草案，完成回放和线下审批后再由有权账号按完整指纹批准。
6. 如启用通知，先在测试接收服务验证签名、幂等、失败重试和恢复投递，再配置
   正式网关；外部网关的责任人路由和回执另行验收。
7. 验证 `/live`、`/ready`、`/health`，执行备份并在隔离目录恢复。
8. 未用正式候选制品和正式配置重复通过第 7.4 节黑盒前，不开放边缘生产入口。

### 8.3 矿端

1. 部署到矿井机房独立主机或隔离虚机，默认只允许向县平台出站。
2. 来源账号全部设为只读；先接影子库、只读 API 或厂商推荐接口。
3. 一类一类上线适配器，先保存不转发，校验原始值、单位、时间和点位。
4. 保持 `MINE_EDGE_THRESHOLDS_CALIBRATED=false`，完成历史回放和审批后再改。
5. 用正式候选制品重复协议黑盒验收后启用上行，模拟断网并验证同批次续传。
6. 备份 SQLite 时使用在线备份；不得只复制运行中的 WAL 主文件。

### 8.4 企业端

1. 创建逐用户账号，不在共享环境使用 `demo/123123123`；
2. 分离经办、核对、确认和提交权限；
3. 注册企业运输客户端和监管端确认人；
4. 先做草稿、导入、追问、预检和确认演练，再启用真实提交；
5. 验证接收回执始终是“接入时未作监管认定”。

## 9. 验收方法

### 9.1 代码门

每次候选发布必须在干净环境执行：

```bash
cd platform
pytest

cd ../agent
pytest

cd ../edge-agent
pytest

cd ..
python contracts/scripts/validate_contracts.py
```

当前基线已验证：

- `platform/` 全量测试通过，其中边缘平台集成、责任路由、周期报告、前端和权限
  均有专项覆盖；
- `agent/` 全量测试通过；
- `edge-agent/` 全量测试与 Ruff 检查通过；
- 独立边缘—平台 pipeline 黑盒 1 项通过；
- 契约脚本通过 JSON、引用、摘要和签名向量检查；使用
  `contracts/requirements-validation.txt` 在隔离依赖目录复跑后，7 个示例也
  全部通过 Draft 2020-12 schema 实例校验。默认项目解释器未把
  `jsonschema` 作为运行时依赖，未安装校验依赖时脚本仍会明确报告跳过。

发布门要求安装 `jsonschema>=4.18` 后重新执行契约验证，任何“跳过”都不能视为
完整通过。测试数量会随功能增长，验收以“当前全部收集项零失败、零意外跳过”
为准，不以固定数量为准。

### 9.2 接口门

必须保存请求摘要、响应、服务日志和时间：

1. capabilities 与客户端期望版本一致；
2. 正确 HMAC 批次成功；
3. body 改一个字节验签失败；
4. 过期时间失败并不泄露密钥细节；
5. nonce 重放失败；
6. 相同批次相同内容返回原回执；
7. 相同批次不同内容返回冲突；
8. 客户端报送未授权矿井失败；
9. 超限 body、观测数和非法单位失败；
10. 断网后队列保留，恢复后续传且不重复产生业务记录；
11. 平台保存原始观测，并用监管规则独立复算；
12. 本地预警等级被篡改不能改变监管复算结果；
13. webhook 接收方能按原始 body、摘要、路径、目标 ID 和通知 ID 验证 HMAC；
14. 一个接收方故障不阻塞其他接收方，恢复后只补投失败目标，成功目标不重发；
15. 投递进程重启不丢失目标状态，3xx 不被跟随，管理员只能重试 `dead` 目标；
16. 接收方重复收到同一 `notification_id` 不产生重复业务动作；
17. `dead`、低于级别下限和 HTTP 2xx 的含义与页面/接口说明一致，不把
    HTTP 2xx 当作自然人已读。
18. 附件上传按复核权限和矿井范围鉴权，查阅人员不能上传、越界矿井不能读取；
19. 超过 5 MiB、哈希不符、类型伪装、危险 OOXML 或同预警重复内容被阻断；
20. 下载重新验大小和哈希，响应强制 `attachment/octet-stream`，目录不含 BLOB。

### 9.3 六类数据门

每类至少选取正常、边界、异常、缺失、重复、迟到、修订和来源故障样本：

- 与源系统逐字段核对值、单位、点位和时间；
- 验证班/日/月聚合可由明细重算；
- 验证累计表复位和修订不会重复计算；
- 验证缺测不按零处理；
- 验证人工补录有完整人员、原因和凭证；
- 验证来源恢复后自动数据不会覆盖人工记录；
- 验证越权矿井和未知点位失败关闭。

### 9.4 安全规则门

1. 对规则快照中每个阈值做“阈值前、等于阈值、阈值后”三点测试；
2. 分别验证低瓦斯、高瓦斯和全部支持点位；
3. 验证 80/90/100% 人员边界；
4. 验证甲烷 >0.2 个百分点而不是 ≥0.2；
5. 验证风量下降恰好 15% 不触发、超过 15% 触发；
6. 验证通风—瓦斯联合时间窗内升级、窗外不升级；
7. 验证连续、清除、降级、迟到、乱序和跨批重启；
8. 验证未配置矿井档案时只产生配置缺失提示，不擅自套用阈值；
9. 验证所有结果均无控制动作，抓包确认没有设备写请求；
10. 用批准快照的 SHA-256 与页面、运行记录和验收报告三方比对；
11. 新登记方案/草案在审批前不成为正式生效规则；
12. 错误指纹、无权限、缺少 CSRF 和有效期重叠的审批全部被阻断；
13. 退役现行版本后，新计算不再选用它；批准上一版本后按其指纹稳定回放；
14. 没有已批准规则时明确出现 `safety_rule_approval_required`，不显示为
    已经正式审批；
15. 对主通风机运行、故障和倒机分别验证正常值和触发值，并确认平台只依据
    V1 原始观测及监管规则复算红/黄线索。

### 9.5 生产核验门

1. 分区电量存在时优先采用；
2. 总电量回退必须完整剔除五类干扰；
3. 每缺一类、每出现一类不可识别项都必须返回 `blocked`；
4. 验证 0.8、0.9、1.1、1.3 四个边界的包含关系；
5. 给历史池加入极端离群值，基准中位数不得被显著拖动；
6. 当前窗口重叠、事后才可用、事后才核查的样本全部被排除；
7. 非本矿、非同工况、非人工正常、低质量和摘要无效样本全部被排除；
8. 少于门槛时返回冷启动，不借用其他矿井/工况；
9. 电耗和炸药同向异常时只上调技术优先级；
10. 生产鉴权模式下，未注册、未批准、正文摘要不符或审计链损坏的任一历史样本
    都必须使整次请求失败关闭，不能只静默剔除；
11. 登记人与审批人必须是不同账号，审批必须同时校验预期样本 SHA-256；
12. 关闭鉴权的开发试算必须明确标记调用方历史不可信，不能伪装为平台批准样本；
13. 所有结果不得出现自动违法认定或处罚建议。

### 9.6 PC 工作台门

- 领导账号只能看到授权矿井；
- 无数据明确显示“不能判断”，不能显示绿色正常；
- 四色、矿井、状态筛选与 API 数据一致；
- 原始值、点位、规则版本、证据观测和处置历史可追溯；
- 无权限账号不能执行预警动作；
- 乐观锁冲突不会覆盖其他人的办理；
- 逾期数量与批准时限一致；
- 页面在常用办公分辨率和键盘操作下可用；
- 相对坐标示意能与矿井筛选联动，坐标不足时明确降级为一矿一档；
- 页面明确说明相对坐标示意不是测绘底图或导航依据；
- 附件上传越权、超限、哈希不符、类型伪装和重复内容均被阻断；
- 附件目录不返回内容，下载必须是 `attachment` 且篡改后不能下载；
- 页面不内联预览附件，查阅账号只能下载授权矿井材料；
- PC 页面通过不代表真实 GIS、具体短信/APP/政务消息网关或手机 APP 已交付；
- 通用 webhook 通过不代表责任人目录、人工已读和厂商送达回执已交付。

| webhook 不确定失败造成的重复责任业务动作 | 0，接收方按通知 ID 去重 |
| 系统发出的生产控制请求 | 0 |
| 备份恢复 | 每月至少一次，恢复库校验通过 |

模型业务效果不能只看“准确率”。试点报告至少同时给出：

- 人工核查样本数和标签分布；
- 精确率、召回率、误报率、漏报率及置信区间；
- 按矿井、工况、数据来源和预警等级的分层结果；
- 冷启动、被阻断和无法判断的比例；
- 从预警到已阅、开始办理、复核和关闭的时长；
- 参数版本、数据截止时间和排除样本原因。

红色安全事件样本稀少时，不能用总体准确率掩盖漏报。上线门应以批准规则的边界
回放零漏判、真实事件逐例复盘和人工兜底为主。

## 11. 试点和回滚

### 11.1 试点阶段

1. **协议确认期**：使用正式候选制品和现场网络重复第 7.4 节双进程验收。
2. **离线回放期**：使用脱敏历史数据，不发送真实通知，不改变生产。
3. **单矿影子期**：只采集、计算、展示；矿井原法定系统和处置流程保持唯一有效。
4. **并行核验期**：每条系统线索与人工/原系统结果对照，记录误报和漏报。
5. **一期验收**：关闭安全接入、规则、工作台和处置链问题。
6. **二期建模期**：积累 1—3 个月合格数据后启用电耗/炸药基线试运行。
7. **推广评审**：达到签批指标后才进入全县复制。

至少完成一个完整班次的端到端技术联调；建议连续 7 天影子运行后做一期试点评审。
生产核验不得跳过原方案要求的历史积累期。

### 11.2 回滚触发

出现以下任一情况应停止新规则或新版本扩面：

- 边缘积压持续增长且无法恢复；
- 数据单位、时间、点位或矿井映射错误；
- 规则版本/指纹与批准件不一致；
- 同一输入不能稳定重放；
- 发现越权读取、密钥泄露或签名旁路；
- 产生未授权设备写请求；
- 严重误报、漏报或页面把缺测显示成正常；
- 数据库、磁盘、CPU 或网络达到批准容量上限。

### 11.3 安全回滚步骤

1. 先停止新版本上行或分析，不删除边缘原始数据和 outbox；
2. 保存日志、版本、规则指纹、数据库在线备份和故障时间窗；
3. 边缘可清空 `MINE_EDGE_UPSTREAM_URL` 或由防火墙暂时阻断出站，继续本地只读
   留存；
4. 平台撤下有问题的服务构建，恢复上一受控发布包；
5. 数据库恢复必须恢复到新目录验证，禁止覆盖仍在运行的唯一生产库；
6. 在配置管理后台核对完整指纹，先退役现行版本，再批准上一经复核版本；不能
   沿用不同指纹的状态，须重新回放必要窗口；
7. 换钥时短暂保留当前/旧密钥验证，确认全部客户端切换后吊销旧密钥；
8. 完成原因分析、数据补传、结果作废/重算和人工签字后再恢复。

当前后台已经支持方案/草案登记、指纹绑定的批准和退役，但没有原子化“一键
回滚”，也不能替代多人复核和批准文件。退役与重新批准是两个受控动作，应先
停止新分析、保留数据和审计，再在首次试点前演练完整流程；任何短暂的“无已
批准规则”窗口都必须显示审批缺失警告，不能静默使用默认值。

## 13. 验收签字清单

验收报告至少附：

- 候选发布版本、依赖锁定文件和制品 SHA-256；
- 三套服务及契约的完整测试报告；
- 边缘—平台和企业—平台双进程黑盒报告；
- 六类来源系统字段映射表和抽样核对记录；
- 矿井档案、点位、规则版本、规则指纹和审批件；
- TLS、NTP、账号、权限、密钥轮换和安全扫描记录；
- 断网续传、幂等、重放、越权和篡改测试记录；
- 规则登记、回放、完整指纹、批准/退役记录和职责分离审批件；
- webhook 签名、接收方幂等、持久重试和恢复投递记录；如接入真实渠道，另附
  责任人路由、厂商送达和人工已读记录；
- 备份、恢复和回滚演练记录；
- 影子运行指标、误报漏报逐例复盘；
- 未完成项、风险接受人、计划完成日期和范围变更单；
- 矿方、平台方、县能源/应急等责任单位的签字。

只有“代码门、接口门、现场数据门、规则门、安全门和回滚门”全部通过，且所有
`B` 项已关闭或由有权单位正式变更范围，才能声明相应一期能力通过验收。

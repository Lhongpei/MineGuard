# MineGuard · 矿安智察 · 煤矿智能辅助监管系统 V2 部署与运行

本文是当前可执行的部署手册，适用于本机联调、单矿试点和政府内网部署。当前系统只有
两个运行产品：

- `agent/`：企业侧，一座煤矿部署一个独立智能体；
- `platform/`：政府侧，集中接收多个煤矿的报送并自动分析，领导业务界面只读。

`contracts/` 只发布中立的 Schema、OpenAPI、签名规范和测试向量，不是第三个服务，
也不是任一产品的 Python 运行时依赖。原独立 `edge-agent` 已退役；固定目录监听和
受控设备/API 连接器属于企业 Agent 内部能力。

## 1. 运行拓扑与责任边界

```text
每座煤矿独立部署 Agent                         政府集中部署 Platform
┌────────────────────────┐                ┌──────────────────────────┐
│ 人工导入 / 固定目录直采 │                │ 验签、幂等接收、追加留痕 │
│ 规范化、缺项提示、复核   │  HTTPS/HMAC   │ 唯一五量监管算法          │
│ 企业确认、持久 outbox    │ ────────────> │ 报告、风险、修订重算      │
│ 风险解读、回复草稿和确认 │ <──────────── │ 领导只读大屏              │
└────────────────────────┘  企业主动拉取   └──────────────────────────┘
```

硬边界如下：

- 一个 Agent 进程只能绑定一个 `mine_id` 和一个独立经营主体；不同煤矿不能共享
  Agent 数据库、用户、目录、消息 cursor 或密钥；
- 政府无需反向连接矿区内网，Agent 主动上报并主动拉取分析报告；
- Platform 与 Agent 不共享数据库、文件目录、Cookie、Python 包或领域对象；
- 政府领导端只有查看、筛选、搜索和钻取能力，不能代企业填报、修改数据、删除记录、
  改算法结论或手工关闭风险；
- 人工导入与直采都是合法采集方式，`acquisition_mode` 只用于追溯，算法不因来源方式
  设置不同信任等级、权重或阈值。

## 2. 五量报表与唯一算法

每份月报按自然日保存日报合计和三班数据。监管“五量”固定为风量、电量、火工品量、
入井人员量和产量。数据层使用六个规范原子字段，是因为火工品量保留两个不同单位的
子项；六个原子字段不等于六量：

| 所属五量 | 规范原子字段 | 含义 | 固定单位 | 聚合 |
|---|---|---|---|---|
| 风量 | `ventilation_m3_min` | 风量 | m³/min | `time_weighted_average` 或 `snapshot` |
| 电量 | `electricity_kwh` | 电量 | kWh | `sum` |
| 火工品量 | `detonators_count` | 雷管数量 | count | 整数、`sum` |
| 火工品量 | `explosives_kg` | 炸药质量 | kg | `sum` |
| 入井人员量 | `mine_entry_persons` | 统计范围内实际入井人次 | person | 整数、`sum` |
| 产量 | `production_t` | 产量 | t | `sum` |

雷管和炸药只是火工品量中按各自单位保存的子项，后续增加其他火工品子项时也必须保留
品类和单位，不能把 `count`、`kg` 等不同量纲直接相加。`mine_entry_persons` 不表示
在册人数、排班用工或时点井下人数；日报与班次必须使用同一“实际入井人次”事件口径，
才能按 `sum` 确定性核对。

缺失必须保持 `null` 并给出缺失原因，不能用 0 代替。三班固定为本地时间
`00:00–08:00`、`08:00–16:00`、`16:00–次日 00:00`；夏令时地区按实际持续时间
处理风量加权。

政府侧只有一个对外业务算法 `mineguard-five-quantity-engine`。同一版本化管线内完成：

1. 契约、单位、缺失、非负和日报—三班确定性核对；
2. 停产、检修、复产爬坡和稳产工况识别；
3. 本矿正式准入历史的 Median/MAD、Rolling MAD、EWMA、CUSUM、Page-Hinkley、
   连续异常、漂移和变化点；
4. 至少三座可比矿、每矿等权且按截止日冻结的匿名同类矿参考区间；
5. HiGHS 加权 L1 联合协调和最小冲突集 MCS；
6. 汇总为 `normal_candidate`、`risk` 或对外报告中的 `data_insufficient`。

求解器只在第 5 步内部使用。规则层先按 `sum`、`time_weighted_average`、`snapshot`
真实语义核对；主问题求观测与本矿历史、匿名同类矿软区间联合相容所需的最小加权
L1 调整；MCS 才把观测容差和参考带硬化，定位最少应复核的日期、指标和证据组。它不
预测所谓“真实产量”，历史和同类矿也不是物理定律。原有时序算法作为内部模块保留。

分析结论与历史基线准入相互独立。首期完整正常数据只进入隔离参考候选；只有求解
成功、无复核级/风险级信号，并有正式本矿历史或冻结匿名同类矿独立锚点的数据，才
进入正式历史基线。企业解释只能形成
`explanation_recorded`；只有更高修订版沿完整血缘重新通过同一算法，风险才能成为
`cleared_by_reanalysis`。

`--no-auth`；该参数只允许回环隔离演示。

### 4.1.1 增加领导端账号

账号管理属于政府平台运维，不属于领导业务操作，因此不放进只读监管页面。另开终端，
使用与 `serve` 完全相同的状态目录执行；SQLite 支持在线新增，无需停止或重启服务：

```bash
cd /home/sevan/coral/platform
. .venv/bin/activate

mineguard user mines --state-directory .mineguard-v2
mineguard user list  --state-directory .mineguard-v2

mineguard user add leader_a \
  --role viewer \
  --mine-id MINE-QY-001 \
  --state-directory .mineguard-v2 \
  --demo-default-password
```

需要查看当前辖区全部煤矿时仍使用只读 `viewer`，不要授予 `admin`：

```bash
mineguard user add leader_all \
  --role viewer \
  --all-mines \
  --state-directory .mineguard-v2 \
  --demo-default-password
```

`--all-mines` 会展开为当前全部煤矿的明确授权。后续接入新煤矿后，重新执行一次
`set-access leader_all --role viewer --all-mines ...` 即可更新范围。

最后一个参数把受控演示初始密码设为 `123123123`。正式环境不要使用该参数，命令会
无回显地要求输入和确认密码；自动化部署可临时设置
`MINEGUARD_NEW_USER_PASSWORD`，命令完成后立即清除。给账号增加多矿查看范围时重复
传入 `--mine-id`：

```bash
mineguard user set-access leader_a \
  --role viewer \
  --mine-id MINE-QY-001 \
  --mine-id MINE-QY-002 \
  --state-directory .mineguard-v2
```

修改范围、停用账号或重置密码都会立即撤销该账号的现有会话：

```bash
mineguard user disable leader_a --state-directory .mineguard-v2
mineguard user enable leader_a  --state-directory .mineguard-v2
mineguard user reset-password leader_a \
  --state-directory .mineguard-v2 --demo-default-password
```

当前 V2 中 `viewer`、`reviewer`、`supervisor` 的监管页面都是只读，区别只保留给后续
流程扩展；三者都必须明确指定煤矿。普通领导使用 `viewer`，辖区多矿领导逐项授权。
`admin` 自动查看全部煤矿，只给系统管理员。系统不提供物理删除命令；离岗账号应停用，
从而保留历史账号、权限审计和交换留痕。

### 4.3 完整业务路径

1. 企业在“数据收件箱”人工上传，或由固定目录/受控 API 直采；
2. Agent 规范化后生成待复核草稿，缺失保持 `null`；
3. 具名企业人员逐项复核并确认，消息进入持久 outbox；
4. Platform 验签、幂等接收并自动运行唯一算法；
5. Agent 主动拉取并验签报告，先保存 inbox，再确认送达；
6. 有风险或数据不足时，企业可对话解读并形成原因、证据索引和措施草稿；
7. 企业人员确认回复，政府留痕为 `explanation_recorded`；
8. 如需解除风险，企业提交严格递增、指向直接前版的更正报表，政府重新运行同一算法。

会议大屏可按 F11，固定展示终端可使用浏览器自身的 kiosk 模式。政府登录仍然有效，

## 5. 人工导入、固定目录与设备接口

前端支持 ET/XLS/XLSX/CSV/JSON/JSONL。固定目录在启动前配置：

```bash
export ENTERPRISE_FIVE_QUANTITY_WATCH_DIRS='/srv/mine-readonly/five-quantity-inbox'
export ENTERPRISE_FIVE_QUANTITY_POLL_SECONDS=5
export ENTERPRISE_FIVE_QUANTITY_STABLE_SECONDS=2
```

多个目录使用操作系统路径分隔符。监听器只读普通文件，不跟随符号链接；文件大小和
修改时间稳定后再读取，按 SHA-256 去重。解析失败内容复制到 Agent 数据库同级的
`five-quantity-quarantine/`，不删除或改写来源原件。

`POST /api/v2/direct-ingest` 是受控直采入口。生产设备连接器应逐来源固定 HTTPS
origin/path、身份、CA、响应上限、超时和内容类型；不能提供任意 URL 抓取，不能把
HMAC、设备凭据或原件交给模型。人工导入与直采采用相同的字段校验和政府算法。

## 6. 多矿部署

每增加一座煤矿，都需要：

1. 新建独立 Agent 主机或容器、数据库、状态目录、用户和端口；
2. 分配新的 `mine_id`、`operator_id`、`system_id/sender_id`；
3. 生成该矿独立的应用消息密钥和运输密钥；
4. 在政府 `MINEGUARD_V2_CLIENTS_JSON.clients` 中新增恰好一项；
5. 为五个 `comparison_context` 维度填写经治理的分组值；
6. 分别执行报送、报告隔离、回复和断网恢复测试。

同一 `sender_id` 和同一 `mine_id` 在政府注册表中都只能出现一次。禁止 `*`，禁止一
个 Agent 在页面上切换矿井。政府跨矿分析只使用至少三座可比矿形成的匿名区间，且每
矿等权；企业报告不返回其他矿名称、ID 或原始数值。

## 7. 生产 systemd 与 HTTPS

仓库提供可直接改造的模板：

- `platform/deploy/mineguard.env.example`；
- `platform/deploy/mineguard.service.example`；
- `platform/deploy/nginx-mineguard.conf.example`；
- `agent/deploy/enterprise-agent.env.example`；
- `agent/deploy/enterprise-agent.service.example`；
- `agent/deploy/nginx-enterprise-agent.conf.example`。

生产建议代码只读安装在 `/opt`，状态在 `/var/lib`，配置和秘密在 `/etc`，进程使用
独立低权限系统账号。复制模板后核对实际路径和权限：

```bash
sudo install -m 0640 -o root -g mineguard \
  platform/deploy/mineguard.env.example /etc/mineguard/mineguard.env
sudo install -m 0644 -o root -g root \
  platform/deploy/mineguard.service.example /etc/systemd/system/mineguard.service

sudo install -m 0640 -o root -g enterprise-agent \
  agent/deploy/enterprise-agent.env.example /etc/enterprise-agent/enterprise-agent.env
sudo install -m 0644 -o root -g root \
  agent/deploy/enterprise-agent.service.example /etc/systemd/system/enterprise-agent.service

sudo systemctl daemon-reload
sudo systemctl enable --now mineguard enterprise-agent
sudo systemctl --no-pager --full status mineguard enterprise-agent
```

政府端全新非回环部署必须设置至少 8 字符的 `MINEGUARD_ADMIN_PASSWORD`；正式环境
不得使用默认 `123123123`。企业端先用 `enterprise-agent hash-password` 生成具名
账号摘要，并配置 `ENTERPRISE_AGENT_USERS_JSON`。两个服务仍只监听
`127.0.0.1`，由 Nginx/API 网关提供 HTTPS；Platform 使用 `--secure-cookie`，Agent
设置 `ENTERPRISE_AGENT_SECURE_COOKIE=true` 和准确的
`ENTERPRISE_AGENT_PUBLIC_ORIGIN`。

反向代理必须保留原始 path/query/body，不重新序列化已签名 JSON，不跟随或制造
重定向，不记录 Cookie、签名头、body 或模型密钥。生产 Agent 的
`PLATFORM_V2_BASE_URL` 必须是 HTTPS；私有 CA 使用：

```bash
export PLATFORM_V2_CA_BUNDLE='/etc/enterprise-agent/regulatory-ca.pem'
```

## 8. V2 交换接口

双方实现必须与 `contracts/openapi/five-quantity-exchange-v2.openapi.json` 一致：

| 方法与路径 | 用途 |
|---|---|
| `POST /v2/five-quantity-submissions` | 企业上报确认后的五量月报 |
| `GET /v2/five-quantity-submissions/{message_id}/receipt` | 读取接收回执 |
| `GET /v2/analysis-reports/next?after_cursor=...` | 企业主动领取下一报告 |
| `GET /v2/analysis-reports/{report_id}` | 读取所属矿不可变报告 |
| `POST /v2/analysis-reports/{report_id}/delivery-ack` | Agent inbox 持久化后确认送达 |
| `POST /v2/analysis-reports/{report_id}/responses` | 上报人工确认的结构化回复 |
| `GET /v2/risk-responses/{response_id}/receipt` | 读取回复回执 |

政府业务查询只有登录和只读 GET：

```text
GET /v2/regulatory/overview
GET /v2/regulatory/mines
GET /v2/regulatory/mines/{mine_id}
GET /v2/regulatory/findings
GET /v2/regulatory/exchanges
```

机器 POST 是双方协议通道，不赋予领导浏览器任何写权限。

## 9. 密钥、轮换和时钟

每矿需要两把至少 32 字节且内容不同的高熵秘密：

- 应用消息密钥：Agent 的 `ENTERPRISE_EXCHANGE_HMAC_SECRET`，对应政府注册项
  `message_keys`；
- HTTP 运输密钥：Agent 的 `PLATFORM_V2_TRANSPORT_HMAC_SECRET`，对应政府注册项
  `transport_secrets`。

`ENTERPRISE_EXCHANGE_KEY_ID` 必须命中该矿政府注册项的消息 key ID；
`REGULATORY_EXCHANGE_KEY_ID` 必须等于政府 `MINEGUARD_V2_PLATFORM_KEY_ID`。双方
时钟由 NTP 同步，代理不能改写请求目标或 body。

消息换钥时，在政府 `message_keys` 中临时保留新旧 key ID，并用
`active_message_key_id` 指定企业当前签名 key；企业验政府消息可短期配置：

```bash
export REGULATORY_PREVIOUS_EXCHANGE_KEY_ID='regulator-key-previous'
export REGULATORY_PREVIOUS_EXCHANGE_HMAC_SECRET='previous-secret-at-least-32-bytes'
```

运输换钥时，`transport_secrets[0]` 是当前密钥，后续项仅用于批准的重叠窗口。先让
验签方同时接受新旧密钥，再切发送方；确认存量 outbox 清空并超过重试窗口后删除旧
密钥。日志只记录 key ID，绝不记录秘密。

## 10. 数据、备份与恢复

政府状态目录包含：

```text
.mineguard-v2/mineguard.db
.mineguard-v2/auth.db
.mineguard-v2/backup.key
.mineguard-v2/backups/
```

每矿 Agent 默认数据库是 `agent/data/enterprise-agent.db`，生产建议显式设置
`ENTERPRISE_AGENT_DB=/var/lib/enterprise-agent/enterprise-agent.db`；隔离文件位于
同一状态目录。两端不得指向同一数据库或同一状态目录。

政府端使用产品自带一致性备份命令：

```bash
mineguard backup 2026-08-01T120000Z \
  --state-directory /var/lib/mineguard \
  --backup-directory /srv/backup/mineguard \
  --key-file /var/lib/mineguard/backup.key

mineguard verify-backup 2026-08-01T120000Z \
  --state-directory /var/lib/mineguard \
  --backup-directory /srv/backup/mineguard \
  --key-file /var/lib/mineguard/backup.key
```

恢复必须指向不存在或为空的新目录，不能覆盖在线状态：

```bash
mineguard restore-backup 2026-08-01T120000Z \
  --state-directory /var/lib/mineguard-restore-test \
  --backup-directory /srv/backup/mineguard \
  --key-file /secure/offline-copy/mineguard-backup.key
```

`serve` 会在状态目录创建 `backup.key`，但该文件不包含在业务备份中，必须另复制到
受控离线介质；灾备恢复时用该离线副本。Agent 当前没有产品级备份 CLI；
应停服务后一致性备份整个状态目录，或使用经恢复演练验证的 SQLite backup API，不能
只裸拷贝正在写入的 WAL 主文件。恢复后验证 Agent `/api/v2/audit`、cursor、outbox、
inbox、回复和隔离文件一致，再接入网络。

## 11. 监控与故障处置

基础检查：

```bash
curl -fsS http://127.0.0.1:8080/healthz
curl -fsS http://127.0.0.1:8080/readyz
curl -fsS http://127.0.0.1:8090/api/v1/health
```

还应监控每矿最近报送和 `as_of`、Agent outbox/inbox、分析耗时、HMAC 失败、时间超窗、
nonce 重放、幂等冲突、跨矿拒绝、磁盘余量、证书、审计链和备份恢复演练。

| 故障 | 正确处置 |
|---|---|
| 政府暂不可达 | 保留原 `message_id`、幂等键和 body，由 Agent outbox 重试 |
| Agent 暂不可达 | 恢复后从持久 cursor 继续拉取，不人工跳 cursor |
| 报告验签失败 | 停止业务展示，核对 key ID、密钥和时钟，保全原报文 |
| 分析失败 | 保留输入快照和错误，不得写成正常 |
| 文件格式变化 | 隔离并重新确认映射，不猜测或插补数值 |
| 审计链失败 | 隔离受影响状态并保全副本，不直接改表“修链” |
| 密钥疑似泄露 | 暂停该 sender、保全日志、按受控流程轮换 |

可选大模型只用于煤炭字段映射建议、风险解释和回复草稿；未配置或不可用时，导入、
校验、报送、政府算法、报告收取和人工回复仍然工作。API Key 只能从服务端密钥环境
注入，不能写入仓库、数据库业务记录或浏览器。

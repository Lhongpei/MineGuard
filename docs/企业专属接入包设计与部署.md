# 企业专属接入包设计与部署

> **当前 Windows 简化流程已更新。** 企业只接收一个 `.mgprov`，不再单独填写
> CA、激活码、公钥或指纹；账号为一个业务管理员加固定 `api_admin`。
> 实际操作以 [Agent Windows 部署说明](../agent/deploy/windows/README.md) 为准。

MineGuard 正式部署使用“统一程序 + 一矿一对签名配置包”。不为每家企业
复制源码、编译专用 EXE 或把 API 密钥写死在程序中。Platform 与 Enterprise
Agent 也不互相导入代码、不共享数据库；两端只独立实现 `contracts/` 中的
版本化文件与 HTTPS 契约。

## 1. 一座矿实际会生成什么

生成器从一份已审批 profile 一次产生：

```text
<mine-id>-v<profile-version>.mgprov       交给该矿企业 Agent
<mine-id>-v<profile-version>.mgreg        留在政府 Platform
<mine-id>-v<profile-version>-agent.activation
                                            与企业包分开交付
<mine-id>-v<profile-version>-platform.activation
                                            与政府注册包分开保管
```

两个包共享 `pair_id`，但有不同的 `bundle_id`、激活码、scrypt salt 和
AES-GCM nonce。两把交换 HMAC 也由操作系统 CSPRNG 现场生成，每矿唯一且
内容不同。

`.mgprov` 会锁定矿井、经营主体、Agent 系统身份、政府 HTTPS origin 和正式
运行开关。`.mgreg` 含同一主体的 Platform
客户登记。只有在两端分别验签、核对介质外公钥指纹并使用对应激活
码后，才能导入。

## 2. 生成时需要填的业务信息

- profile 版本和本次导入截止时间 `expires_at`；
- 签发机构 ID 和获批的 Ed25519 签发密钥 ID；
- 矿井 ID/名称、经营主体 ID/名称、企业 Agent 系统 ID；
- 企业端 HTTPS origin、政府端 HTTPS origin、企业机器上的 CA 绝对路径；
- Platform 的 system/party/key ID。

同类矿比较资料不属于首次接入条件；未配置时仍可注册和报送，只使用单矿历史
分析。生成器会拒绝未知字段、占位值、换行/控制字符、回环地址、带账号的 URL、
非 HTTPS 正式地址和不安全 CA 路径。`expires_at` 只限制首次或升级导入窗口，
不会让已正确安装的服务在日后突然停止。

## 3. 绝对不进包的内容

- LLM、新闻搜索或其他模型服务/API 密钥；
- 用户密码、密码摘要、会话密钥或默认账号；
- 数据库、备份密钥、命令、脚本、任意环境变量或插件；
- CSV 自动监听目录、设备凭据、Connector 配置或企业原始数据。

两名经办/复核用户在企业目标机器上由安装向导建立。模型、搜索、自动采集
和 Connector 是另外的可选配置域，不得借接入包绕过它们自身的授权与审计。

## 4. 信任和秘密怎么保护

- 包签名用 Ed25519，介质外审批指纹是公钥 SPKI DER 的 SHA-256；
- 包加密用 scrypt + AES-256-GCM，激活码至少包含 128 bit 随机性；
- Windows Agent 用 DPAPI LocalMachine 保护交换密钥，同时使用 NTFS ACL 限制访问；
- Platform 把签名公钥、预期指纹和 key ID 作为注册表之外的运行信任锚；
- 两端每次正式启动和 `config-check --production` 都重新验证配置锁。

把公钥文件和包放在同一可写 U 盘上不是信任根。公钥指纹和 CA 文件
SHA-256 必须从另一份获批交接记录中核对；导入向导不允许用“包旁边的公钥”
自我证明。

## 5. 简化的现场操作

Windows 正式安装包提供两个独立中文向导：

1. Platform 上的“企业接入包与注册向导”用于初始化离线签发密钥、填一座
   矿的 profile、生成四个彼此隔离的交付区，以及把政府本机留存的
   `.mgreg` 导入注册表；
2. 企业端“企业接入配置向导”可从企业交接清单自动识别 `.mgprov`、签发
   公钥、CA、实例名和审批摘要，现场只需另选激活码、核对审批记录，再输入
   两名本地用户密码。

企业导入使用同卷暂存、CreateNew 写入和原子发布。验签、解密、CA 摘要、
DPAPI、账号摘要或正式配置检查任一失败，都不会留下半配置实例。首次导入拒绝
覆盖已有同名实例；只有显式选择“更新现有实例”并通过旧锁认证、版本递增和正式
预检后，才会在不改账号和业务数据库的前提下原子换版。激活码和用户密码不作为命令行
参数，也不写入日志。

Linux/自动化环境可用同等的 `mineguard provision ...` 和
`enterprise-agent provision-import ...` 命令；通常命令只传文件路径，秘密从受保护
文件或交互终端读取。

## 6. 更新、换钥和恢复

同一矿的更新必须使用原 `.mgreg` 及其政府激活码作为上一版本证据，
`profile_version` 只能在原版本上加 1。矿井、主体、Agent 系统身份、`pair_id`、
Platform system/party 不得在原实例上偷换；政府全局应用 key ID 保持稳定，企业当前
key ID/应用 HMAC 和运输 HMAC 必须换新，并且只保留紧邻上一版的受控重叠。
降级、跳版、跨矿覆盖、未管理客户混入及已过
导入窗口都必须拒绝。

DPAPI 秘密库不是跨机器备份。更换主机时，在新机重新导入仍获批的配置包
或签发新版包，再恢复业务数据库并做一次完整 V3 报送验收。

## 7. 规范与实现依据

完整字节级协议、字段白名单、签名/AAD 计算和错误规则以
[`contracts/specs/provisioning-bundle-v1.md`](../contracts/specs/provisioning-bundle-v1.md) 为准。
Platform 和 Agent 的实现必须分别通过同一批契约样例和交叉产物测试。
